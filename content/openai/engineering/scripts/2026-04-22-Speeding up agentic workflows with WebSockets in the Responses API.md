好，我们先从背景讲起。

这篇文章的主角是一个叫 Codex 的产品，也就是 OpenAI 的 AI 编程助手。我先给你描述一下 Codex 在处理一个典型任务时到底在做什么。假设你让 Codex 去修复一个 bug，它不是直接给你输出答案，而是要经历一系列步骤：先扫描你的代码仓库，找到和这个 bug 相关的文件，读取这些文件来建立对代码库的理解，然后做出修改，最后运行测试来验证修改是不是有效，如果测试失败了还要再分析原因、再修改、再测试。

这个过程里每一个步骤，都对应着模型和 API 之间的一次交互。更重要的是，这不是简单的一来一回，而是大量的循环交互。文章里说，完成一个复杂任务可能需要几十次 Responses API 请求。

我们把这个交互模式抽象一下，它的结构大概是这样的：第一步，你向 API 发请求，问模型"下一步应该做什么"；第二步，模型回答说"我要调用某个工具，比如读取这个文件"；第三步，你在本地执行这个工具调用，拿到文件内容；第四步，你把工具执行的结果发回给 API；第五步，把这个结果加进对话历史，再问模型"下一步做什么"；然后不断重复。

这个反复循环的交互模式，在 AI 工程里叫做 agentic loop，也就是智能体循环。理解这个循环对今天的整个讨论非常关键，因为文章里所有的优化，都是围绕着怎么让这个循环跑得更快。

那么在这个循环里，时间都花在哪儿了？文章把延迟分成三个主要阶段来分析。第一个阶段叫做 API 服务时间，就是 OpenAI 的服务器接收到你的请求之后，在把它交给 GPU 运算之前需要做的一切处理工作——验证请求格式、解析输入内容、做安全检查、配置模型参数等等。第二个阶段叫做模型推理时间，就是 GPU 实际运行大语言模型、生成 token 的时间，这是整个过程中真正在"思考"的阶段。第三个阶段叫做客户端时间，就是你这边执行工具调用、构建下一次请求所花的时间。

在过去相当长的时间里，这三个阶段里最慢的是第二个——模型推理。大语言模型在 GPU 上跑就是慢，所以 API 服务那边多花几十毫秒根本无所谓，对用户体验没什么影响。但是现在，情况发生了根本性的变化。

文章提到，在 Responses API 里，之前的旗舰模型 GPT 五和 GPT 五点二，推理速度大约是每秒六十五个 token。而他们为 GPT 五点三代号 Codex Spark 这个专门为编程场景优化的快速模型定下的目标，是每秒超过一千个 token，背后用到的是 Cerebras 为大语言模型推理专门设计的硬件。

从六十五到一千，这是将近十五倍的提速，整整一个数量级的跨越。听起来非常令人兴奋对吧？但问题随之而来。GPU 跑快了，CPU 跑的那部分 API 开销没有相应缩短，甚至在整个端到端时间里的占比反而增大了。

我用一个生活里的类比来帮你建立直觉。想象一个快递站，过去快递员分拣包裹很慢，所以前台登记包裹信息、核验证件这些时间完全不是问题——反正大家都要等快递员。但现在快递员变得超级快，几秒钟就能分拣完一个包裹，这时候你突然发现，前台登记和核验的时间反而成了瓶颈。快递员在那里等着没活干，但用户还是要等，因为堵在前台。这就是硬件推理加速了，但软件层面的 API 开销没有跟上的处境。

好，背景交代清楚了，我们来看 OpenAI 是怎么一步一步解决这个问题的。

故事从二零二五年十一月说起。文章提到，他们在那个时候启动了一个针对 Responses API 的性能冲刺项目，目标是优化单次请求的关键路径延迟。在这个阶段他们做了三类优化。

第一类优化是缓存渲染好的 token 和模型配置。大语言模型处理文字的方式不是直接读字符，而是先把文字转化成 token，这个过程叫做 tokenization，中文叫分词。每次请求进来，都要对完整的对话历史做一遍 tokenization，把所有历史文字转成 token 序列，这是一笔不小的计算开销。尤其是对话历史很长的时候，这个开销会随着历史长度线性增长。优化的思路是：把已经计算好的 token 缓存在内存里，下次同样的内容直接复用，省去重复计算的时间。

第二类优化是减少网络跳转。在 API 处理请求的过程中，有些操作需要调用中间服务，比如如果请求里包含图片，需要先调用图片处理服务来解析。这些调用每一次本身可能只需要几毫秒，但在一个多轮的 agent 循环里，这些毫秒级的开销叠加起来就很可观了。优化的方向是消除不必要的中间跳转，让 API 在可以的时候直接和推理服务通信，减少数据在不同服务之间流转的额外开销。

第三类优化是改进安全栈。OpenAI 的 API 在处理每次请求时都需要运行安全检查，用各种分类器来判断对话内容是否存在违规情况。这些检查是必不可少的，但可以让它们跑得更快。优化的方向是改进某些分类器的实现，让它们能够更快地对内容打标签，减少安全检查在整体请求处理时间里的占比。

这三类优化组合在一起，让首 token 时间，也就是 TTFT——从你发出请求到收到第一个回复 token 的时间——缩短了接近百分之四十五。TTFT 是衡量 API 响应快不快最重要的指标之一，因为它直接影响用户感知到的那种"模型开始说话"的速度。

听起来已经很不错了，百分之四十五的改善，对吧？但文章明确说，这还不够。问题出在哪里？即便做了这些优化，API 服务层面的开销相对于新模型的速度来说还是太大了。用户还是要等着 CPU 把请求处理完，才能真正用到 GPU 跑出来的结果。

更深层的问题是结构性的，而不是某几个操作太慢。

文章指出，根本的问题在于他们把 Codex 的每次请求都当作完全独立的请求来处理。每次请求进来，服务器都要从头到尾完整地重新处理一遍对话历史，重新验证所有输入，重新构建模型运行所需的上下文。即使从上一次请求到这一次请求，对话历史里大部分内容根本没有变化，这些重复工作还是要全部重做一遍。

更糟糕的是，这个问题随着对话变长而越来越严重。假设你和 Codex 已经进行了二十轮工具调用，对话历史已经很长了。第二十一轮请求进来的时候，你只是在上一轮基础上新增了一个工具执行结果，但服务器还是要把前面二十轮的所有内容全部重新处理一遍。对话越长，每次请求要做的冗余工作就越多，效率就越低。

还是用类比来帮你理解。假设你在和一个助理合作写一份很长的技术文档。每次你给助理发来一条新的修改意见，他都要把整份文档从第一行读到最后一行，然后再看你的新意见，再做修改。如果文档只有一页，这还行；但如果文档已经写了五十页，每次修改都要重读五十页，这就非常浪费时间了。更好的做法显然是：助理记住自己之前已经读过、理解过的内容，你每次只发给他新增的部分，他在已有理解的基础上继续工作。

这个类比非常准确地描述了 WebSocket 方案的核心动机：建立一个持久连接，在连接的生命周期内缓存对话状态，后续请求只需要发送新增的内容，而不是每次都重发完整的历史。

好，现在我们来聊 WebSocket 这个解决方案本身，以及为什么 OpenAI 选了它而不是其他方案。

WebSocket 是一种网络通信协议，和我们平时说的 HTTP 有本质区别。HTTP 是请求-响应模式：你发一个请求，服务器给你一个响应，这次交互就结束了，下次交互需要重新建立连接。而 WebSocket 建立的是持久的双向连接：一旦握手建立成功，客户端和服务器都可以随时向对方发消息，不需要每次重新建立连接，也不需要每次都重新传输完整的上下文。

在考虑这个问题的时候，OpenAI 也评估了另一个选项——gRPC 双向流。gRPC 是 Google 推出的一套高性能远程调用框架，基于 HTTP 二点零协议，支持双向流式通信，在微服务架构里被广泛使用。从纯粹的技术性能角度来看，gRPC 双向流是很有竞争力的方案。

但 OpenAI 最终选择了 WebSocket，理由文章里说得很清楚：WebSocket 作为一个简单的消息传输协议，开发者不需要改变他们调用 Responses API 的输入和输出的数据结构。换句话说，你原来怎么调用 Responses API 的，切换到 WebSocket 之后接口形状不变，只是底层的连接方式变了。

这背后是一个非常务实的考量：开发者生态系统的迁移成本。如果选择 gRPC，开发者可能需要更换 SDK、学习新的调用方式、重构现有的业务代码。这个迁移成本对于很多已经在生产环境跑着 agent 系统的团队来说是很难接受的。而如果接口形状不变，开发者只需要改一个连接方式，其他代码几乎不用动，迁移摩擦极小。对于一个有大量外部开发者依赖其 API 的平台来说，这种兼容性优先的设计哲学是非常正确的。

好，接下来我们来看具体的实现设计。这部分是整篇文章技术含量最高的地方，我会用尽可能通俗的语言来讲清楚两个版本的设计思路。

先说原型版本。这个原型是 Codex 团队里一位对整个 API 技术栈都有深入理解的工程师，利用一个晚上跑 Codex agent 搭出来的。文章用了一句话让我印象特别深刻，大意是说"这个原型改变了我们对 Responses API 延迟极限的认知"。一夜之间搭出来的原型，就改变了整个团队对可能性边界的判断，这种快速迭代的能力是工程文化里非常珍贵的东西。

在原型版本的设计里，整个智能体的多轮交互被建模成一个单一的、长期运行的 Response。我来解释一下这是什么意思。

在普通的 HTTP 模式下，每次工具调用是一个独立的请求-响应周期。模型生成工具调用，你执行工具，把结果加进对话历史，再发起一个新的请求，问模型下一步做什么。每次都是独立的一次 HTTP 请求。

而在原型版本里，整个 agent 循环被看作一个单一的 Response，这个 Response 可以在工具调用的等待过程中暂停，在工具结果回来之后继续。具体的机制是这样的：当模型在推理过程中决定要调用某个工具时，服务器端的推理循环会进入异步等待状态，同时通过 WebSocket 向客户端发送一个叫做 response.done 的事件，里面包含了模型想要执行的工具调用信息。客户端收到这个事件后，在本地执行工具调用，拿到结果，然后通过 WebSocket 发回一个叫做 response.append 的事件，里面包含工具执行的结果。服务器收到这个事件，把工具结果放进模型的上下文，然后解除推理循环的等待状态，让模型继续生成。

文章在这里用了一个非常精妙的类比，我觉得是帮助理解这个设计最有效的方式。他们说，这个机制和模型调用托管工具的逻辑是完全一样的。什么叫托管工具？就是服务器端直接管理的工具，最典型的例子是联网搜索。当模型在推理过程中决定要搜索某个信息时，推理循环会暂停，服务器去调用搜索服务，拿到结果，把结果放进模型上下文，然后继续推理。整个过程对于推理循环来说，就是在等一个远程服务的响应。

原型设计做的事情完全一样，只是把这个"远程服务"换成了"客户端本地执行的工具"。推理循环暂停，把工具调用信息发给客户端，等客户端把结果发回来，把结果放进上下文，继续推理。从推理循环的角度来看，它只是在等一个响应，不管这个响应来自远程服务还是来自客户端，逻辑是一样的。

这个设计的威力在于它几乎完全消除了整个 agent 循环里的重复性工作。整个 agent 运行开始之前的准备工作——验证输入、配置模型、做安全检查——只需要做一次；工具执行期间推理循环暂停等待，不需要重复处理上下文；整个 agent 运行结束之后的收尾工作——记录日志、计费处理——也只需要做一次。这和之前每次请求都要完整走一遍所有步骤的 HTTP 模式相比，效率提升是根本性的。

但原型版本有一个明显的问题：它引入了全新的、不熟悉的 API 交互模式。response.append 这种概念对于已经在用 Responses API 的开发者来说是陌生的，他们需要理解这套新机制，并且重写他们的集成代码，这个迁移成本是不可忽视的。

于是，在最终上线的生产版本里，OpenAI 做了一个重要的设计取舍：回归熟悉的 API 形状，在兼容性上做出妥协，换取更低的迁移门槛。

生产版本的核心思路是这样的：在 WebSocket 连接上，继续使用开发者已经熟悉的 response.create 方式来发起请求，请求的格式和之前一模一样；通过一个叫做 previous_response_id 的参数来告诉服务器"上一次响应是哪个"，让服务器从连接级别的内存缓存中恢复之前的状态，而不是重新处理完整的对话历史。

这里最关键的概念是"连接级别的内存缓存"，英文是 connection-scoped in-memory cache。当你建立一个 WebSocket 连接后，服务器会在这个连接的生命周期内维护一份缓存。只要连接还活着，这份缓存就存在。当你发下一次 response.create 请求并且带上 previous_response_id 时，服务器不会重新处理完整的对话历史，而是直接从缓存中读取上一次的状态，然后只处理新增的部分。

那么这份缓存里到底存了什么？文章列出了几类具体内容：第一是上一次的 response 对象本身；第二是之前所有的输入和输出条目；第三是工具定义和命名空间，也就是这次 agent 运行里定义了哪些工具、工具的接口是什么；第四是可复用的采样中间结果，比如之前已经渲染好的 token 序列。

有了这份缓存，OpenAI 能做到几个具体的优化：其一，安全分类器和请求验证器只需要处理新增的输入内容，而不是每次都重新扫描完整的对话历史；其二，token 缓存可以直接在已有的基础上追加，跳过不必要的重复 tokenization；其三，模型的选路和路由逻辑可以在连接内部复用，不需要每次请求都重新计算用哪个版本的模型、路由到哪个推理服务；其四，一些不阻塞推理的后处理工作，比如计费逻辑，可以和下一次请求的处理并行进行，而不是必须在响应发出之前全部完成。

我特别想展开讲一下最后这点，因为它代表了一种很优雅的并行化思路。在 HTTP 模式下，每次请求完成之后，服务器需要做一些收尾工作，比如记录这次调用消耗了多少 token、该如何计费。这些工作虽然和推理本身无关，但在请求-响应模型里，它往往必须在给你发响应之前或者在两次请求之间的间隙里完成。而在 WebSocket 模式下，连接是持久的，这些后处理工作可以和下一次 response.create 的前处理工作并行进行，从用户视角来看就是：你觉得两次模型响应之间的等待时间缩短了，但其实是因为后台把原来串行的工作变成了并行。

文章里把生产版本的设计目标描述为：尽可能接近原型版本的最小化开销设计，但使用开发者已经熟悉、已经围绕它构建了业务逻辑的 API 形状。这个目标的背后是一种成熟的工程判断——有时候一个稍微次优但容易落地的方案，比一个最优但难以采用的方案要有价值得多。

好，来看实际效果。

在正式大规模上线之前，OpenAI 组织了一个 alpha 测试，找了几家核心的 AI 编程工具创业公司提前接入 WebSocket 模式，在真实流量下测试效果。alpha 用户的反馈是他们的 agent 工作流速度提升了最多百分之四十。

正式上线之后的数据更加清晰和令人信服。文章提到了几个具体案例。

Codex 自己迅速把大部分 Responses API 流量迁移到了 WebSocket 模式，看到了显著的延迟改善。对于 GPT 五点三 Codex Spark 这个快速模型，他们不但实现了每秒一千 token 的目标，在生产流量里还看到了每秒高达四千 token 的爆发速度。这个数字的意义在于：它证明了 Responses API 完全有能力跟上比现有模型快得多的推理速度，不会成为限制上限的那块短板。

Vercel，就是那个做前端部署和开发者工具平台的公司，把 WebSocket 模式集成进了他们的 AI SDK，在实际流量中看到了最多百分之四十的延迟下降。

Cline，一个专门处理多文件代码修改场景的 AI 工具，他们的多文件工作流速度提升了百分之三十九。多文件场景对这个优化来说特别典型，因为它涉及大量的工具调用——读文件、写文件、分析依赖关系——正是这类多轮工具调用的场景从 WebSocket 缓存里获益最大。

Cursor，这个大家可能很多人用过的 AI 代码编辑器，OpenAI 模型在 Cursor 里的响应速度提升了最多百分之三十。

这四组数字——百分之四十、百分之四十、百分之三十九、百分之三十——都是真实生产环境里跑出来的数据，不是实验室基准测试。这意味着对于真实用户来说，等待时间实实在在地减少了将近三分之一到四成，是完全能感知到的体验提升。

现在我们来说说最关键的部分：这对你的实际工作意味着什么，你应该怎么用，以及有哪些坑需要提前知道。

首先是适用场景的判断。WebSocket 模式最适合的是那种需要多轮工具调用、对话历史会持续积累的 agent 工作流。如果你的场景是单次对话——用户发一条消息，模型回一个答复——这种场景从 WebSocket 里获得的收益是相对有限的，因为你没有跨请求复用状态的需求。

但如果你的场景符合这些特征：每次 agent 运行会有许多轮工具调用、对话历史随着运行进行变得越来越长——那 WebSocket 模式就非常适合。典型的例子有这几类：一是代码 agent，需要反复读文件、写文件、运行测试、分析错误、再修改；二是研究 agent，需要多次搜索、总结、提炼、再深挖；三是数据处理 agent，需要多次查询数据库、做计算、根据计算结果调整查询、再计算。这些场景共同的特征就是高频工具调用和不断积累的对话历史，正是 WebSocket 连接缓存能发挥最大价值的地方。

第二，关于如何迁移。从开发者的角度来看，迁移到 WebSocket 模式的核心变化只有两点：第一，把底层连接方式从 HTTP 换成 WebSocket；第二，在发后续请求的时候带上 previous_response_id，告诉服务器这次请求是上一次响应的延续。其他的请求参数——你的 model 参数、system prompt、tools 定义——格式都不变，这就是 OpenAI 刻意在生产版本里保留熟悉接口形状的价值所在。

值得一提的是，OpenAI 官方的 SDK 已经封装了 WebSocket 连接的建立和管理，你不需要自己手写 WebSocket 握手逻辑，直接用 SDK 里提供的接口就好。

第三，要注意哪些坑，这里我给你梳理几个重要的点。

第一个坑是连接管理和重连逻辑。WebSocket 是持久连接，这和 HTTP 的无状态、可随时重试的特性很不一样。网络是不可靠的，连接随时可能因为超时、网络抖动或者服务器重启而断开。如果你没有实现健壮的重连逻辑，连接断了之后你的 agent 循环就中断了，而且由于服务器端的缓存是和连接绑定的，连接断了缓存也就没有了，你可能需要从头开始或者从某个检查点恢复。所以在生产环境里使用 WebSocket 模式时，一定要认真对待连接生命周期管理，包括心跳机制、断线检测、自动重连，以及重连后如何恢复 agent 的运行状态。

第二个坑是状态的双重维护。虽然 WebSocket 模式允许你依赖服务器端的连接缓存来避免重发完整历史，但在生产系统里，你不能完全依赖服务器端缓存作为你的单一真相来源。万一连接断了，你需要能够重建状态。这意味着客户端也需要维护足够的对话历史，能够在必要时回退到 HTTP 模式，用 previous_response_id 加完整历史的方式继续任务，或者从某个已知的检查点重新发起一个 WebSocket session。

第三个坑是连接复用的边界理解。文章里说缓存的生命周期是"连接的生命周期"，也就是说缓存是和特定的 WebSocket 连接绑定的，不同连接之间不共享缓存。这对于做了负载均衡的生产系统很重要——同一个 agent session 的所有请求，必须路由到同一个 WebSocket 连接上，而不能因为负载均衡策略把不同请求分散到不同连接。如果你的基础设施有多层负载均衡，需要确认 WebSocket 粘性会话是配置正确的。

第四个坑是并发场景下的连接管理。如果你的系统需要同时跑多个相互独立的 agent 任务，你需要为每个任务维护一个独立的 WebSocket 连接，因为每个连接的缓存是独立的。别把不相关的任务请求混在同一个连接里发，否则 previous_response_id 关联到错误的上下文，结果会很混乱。

我还想聊一下这篇文章给我带来的更宏观的思考，这也是我认为这篇文章超越"一个新功能上线了"的公告文章的部分原因。

文章里有一个判断，我觉得对 AI 工程师来说非常值得记住：随着模型推理速度越来越快，围绕推理的那些服务和系统——API 层、安全检查层、网络传输层——也需要相应地提速，才能把推理速度的提升真正传递给终端用户。

这背后是系统工程里的木桶原理——一个系统的性能上限，由最慢的那个环节决定。在过去几年里，模型推理一直是那块最短的木板，所以几乎所有的优化精力都放在模型本身：怎么让模型更聪明、更快、消耗更少的内存。但当模型推理速度提升了一个数量级之后，原来不引人注意的 API 服务开销、网络传输延迟，突然就暴露为新的瓶颈。

这个模式在计算机历史上反复出现过。CPU 越来越快，内存访问延迟变成了瓶颈；内存带宽提升了，磁盘 IO 成了瓶颈；网络带宽增大了，路由跳转的延迟成了瓶颈。每当一个组件的性能大幅提升，系统就会暴露出下一个最慢的环节。AI 推理也不例外，而且这个过程还会继续——随着推理速度继续提升，网络传输本身、客户端的处理速度，都可能陆续成为新的瓶颈。

这对我们普通的 AI 工程师有一个很实际的启示：当你在优化一个 AI 应用的性能时，不能只看单次 API 调用的延迟，而要把整个 agent 循环拆开来看，找出各个阶段的时间占比，定位你的瓶颈到底在哪里。有时候真正的瓶颈不在模型，而在你的工具执行效率、上下文构建的方式、甚至你的代码里不必要的串行等待。

还有一个值得思考的设计哲学层面的点。文章里描述了两个版本的设计：技术上更优但接口陌生的原型版本，以及性能稍微次优但接口兼容的生产版本。这个取舍的背后是一种非常成熟的工程判断——当你的系统有大量外部用户依赖时，接口兼容性和迁移摩擦是真实的工程成本，不能因为某个方案技术上更优就无视这个成本。一个没有人迁移过来用的完美技术方案，其价值是零。

从二零二五年三月 Responses API 发布，到二零二六年四月 WebSocket 模式正式上线，这中间经历了差不多一年的时间。但从 WebSocket 这个想法产生到进入生产，文章说只花了几个星期。这个速度背后是 API 团队和 Codex 团队深度协同的结果，也是有一个真实的产品需求——Codex 用户的体验——在驱动工程决策的结果。技术改进有时候需要一个真实的压力源，这个压力源就是 GPT 五点三 Codex Spark 带来的每秒一千 token 的推理速度，它让 API 开销这个原本可以忽略的问题变得不可能继续忽视。

好，来做个总结。

这篇来自 OpenAI 的工程博文，讲的是他们如何通过引入 WebSocket 持久连接，把智能体工作流的端到端延迟降低了百分之四十。这个数字背后是分层的优化：从单次请求的 token 缓存、网络跳转减少、安全栈提速，到 API 底层传输协议的根本性改变，把每次请求独立处理的 HTTP 模式换成了连接内状态共享的 WebSocket 模式。生产数据非常有说服力：GPT 五点三 Codex Spark 在真实流量里看到了每秒四千 token 的爆发速度，Vercel、Cline、Cursor 等主流开发工具都报告了百分之三十到四十的延迟改善。

我个人的点评是：这篇文章的价值在两个层面上值得关注。第一个层面是直接可用的技术方案，WebSocket 模式已经上线了，你现在就可以去接入，如果你在构建多轮工具调用的 agent，应该认真考虑迁移。第二个层面是工程思维的示范，它告诉我们：AI 系统的优化不能只盯着模型本身，整个系统里每个环节的效率都重要，而且随着模型越来越快，那些之前被推理延迟遮蔽的"小"开销，会一个一个浮出水面成为新的挑战。
