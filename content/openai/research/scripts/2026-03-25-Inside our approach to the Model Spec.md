好，我们今天来聊一篇来自 OpenAI 官网的重量级文章。英文标题是 Inside our approach to the Model Spec，我把它翻译成中文是"走进 Model Spec 方法论：OpenAI 的 AI 行为规范是怎么设计的"。这篇文章发表于二〇二六年三月二十五日，距今大约五个半月。

虽然还没超过六个月，但对于 AI 领域这种变化速度，五个月绝对是一段值得做时间坐标定位的时间。二〇二六年三月，AI 发展处于什么阶段？那个时候，大语言模型已经不再是单纯的问答工具了。它们快速演化成了能够调用外部工具、执行多步骤任务的 agent 系统，也就是我们说的智能体。模型在代码生成、数学推理、复杂分析上的能力在持续跃升，AI 的部署场景也在爆炸式增长，从个人助手到企业 workflow，从代码生成到内容创作，再到医疗、教育、法律咨询。整个行业对 AI 的讨论，也在快速从"这个技术能不能用"转向"这个技术应该怎么用、应该遵守什么规则"。

正是在这个背景下，OpenAI 发表了这篇文章。要注意，这不是他们发布 Model Spec 本身的那篇文章，而是专门解释 Model Spec 背后设计哲学和运作机制的元文章。换句话说，他们不只是给你看规则，还在告诉你这些规则是怎么被设计出来的，为什么要这样设计，又是如何随着时间演进的。这对于任何认真做 AI 产品或者关心 AI 治理的人来说，都是非常值得深度阅读的一篇文章。

好，先给大家建立背景认知。

Model Spec 是 OpenAI 的模型行为规范，是一份公开文件。它定义了 OpenAI 希望自己的模型在遵循指令、处理冲突、尊重用户自由，以及在各种各样的查询场景下保持安全这些方面应该如何表现。但这篇文章讲的不是 Model Spec 的具体条文，而是那些条文背后的设计逻辑。

OpenAI 在文章里说得很清楚，Model Spec 并不是在宣称他们的模型今天就已经完美地按照它行事了。他们把 Model Spec 同时定位成描述性的和目标性的，既描述当前的行为意图，也是他们希望模型朝着走去的方向。这种双重定位非常有意思，因为它把 Model Spec 变成了一个持续演进的活文档，而不是一次性发布就束之高阁的静态文件。文章里有一个细节很能说明这一点：他们说 Model Spec 通常比当前模型超前零到三个月左右，描述的是他们已经在做或者有明确近期计划实现的行为。

好，第一个核心点，我想讲 Model Spec 的整体结构，以及它里面一个经常被人忽视的关键设计。

Model Spec 里包含了几种不同类型的内容，这是经过深思熟虑的设计安排。首先是一个高层次的意图声明，也就是引言部分，明确了三个目标。第一个目标是迭代式地部署能赋能开发者和用户的模型；第二个目标是防止模型对用户或其他人造成严重伤害；第三个目标是维持 OpenAI 的运营许可，通俗点说就是商业上的可持续性。这三个目标的顺序本身就是一个公开的价值声明，安全和有益排在商业利益之前。

但这里有一个非常重要、值得特别强调的细节：这个引言不是直接给模型的指令。文章里明确说，"造福人类"是 OpenAI 的目标，而不是他们希望模型自主去追求的目标。让我用一个类比来解释这为什么重要。

假设你是一家公司的高管，公司使命是"让用户生活更美好"。你不会告诉每个员工"你的工作就是自己判断什么对用户最好，然后去做任何你认为对的事情"，因为那样会产生混乱，每个员工都可能做出各种"自认为是好的"但实际上相互矛盾的行为。你会建立流程、设定权限、明确职责边界，让员工在这个框架内行事。OpenAI 对模型的逻辑完全一样。他们不希望模型成为一个自主的道德仲裁者，不希望模型根据自己对"什么对社会好"的判断来决定是否遵守指令。他们希望模型遵循一个指令链，在这个链条内行事。文章里给的理由非常坦诚：如果他们训练模型根据自己对社会好坏的判断来执行指令，那 OpenAI 就在扮演一个在极大规模上裁决道德的角色，那是他们不愿意、也不应该承担的位置。我个人认为这个思路非常清醒，也非常重要。

除了高层次意图声明，Model Spec 里还有一类值得特别提的内容，叫做公开承诺。这些承诺超越了直接可测量的模型行为，涉及训练意图和部署约束。比如在第一方部署，也就是 ChatGPT 这类场景里，他们承诺不会用系统提示词来故意破坏客观性；以及他们承诺不会为了收入或者无益的用户留存时间来优化模型回应，也就是说，不会让模型变成制造焦虑或者强迫你刷屏的工具。这些是写在 Model Spec 里的明确承诺，是对公众的公开责任状。

第二个核心点，我来深入讲指令链和规则的层次结构，这是 Model Spec 最核心的工程设计。

在实际使用中，指令来自不同的地方。OpenAI 通过训练和规范给模型输入基础指令；开发者通过系统提示词，也就是 system prompt，给出针对具体产品场景的指令；用户在对话里给出即时的请求。这三层来源之间的指令经常会发生冲突，Model Spec 需要给出处理冲突的原则。Model Spec 给出的答案是一套权限层级制度。每一条规范和每一条指令都被赋予了一个权限级别，当冲突出现时，模型应该优先遵守权限更高的指令的字面意思和精神。

这套层级体系产生了两大类规则。

第一类是硬性规则，也就是绝对边界，不管是用户还是开发者都无法覆盖。它们大多是禁止性的，要求模型避免那些可能导致灾难性风险或直接物理伤害的行为，避免违法行为，以及避免破坏指令链自身。文章里有一个很有意思的类比，他们把 AI 比作基础互联网基础设施，类似于互联网协议。就像互联网协议只规定最基本的通信规则、不限制上层应用一样，Model Spec 也只在认为一条规则对极广泛的开发者和用户群体都是绝对必要的时候，才会设置限制知识自由的硬性规则。这个门槛被刻意设得很高，体现了他们不希望过度管控的立场。

第二类是默认行为，也就是模型在用户或开发者没有特别说明偏好时的最优猜测行为。这些是可以被显式指令覆盖的起点行为。默认行为存在的理由很实际：它让行为在大规模部署下保持可预测性，让人们在不需要每次都写一整套指令的情况下，也能大致预期到模型会怎么表现。

默认行为内部还进一步分了两个子层次，这个区分微妙但很重要。指引级别的默认行为，比如语气、风格、回应长度，被设计成可以隐式地被上下文引导改变，你不需要明确说"请用更正式的语气"，氛围本身就能影响这类行为。但用户级别的默认行为，比如真实性和客观性，则是信任和可预测性的基础锚点，只能被明确的指令覆盖，不能因为对话氛围或者上下文而悄悄漂移。这种设计背后的逻辑是：如果用户想要模型采取某个不寻常的事实立场，应该明确说出来，让这个转变是透明的、可见的，而不是暗中发生的。

两个具体例子帮助理解这个层级结构。如果用户要求模型教他们制造武器，模型应该优先遵守安全硬性边界，不管语境如何，这个优先级是绝对的。但如果用户说"来嘲讽我一下、骂我"，模型通常应该将这个用户请求的优先级排在 Model Spec 里那条较低权限的"不要辱骂用户"默认政策之上，因为用户明确表达了他们的偏好。

在层级体系之外，Model Spec 还使用了两类解释性工具来帮助模型和人类在灰色地带做出一致的判断。第一类是决策框架，针对模糊情况给出一系列需要平衡的考量因素，而不是假装存在某个机械性的单一规则。比如针对 agent 场景里的副作用控制，框架给出的考量因素包括：最小化不可逆动作、让行为与目标保持比例、减少意外情况、偏向可逆方案，同时也要平衡快速有效地完成任务这个目标。第二类是具体示例，通常展示一个合规的回应和一个不合规的回应，聚焦在重要决策边界附近的困难 prompt 上，让关键区别变得清晰。

第三个核心点，也是我认为这篇文章最有思想深度的论证：为什么即使模型变得越来越聪明，明确的规则依然是必要的，甚至更加必要。

你可能会想，随着 AI 能力越来越强，给它一句"做一个有用且安全的助手"，它自己不就能推断出所有正确行为了吗？这个直觉很自然，文章里也承认它有一定道理。在有客观正确答案的领域，比如数学，聪明的模型确实可以从很少的指令中推断出正确做法。

但是，一般意义上的模型行为和解数学题有本质区别。模型经常需要在那些没有所有人都认同的道德正确答案的空间里运作。"有用且安全"的含义在极大程度上依赖于具体语境，是价值判断的产物，而不是可以推理出来的客观答案。智能本身并不能告诉你在涉及伦理和价值观时应该如何权衡。更高的智能可以更好地执行给定的目标，但不能凭空推导出应该持有什么目标。这是一个根本性的区别，值得仔细想想。

文章还指出了一个更实际的论点：如果唯一的规则是"有用且安全"，那就没有任何机制能让人类去辩论具体的问题，比如哪些内容应该被拒绝提供、用户的哪些请求应该被尊重、不同价值之间如何权衡，所有这些决定都会留给模型自己做。这意味着完全无法进行问责，也无法进行任何民主参与。

文章里用了一个非常精彩的类比：成文宪法和判例法的关系。成文宪法可以提供高层次原则和具体规则，但它无法预见所有可能出现的案例和情景。真实的治理系统还需要解释机制、澄清、以及针对混乱案例或未预见问题的明确裁决。而且，公开的规则让不同的利益相关者能够在存在分歧的情况下依然能够协调行动，同时规则本身也约束了变化的方式：任何变化都必须是明确的、公开的，而不能悄悄发生。

Model Spec 被设计成同时扮演所有这些角色：一份原则声明、一套公开行为框架，以及一套随时间修订规范的流程机制。

文章在这里还说了一句很有预见性的话：随着模型变得更强大、更自主、部署范围更广，模糊性的代价实际上在增加，而不是减少。这让清晰的行为框架变得更加重要，而不是更不重要。我个人非常认同这个判断。

第四个核心点，我来讲 Model Spec 是如何被写出来和持续更新的，这个过程本身就很有参考价值。

Model Spec 通过一个开放的内部流程来开发，OpenAI 的任何员工都可以对其评论或提议修改，最终更新由一批跨职能的利益相关者批准。实际上，数十人直接贡献了文本，更多来自研究、工程、产品、安全、政策、法务、传播、全球事务等不同职能的人参与了审查。

文章里提到了一个让他们感到惊喜的发现：真正的共识往往是可以达成的，尤其是当他们强迫自己把权衡写得足够精确，让分歧变得足够具体的时候。这句话看起来平淡，但实际上蕴含了很深的实践经验。很多时候人们争论不休，是因为双方都在用模糊的语言描述自己的立场。一旦被迫把立场写成具体的规则和例子，很多表面上的分歧就会消失，真正的分歧也会变得更容易处理。

驱动 Model Spec 更新的输入来自几个主要方向。首先是公众的问题和反馈，包括模型行为上的困惑、边缘案例和失效模式。其次是内部问题，比如在开发和测试中发现的歧义，不同合理解释导致不同行为的情况。第三是行为和安全政策的更新，当更高层次的约束或承诺发生变化时，Model Spec 需要反映这种新结构。第四是新能力和新产品的出现，比如多模态交互、自主 agent、以及专门针对未成年用户的场景，都需要 Model Spec 跟上步伐。

写 Model Spec 的设计原则里有几条特别值得记住。第一是清晰和精确，文章里的原话是"'诚实'是一个好的价值观，但不是一个完整的决策程序"，Model Spec 应该把分歧磨得更尖锐，而不是用让人觉得舒服的模糊措辞把分歧掩盖掉。第二是实质性规则，读者应该能够拿一个真实的 prompt，然后产生出一个另一个读者认为明显在界限之内或之外的答案。第三是高信噪比的例子，好的例子应该直击规范行为的核心难点，把困难的冲突暴露出来，并对如何解决这些冲突采取清晰立场。

这里还有一个设计原则我个人认为非常重要，文章把它叫做"接口而非实现"。他们把 Model Spec 定位成描述他们想要什么行为，而不是描述如何在训练上实现这种行为。具体的训练配方、内部 token 格式等实现细节，他们刻意不写进 Model Spec，因为这些细节可能会变化，而期望的行为本身可能不变。更重要的是，Model Spec 的主要受众不是模型本身，而是人类，包括 OpenAI 的员工、用户、开发者、研究者和政策制定者。

第五个核心点，我来讲当前模型和 Model Spec 之间存在的差距，以及他们怎么评估和弥合这个差距。

文章里非常坦诚地承认了这个差距，并给出了几个原因。第一，模型训练可能落后于 Model Spec 的更新，因为 Model Spec 描述的是他们正在朝向的行为。第二，训练可能无意间教会了与 Model Spec 不一致的行为，他们把这种情况当成严重的 bug 来对待。第三，训练永远不可能覆盖所有可能的行为空间，真实使用中包含大量只有在规模上才会出现的长尾语境和边缘案例。第四，泛化可能与预期不同，模型可能在训练中因为非预期原因产生了"正确"的输出，这会导致在与训练场景不同的新情况中出现意外行为。

针对第四个问题，他们提到了一个叫 deliberative alignment 的技术，中文可以叫"深思熟虑式对齐"。虽然这篇文章里没有详细展开这个技术的原理，但核心思路是让模型在做出关键决定之前，通过某种明确的推理过程来应用 Model Spec 的原则，而不是纯粹依赖隐式的训练内化。文章也诚实地说，这并不是一个完整的解决方案，只是他们正在投入的一个研究方向。

和这篇文章同期发布的，还有一套叫 Model Spec Evals 的公开评估套件。这是一个基于场景的评估体系，尝试用少量有代表性的例子覆盖 Model Spec 中尽可能多的断言，帮助追踪模型行为和 Model Spec 可能出现偏离的地方，也帮助检验模型是否按照预期方式来解读 Model Spec。值得注意的是，这只是他们更广泛评估策略的一部分，还包括针对特定安全领域、真实性和拍马屁倾向、个性风格以及能力等维度的更精细评估。

好，核心内容讲完了，我们来谈谈这对你的实际工作具体意味着什么。

首先对于直接使用 OpenAI API 的开发者来说，理解 Model Spec 的层级结构能帮助你写出更有效的系统提示词。这里有几个非常具体的实践要点。

第一个要点，区分哪些行为是硬性规则，哪些是默认行为，然后把精力花在对的地方。硬性规则你改不了，不要花时间去尝试绕过它们，那是徒劳的，还可能造成奇怪的模型行为。但默认行为是完全可以被你的系统 prompt 覆盖的。比如语气是否正式、回应是否主动给出观点、内容的详细程度、是否主动提示风险，这些都属于默认行为的范畴，通过明确的指令是可以有效调整的。

第二个要点，利用权限层级来理解你的系统 prompt 的权限边界。作为开发者，你处在这个层级的第二层，OpenAI 的训练层在你上面，用户的请求层在你下面。这意味着你可以在系统 prompt 里为你的具体产品场景设定更细化的规则，用户的请求会在你的规则框架内被处理。但你无法覆盖 OpenAI 的硬性规则，无论你的系统 prompt 怎么写。如果你在构建面向特定行业的产品，比如医疗、法律或教育，了解哪些默认行为你可以调整、哪些你不能调整，对你设计产品行为至关重要。

第三个要点，理解"用户级别默认行为"的隐含含义。像真实性和客观性这类默认行为，只能被明确的指令覆盖，而不能被隐式的语境暗示改变。这在实践中意味着：如果你的产品需要模型在某个特定场景里采取一种特殊立场，比如说"在这个创意写作场景里，你可以提供虚构的第一人称叙述而不需要加免责声明"，你必须在系统 prompt 里明确写出来，而不能期望上下文会让模型自然漂移到那个方向。隐式期望往往会落空，明确指令才是可靠的。

第四个要点，特别针对正在构建 agent 系统的工程师。Model Spec 里有专门关于 agent 场景的规范，核心原则是在自主完成任务的同时谨慎控制对真实世界的副作用。文章给出的几个具体考量因素是：最小化不可逆动作、让行为与目标保持比例关系、减少不可预期的意外情况、以及在可能的情况下偏向可逆的方案。如果你在设计 agent 的工具调用策略或者多步骤任务规划，把这几个原则内化进设计决策，不仅会让你的系统更健壮，也会与模型的内置价值取向更一致，减少不必要的摩擦和意外行为。举个例子，如果你的 agent 有删除文件的能力，优先设计成移入回收站而不是直接永久删除，这完全符合"偏向可逆方案"这条原则，模型对这类工具调用的配合程度也会更高。

第五个要点，关于 Model Spec Evals 这套公开评估套件。如果你在对模型进行微调或者针对特定场景做行为优化，这套 Evals 可以作为一个基准参考，看看你的调整是否在 OpenAI 认为重要的行为维度上产生了预期之外的偏移。这类公开基准的价值不只在于它的完整性，更在于它提供了一套行业内可以共同参照的语言。在你和团队讨论"模型在这个场景下表现得合不合适"的时候，有一套外部框架可以参照，比纯粹依赖主观判断要稳健得多。

还有一个更宏观的视角值得一提。文章末尾讲到了一个叫 collective alignment 的方向，中文可以叫"集体对齐"。OpenAI 表示他们正在投资公众反馈机制，目标是帮助人类保持对 AI 使用方式和 AI 行为塑造方式的控制权。虽然这部分说得比较宏观，没有给出具体的机制细节，但它预示着 AI 行为规范这件事，未来不会只是公司内部的技术和商业决策，而是会有越来越多的公众参与路径和民主协商机制。对于关心 AI 治理、或者想要在这个领域发挥影响力的朋友来说，这是一个值得持续关注的趋势。

还有一点想拎出来单独说。文章里提到 Model Spec 有三个成功标准，这三个标准本身就是很有价值的框架，不只适用于 AI 行为规范。第一个是可读性，相关的人能够形成准确的行为预期，并且在行为出乎意料时能够找到对应的文字作为依据，而不是一头雾水。第二个是可操作性，这份文件能被实际用来设计评估、诊断问题、做出一致的产品决策，而不只是表达美好的价值观。第三个是可修订性，这份文件能够随着实践学习而演进，同时不变成一个让人无所适从的移动目标。如果你在你的团队里也在制定某种行为规范或者产品原则文档，这三个标准是非常好的自查框架。

好，最后来做个总结。

这篇文章最核心的价值，是把 Model Spec 重新定位为一套治理基础设施，而不只是一份规则列表。它同时扮演了四种角色：对外的透明度工具，让公众能够理解和质疑 OpenAI 的行为选择；内部的协调机制，给不同职能部门提供共同的语汇和决策框架；评估和改进的锚点，让模型训练有一个明确的行为目标可以对齐；以及公众参与 AI 治理的接入口。

我个人认为，这篇文章背后最重要的一个洞见是把 AI 治理类比成宪法治理。这个类比说明了我们正在进入一个需要认真对待 AI 行为的合法性机制和问责机制的时代。智能不能替代价值观，能力不能替代规则，这是这篇文章反复在表达的核心观点。Model Spec 不是终点，而是一个开端，是一套让所有利益相关者，包括开发者、用户、研究者、政策制定者，能够围绕其进行有意义对话的公共起点。

如果你还没有读过 OpenAI 的 Model Spec 原文，我强烈建议你花半个小时去读一读。不是因为你需要记住每一条规则，而是因为理解一套 AI 系统背后的行为框架，是任何认真从事 AI 产品开发或者 AI 研究的人都应该具备的基础认知。在你每次写系统提示词、每次设计模型的使用场景、每次讨论 AI 产品应该怎么表现的时候，这套框架都在隐隐地起作用。理解它，会让你的判断更准确，你的设计更有意识。
