我们逐个来拆解核心挑战。

先说第一个大问题：写压力和 PostgreSQL 的 MVCC 困境。

PostgreSQL 有一个核心机制叫 MVCC，全称是 Multi-Version Concurrency Control，多版本并发控制。听起来很专业，我用一个生活化的例子解释。

你可以把数据库里的每一行数据想象成一张便利贴，贴在某个位置上。当有人要修改这条数据的时候，PostgreSQL 的做法不是擦掉旧内容重新写，而是在旁边再贴一张新的便利贴，写上修改后的内容，同时把旧便利贴标记为"即将废弃"。这样做的好处是读和写互不干扰：读操作不需要等待写操作完成，因为它可以直接去读旧的便利贴；写操作也不需要等待读操作，因为它只是在旁边贴了新的。这就是"多版本"的含义，并发性能非常好。

但这个机制有一个严重的代价：如果写入非常频繁，那些"即将废弃"的旧便利贴就会越堆越多，占据大量空间。这些废弃的旧数据在 PostgreSQL 里叫做"死元组"，英文叫 dead tuples。积累的死元组不仅占用磁盘空间，还会影响查询性能，因为查询的时候需要扫描更多的版本才能找到最新的那条数据。另外，MVCC 还带来了表膨胀和索引膨胀，随着时间推移，表和索引占用的磁盘空间越来越大，维护成本越来越高。

PostgreSQL 有一个叫 autovacuum 的后台进程专门负责清理这些死元组，就像一个定期来清理便利贴的清洁工。但问题是，如果写入速度太快，清洁工根本来不及清理，死元组堆积的速度超过了清理速度，整个表就开始膨胀，性能越来越差。文章作者 Bohan Zhang 还专门在卡内基梅隆大学的 Andy Pavlo 教授合写过一篇文章，标题是《我们最痛恨 PostgreSQL 的那个部分》，专门深入讨论了这些问题，感兴趣的朋友可以去搜来读。

OpenAI 的应对策略是什么？他们把那些可以分片的、写入量很大的业务，迁移到了微软 Azure 的 CosmosDB 上。CosmosDB 是一个分布式数据库，天生支持水平扩展，更适合处理高写入场景。与此同时，他们在应用层做了大量优化：引入了懒写机制，也就是 lazy write，不是每次状态变化都立刻写数据库，而是攒一攒批量写入，减少写操作频次；修复了许多应用层的 bug，这些 bug 会导致重复写入，同一条数据被写了好几遍，但其实只有最后一次写入是有意义的；还有，当需要给现有数据批量加一列新值——这个操作叫回填——他们会严格限制速率，宁愿让这个过程持续整整一个星期，也不愿让它产生写入峰值冲垮数据库。

另外，他们还做出了一个硬性规定：不允许在现有 PostgreSQL 部署上新增表。所有新功能如果需要新建表，必须放到 CosmosDB 等分片系统上。这是一个从架构层面强制约束写入扩张的做法，非常值得借鉴。

第二个大问题：昂贵的查询，和那个臭名昭著的十二表联查。

在关系型数据库里，Join 操作，也就是联查，是把多张表的数据关联在一起查询。比如你要查一个用户的订单详情，可能需要把用户表、订单表、商品表、地址表关联起来才能得到完整信息。这是关系型数据库的强项，但也是一把双刃剑：联查越多，数据库需要做的计算就越多，代价越大。

文章里提到了一个让人印象深刻的案例：他们曾经发现了一个查询，居然联查了十二张表。想象一下，数据库需要在内存里把十二张表的数据拼在一起，做十一次联表操作，这个计算代价有多恐怖。更可怕的是，这种查询的成本是随着数据量非线性上涨的，在流量低的时候可能还跑得过去，但一旦流量高峰期触发，直接把 CPU 打满，导致整个 ChatGPT 和 API 服务响应变慢。这类事件在 OpenAI 内部叫做 SEV，是 Severity Event 的缩写，即严重事件，这个十二表联查引发了多次高优先级的 SEV。

为什么会出现这种查询？大多数情况下，背后的推手是 ORM 框架。ORM 是 Object-Relational Mapping 的缩写，中文叫对象关系映射，它是一类让开发者用代码对象来操作数据库的工具，比如 Python 里的 SQLAlchemy，Go 里的 GORM，JavaScript 里的 Prisma。ORM 的好处是开发效率高，你不需要手写 SQL，直接在代码里调用方法就行。但坏处是，当你写了一段看起来很无害的代码，ORM 有时候会在背后生成非常低效的 SQL 语句，包括这种拼接了十二张表的怪物查询，而你完全不知道。

OpenAI 的教训是：必须仔细审查 ORM 生成的 SQL，而不是只看代码逻辑。他们现在的原则是尽量避免多表联查，如果真的需要关联多张表，就把这个逻辑从数据库层移到应用层：先分别查出各表的数据，再在代码里拼接。这样的代价是多几次数据库查询，但每次查询都简单、可控，不会有把整个数据库打崩的风险。

他们还特别提到了另一个容易被忽视的问题：长时间空闲的查询。有时候一个数据库事务开始了，应用程序开始一个写入操作，但因为种种原因，应用程序卡住了，这个事务一直悬挂着，既没有提交，也没有回滚，就这么挂着。这种挂起的事务会占住数据库的锁，阻止 autovacuum 清理死元组，影响其他查询。解决方法是配置一个参数叫 idle_in_transaction_session_timeout，也就是"事务内空闲超时"，超过这个时间还没有操作的事务会被自动杀掉，防止僵尸事务堆积。

第三个大问题：连接数耗尽，和 PgBouncer 的救场。

数据库连接这个概念，你可以类比为餐厅的服务员。每个客人坐下来，都需要一个服务员专门负责服务这桌。但餐厅里的服务员数量是有限的。PostgreSQL 在 Azure 上的最大连接上限是五千个。听起来很多，但当你有大量微服务、每个服务启动多个实例、每个实例维护自己的连接池的时候，五千个连接很快就会被耗尽。

更糟糕的是连接风暴。想象一下，你的应用程序突然重启了一大批实例，每个实例启动的时候都要去建立数据库连接，大量连接请求同时涌来，数据库根本来不及处理，直接被打崩。OpenAI 历史上有过真实的因连接风暴导致服务中断的案例。

解决方案是 PgBouncer，一个专门为 PostgreSQL 设计的连接池代理工具。PgBouncer 的原理是在你的应用程序和数据库之间加了一层。应用程序不再直接连接数据库，而是连接到 PgBouncer。PgBouncer 维护一个真正到数据库的连接池，把大量应用程序的连接请求在这个池子里进行复用。

你可以把 PgBouncer 想象成一个超级高效的餐厅前台。原本每个客人进来都需要一个专属服务员陪着，从头到尾跟进，现在前台把客人组织起来，几个客人共用一个服务员，服务员服务完这桌立刻去服务下一桌。客人感觉自己有专属服务，但实际上服务员的数量大大减少了，整体效率反而更高。

PgBouncer 运行在语句级别或者事务级别的连接池模式下，允许大量客户端连接复用少量的真实数据库连接。实测效果非常明显：平均连接建立时间从五十毫秒降低到了五毫秒，整整快了十倍。对于高吞吐量的服务来说，这个提升是非常显著的。

还有一个细节值得关注：他们把 PgBouncer、应用程序客户端和数据库副本都尽可能部署在同一个地理区域。数据库连接不仅有数量限制，还有时间成本，连接挂着不用的时候也在消耗资源。跨地区的连接延迟更高，所以让三者在同一个网络区域内可以显著降低这些开销。同时，PgBouncer 的空闲超时等参数也需要仔细调优，否则积累过多的空闲连接同样会造成问题。

第四个大问题：缓存雪崩，和缓存锁机制。

大多数生产系统都会在数据库前面放一层缓存，比如 Redis，用来存储热点数据。原理很简单：如果同样的数据被频繁读取，就把它放在内存里，下次读的时候直接从内存返回，不用再查数据库，速度快、数据库压力小。理想情况下，绝大部分读请求都命中缓存，数据库只需要处理少量的缓存未命中请求。

但有一种可怕的场景叫做缓存雪崩，也叫缓存击穿。假设缓存层因为某种原因挂掉了，或者大量缓存条目同时过期，那么原本应该被缓存拦截的海量读请求就会同时砸向数据库，瞬间把 CPU 打满，整个服务崩溃。这种场景的破坏力极强，因为它的触发往往是突发的，留给你响应的时间非常短。OpenAI 也遇到过类似情况。

他们的解决方案叫缓存锁机制，英文叫 cache locking，有时也叫 cache leasing，缓存租约。具体怎么工作？

假设现在有一千个请求同时要读同一条数据，而这条数据在缓存里已经失效了。没有锁机制的话，这一千个请求会同时去数据库查这条数据，数据库要处理一千次相同的查询，资源白白浪费，这种情况叫做"惊群效应"，或者"雷鸣群兽"，英文叫 thundering herd。

有了缓存锁之后，这一千个请求里只有第一个请求能拿到锁，获准去数据库查询。其他九百九十九个请求在缓存层等待。等第一个请求查到数据、更新了缓存之后，其他请求直接从缓存里读，完全不需要再碰数据库。这种机制把一千次数据库查询变成了一次数据库查询，对系统的保护效果非常显著，在缓存失效风暴来临的时候尤其关键。

这个方案听起来简单，但实现起来有很多细节要处理：锁的超时时间怎么设置？持有锁的请求本身挂了怎么办，锁如何自动释放？如何防止锁本身成为新的竞争瓶颈？OpenAI 在这方面做了完整的工程实现，并且把它作为防御缓存击穿的标准做法。

第五个大问题：WAL 复制压力与级联复制的探索。

PostgreSQL 的主从复制是通过 WAL 来实现的。WAL 是 Write-Ahead Log 的缩写，也就是预写式日志。简单来说，PostgreSQL 在执行任何写操作之前，都会先把这个操作记录到日志里，然后再真正修改数据。这个日志就是 WAL，它不仅是数据库崩溃恢复的基础，也是主从复制的数据来源：主节点持续地把 WAL 日志流发送给所有读副本，读副本不断地重播这些日志，保持与主节点的数据同步。

现在问题来了：OpenAI 有将近五十个读副本，分布在全球多个地理区域，目的是让不同地区的用户都能就近访问，降低延迟。这五十个副本都需要从主节点接收 WAL 数据流。这意味着主节点需要同时向五十个方向发送数据，每增加一个副本，主节点的网络带宽和 CPU 压力就增加一份。虽然现在 Azure 上的大型实例有非常高的网络带宽，目前还能支撑，但这种线性增长是有上限的，不可能无限加副本，迟早会遇到瓶颈。

解决方案是级联复制，英文叫 cascading replication。这个思路非常优雅：不再让所有副本都直接从主节点同步，而是让部分副本先从主节点同步，成为中间副本，然后其他副本再从这些中间副本同步数据，形成一个树状结构。主节点只需要向少数几个中间副本发送 WAL 流，中间副本再分别负责向下游副本分发。主节点的网络压力从一对五十变成了一对几个，大幅减轻。

文章里提到，这个功能是他们和 Azure PostgreSQL 团队合作开发的，在文章发表的时候还在测试阶段，尚未上线生产。他们的目标是借助级联复制，把副本数量安全地扩展到一百个以上。当然，级联复制也引入了新的复杂性，比如中间副本自己挂掉了怎么办，下游副本如何重新接续同步，故障切换的逻辑变得更复杂。这些问题都需要仔细设计，所以他们非常谨慎，要确保功能完全可靠才会推到生产环境。

第六个大问题：高可用架构、工作负载隔离和限流机制。

说到单点故障，这是任何使用单一主节点架构的系统都绕不开的话题。一旦主节点挂掉，写操作全部失败，影响会非常大。OpenAI 的应对策略是多层次的。

首先，主节点运行在高可用模式下，配备了一个热备实例。热备是一个持续保持和主节点同步的副本，一旦主节点出现故障或者需要维护，热备可以迅速被提升为新的主节点，最大限度减少停机时间。文章特别称赞了 Azure PostgreSQL 团队在确保故障切换在高负载下依然安全可靠方面做的大量工作。

其次，他们把读请求尽可能分流到副本。这有一个额外的好处：即使主节点真的挂了，写操作会失败，但读操作依然可以从副本返回结果。这就把一个 SEV-0，也就是最高级别的全面故障，降级为一个局部影响，因为大多数用户的核心体验——查看对话记录、浏览历史消息——依赖的是读操作，读副本可以继续提供服务。

然后是工作负载隔离，文章里把这个问题比喻为嘈杂的邻居，英文叫 noisy neighbor。你可以想象一栋公寓楼，有个邻居半夜开趴体，影响了整栋楼所有人的睡眠。在数据库场景里，某个低优先级的业务突然产生了大量昂贵的查询，把数据库资源占满，导致高优先级的核心业务也跟着变慢。这种情况在功能上线初期尤其容易发生，因为新功能的查询可能没有经过充分优化。

OpenAI 的做法是把请求按优先级分层，高优先级的请求路由到专用实例，低优先级的请求路由到另一组实例。即使低优先级实例被某个业务打崩了，高优先级服务也完全不受影响。他们还把不同产品线的流量隔离到不同的实例，防止一个产品的爆发式增长波及到另一个产品。

限流是防止级联故障的最后一道防线。他们在多个层面实现了限流：应用层、连接池层、代理层和查询层。当某类查询突然变得异常昂贵，或者某个接口的流量突然飙升，限流机制可以快速介入，阻止这些请求把数据库压垮。他们还特别强调要避免过短的重试间隔，因为过于激进的重试会形成重试风暴，让本来已经过载的数据库雪上加霜。他们增强了 ORM 层，支持针对特定查询类型的速率限制，甚至在紧急情况下可以直接屏蔽某个查询类型，快速止血。

说到模式变更——也就是修改数据库表结构——这是另一个需要格外小心的操作。在 PostgreSQL 里，某些 ALTER TABLE 操作，比如修改列的数据类型，会触发全表重写，意味着整张表的数据都要被复制一遍。对于 OpenAI 这种规模的大表来说，一次全表重写可能需要数小时，期间表会被锁住，整个服务都会受影响。他们的管控策略极其保守：只允许轻量级的模式变更，比如增删某些不触发全表重写的列；所有模式变更操作有严格的五秒超时限制，超时就自动回滚；索引的创建和删除必须使用 CONCURRENTLY 关键字，这样可以在不锁表的情况下并发完成；如果回填一列新值，严格限制速率，宁愿花一周时间，也不允许产生写入峰值。

好，现在来看最终的成果数字。OpenAI 实现了什么？每秒数百万次查询，P99 客户端延迟保持在低两位数毫秒级别——P99 的意思是百分之九十九的请求都在这个时间内完成——系统可用性达到了五个九，也就是 99.999%，换算下来每年只允许大约五分钟的停机时间。在过去十二个月里，他们只有一次 SEV-0，也就是最高级别的全面故障。这次故障发生在 ChatGPT 图像生成功能病毒式传播的时候：一周内有超过一亿新用户涌入，写入流量突然飙升超过十倍，这次冲击实在太猛，才触发了唯一的这次最高级故障。

接下来我们聊聊，这篇文章对我们日常工程工作的实际意义，有哪些可以直接带走的东西。

第一条，仔细审查 ORM 生成的 SQL。这是个老生常谈的建议，但 OpenAI 用十二表联查导致的多次严重故障，再次用真实代价证明了这件事的重要性。你用 Django ORM、GORM 还是 Prisma，写的代码可能看起来非常简洁优雅，但背后生成的 SQL 可能是你想不到的复杂怪物。养成习惯，在开发和测试阶段打开 SQL 日志，看看你的代码到底在跑什么查询，特别是那些涉及多个关联关系的操作。一旦发现有多表联查，评估一下能不能拆到应用层处理。这个习惯在项目还小的时候建立，要比等到流量上来之后再救火省心得多。

第二条，认真对待数据库连接管理。如果你的服务有多个实例，你需要一个连接池代理。PgBouncer 是 PostgreSQL 的标准选择，配置相对简单，效果非常显著。不要让每个应用实例都直接建立大量数据库连接，这在规模化之后是灾难的根源。同时，要配置合理的连接超时参数，空闲连接的超时参数尤其关键，防止空闲连接占满连接数上限。

第三条，为你的缓存设计防击穿机制。如果你用 Redis 或者 Memcached 做缓存，考虑引入缓存锁或者互斥机制，防止缓存失效时多个请求同时打向数据库。这个场景在流量大的系统里非常常见，但很多系统在流量起来之前都没有提前处理，等到出事才来修，往往已经对用户造成了影响。

第四条，要有工作负载隔离的意识。不要把所有业务的数据库请求都路由到同一个实例。对于重要的核心业务，考虑给它专用的数据库资源，和其他业务隔离。这在早期看起来是资源浪费，但当某个边缘业务失控的时候，你会非常庆幸自己做了这层隔离。你的用户登录、支付结算这些核心链路不应该和批量数据处理、日志写入共用同一组数据库资源。

第五条，建立严格的数据库变更管控流程。任何模式变更上线之前，都要评估它的代价，确认它不会触发全表锁或者全表重写。建立一个 checklist，比如这个变更会不会加锁、估计执行时间是多长、有没有回滚方案。在生产环境，一次考虑不周的 ALTER TABLE，可能就能让你的服务宕机几个小时，这种事在各大公司的事故复盘里屡见不鲜。

第六条，持续关注你的 autovacuum 健康状态。如果你在用 PostgreSQL，要养成定期检查死元组数量、表膨胀率、autovacuum 运行频率的习惯。这些指标的异常往往是性能问题的前兆，远比等到查询开始明显变慢才去排查要从容得多。很多监控平台有现成的 PostgreSQL 指标面板，接上去，设好告警阈值。

最后，说几句我个人的感想。

我个人认为，这篇文章最有价值的地方，不是那些具体的技术细节，而是它展示了一种工程决策的哲学：在面临扩展性问题的时候，先认真评估现有方案的极限在哪里，在真正触碰到这个极限之前，不要急着引入更大的复杂性。分片是一个强大的工具，但也是一个巨大的复杂性来源。分片意味着你的应用层要处理数据路由、跨分片事务、分片键的设计和演进，这些都是工程上的坑，会让团队的开发速度显著降低。

OpenAI 的选择是：先把单机 PostgreSQL 优化到极致，把写密集型业务迁移到更适合的分片系统，暂时保留 PostgreSQL 的单主架构。这个选择不是因为他们不懂分片，而是因为他们认真评估了收益和代价，得出结论说现在还不需要走这一步，现有架构还有足够的空间。

我个人觉得，这种推迟复杂性的思维方式，对于大多数中小团队来说尤其值得学习。很多工程师在系统刚上线、流量还很小的时候，就迫不及待地要引入分布式架构、分片数据库、消息队列全套。结果花了大量时间在基础设施上，产品功能反而没时间做。OpenAI 的这个案例告诉我们，一个经过精心优化的单主 PostgreSQL，可以支撑到八亿用户规模。你现在有多少用户？你真的需要那么复杂的架构吗？

当然，OpenAI 的情况也有其特殊性。他们和 Azure 是深度合作伙伴，能够获得超大内存、超高网络带宽的实例，甚至可以和 Azure 团队一起联合开发级联复制这样的新特性。这是大多数公司没有的资源和话语权。所以这篇文章的结论要结合你自己的情况来消化，不能直接复制，但背后的工程思路是普遍适用的。
