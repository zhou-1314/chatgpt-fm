## Script

今天我们来聊一篇来自 OpenAI 官网 engineering 频道的文章，标题叫做 Building self-improving tax agents with Codex，中文可以翻译成"用 Codex 打造自我改进的税务 AI 智能体"。这篇文章发表于二〇二六年五月二十七日，距离我们录这期节目大约过去了三个多月。

文章的作者一共四位，来自两个团队。Aravind Srinivasan 和 Samay Shamdasani 来自一家叫做 Thrive Holdings 的公司，另外两位 Arthur Fernandes Araujo 和 John de Wasseige 来自 OpenAI。这不是一篇学术论文，不是一篇功能发布公告，而是一群工程师把过去半年在真实生产环境里踩坑、解决问题的完整经验记录下来，公开分享出来。这种文章我特别喜欢，因为它有具体的数字，有真实的案例，有你能直接拿去用的方法，而不只是停留在方法论层面的口号。

为什么我觉得这篇值得你在通勤路上认真听完？因为它正面回答了一个很多工程师都在头疼的问题：一套 AI agent 系统部署上线之后，在真实生产环境里发现了各种问题，我们怎么系统性地让它变得更好？不是靠工程师坐在那里一条条手动调 prompt，不是靠偶尔做几次 A/B 测试，而是让整个系统形成一个自动运转的飞轮，真正做到越用越好。这个问题太重要了，而这篇文章给出了一个非常具体、有实际数据支撑的答案。

好，我们先从背景说起。

这篇文章的场景是美国的个人所得税申报。如果你没有经历过美国报税，可能对这件事的复杂程度没有直观感受。简单来说，美国的税务体系相当繁琐。各种收入来源有各自对应的表格：W-2 是工资收入，一〇九九是各种非工资收入，K-1 是合伙企业或信托分配的收入。然后还有各种附表：Schedule E 对应租赁房产收入，Schedule C 对应自雇收入，Schedule A 是逐项扣除。每一个类别都有自己的填写规则和计算逻辑，而且很多情况下，同一份信息可能散落在好几个不同的文件里，需要人工去比对、提取、汇总。

Crete 是一家旗下拥有三十多家会计师事务所的公司，他们每个税务季要处理几万份税务申报，背后涉及的源文件更是以百万计。对于中等到高复杂度的申报表，光是数据录入这一步就可能要花八个小时。而且数据来源非常混乱：有客户手写的笔记，有各种格式的电子表格，有去年的旧文件需要参考，有客户发来的各种邮件附件。

你可以想象一下这个场景：一个会计师坐在那里，面对一叠乱七八糟的文件，要把里面的信息一条条找出来，填到正确的表格字段里，还不能填错，因为税务数据直接关系到客户的钱和合规风险。每到税务旺季，这种高强度、高精度的数据处理工作就成了整个事务所最大的效率瓶颈。

OpenAI 和 Thrive Holdings 的工程师团队在这个场景里建了一套叫做 Tax AI 的系统。今年的税务季，这套系统在 Crete 参与试点的事务所里处理了七千份税务申报，主要覆盖一〇四〇和一〇四一这两种最常见的个人所得税表格。

效果怎么样？文章给出了几个数字：系统帮从业者节省了大约三分之一的税务准备时间，申报草稿的准确率可以达到百分之九十七，整体吞吐量提升了大约百分之五十。

但我认为，这些结果数字本身不是这篇文章最精彩的地方。最精彩的地方是：这套系统是怎么从最初的状态，进化到现在这个状态的。

文章里有一个关键指标。他们用"正确字段完成比例"来衡量系统质量，看有多少份申报表能达到百分之七十五、百分之九十、或者百分之百的字段正确率。这三个门槛对应的是不同程度的从业者后续跟进工作量：达到百分之七十五的申报表还需要会计师做大量手工修正，达到百分之百的申报表基本不需要额外处理。

刚上线时，只有大约四分之一的申报表能达到百分之七十五这个基准线。也就是说，大多数表格还需要会计师花很多时间去修正，系统的价值相当有限。但六周之后，这个比例从百分之二十五跳升到了百分之八十六。在百分之九十和百分之百这两个更高的门槛上，进步速度甚至还要更快。

六周，准确率发生了这样幅度的跃升，背后是一套精心设计的自我改进机制在运转。

这套机制建立在三大支柱上。

第一个支柱，是保持和从业者的紧密连接。

这听起来可能有点像废话，但实际上它是整个系统有效运转的前提条件，而且执行起来需要刻意设计。Tax AI 不是一个离线批处理系统，它被深度嵌入到会计师们的日常工作流程里。会计师上传客户的源文件和备注，系统生成一份税务草稿，然后会计师审核、修改、最终提交归档。

这里的关键洞察是：会计师的每一次修改，本身就携带了有价值的信号。但是这个信号的解读并不简单。一个字段被修改，可能有五种不同的原因。第一，系统从源文件里提取数据时就提取错了，原始信息识别有误。第二，提取是对的，但把这个值映射到税务引擎对应字段的逻辑出了问题。第三，系统根本还不支持这种特定情况，这是一个功能缺口而不是 bug。第四，会计师有自己的操作偏好，这个修改反映的是专业判断而不是系统错误。第五，这个值在税务引擎里之前已经有了去年的旧记录，会计师只是在更新数据，不代表系统本次有问题。

这五种情况，对应五种完全不同的改进方向。如果你不区分它们，你的改进信号就是噪声，你不知道应该往哪个方向迭代，甚至可能越改越错。

所以第一个支柱的核心工作，是让有经验的从业者深度参与进来，帮助团队识别哪些修正是真正的系统问题，哪些只是正常的工作流变化，哪些场景是优先级最高的改进目标。这不是一次性的需求调研，而是一个持续运转的协作机制，从业者的直觉和领域判断是整个改进循环的导航仪。

第二个支柱，是让生产环境自动积累结构化的证据，也就是构建完整的 production trace，我把它翻译成"生产轨迹"。

这个概念非常重要，我想多花一点时间来解释它和普通系统日志的区别。

普通的应用日志通常记录的是：某个请求在某个时刻到达，系统做了某个操作，返回了某个结果。如果出错了，记录一个错误码。这些信息对于排查系统故障很有用，但对于改进 AI agent 的行为质量，往往远远不够，因为它只有两个端点——输入和输出，中间的过程是黑箱。

production trace 记录的是整个处理过程的完整来龙去脉。对于 Tax AI 来说，这意味着要捕获以下这条链路上的每一个环节：源文件是什么，文件是怎么被组织、拆分和分类的，每一个字段的值是从哪个文件的哪个具体位置提取出来的，提取时引用的是哪个证据，这个值是怎么被映射到税务引擎对应字段的，映射时用了什么规则，然后会计师审核之后改了什么，最终归档的是什么值。

我喜欢用一个手术录像的比喻来解释这个区别。普通日志就像记录"手术成功"或者"手术失败"这个最终结果。production trace 则是把整个手术过程完整录下来：每一个切口在哪里开的，用的什么器械，每一个步骤的操作逻辑是什么，助手递了什么给主刀医生。有了这个录像，当病人手术后出现了并发症，你可以精确地回溯，定位是第几分钟的哪个操作环节出了差错，而不是只能靠猜测。

对于 Tax AI，这种完整的轨迹记录让团队可以做到一件关键的事：当会计师修正了一个字段，系统可以追溯，这个差异究竟是在哪个环节产生的。是文档分类时就分错了？是字段提取时漏掉了？是映射规则写错了？还是提取和映射都对，只是会计师有不同的专业判断？有了完整的 trace，这些问题才能得到精确的诊断，整个系统的改进才能做到有的放矢。

第三个支柱，是 Codex 驱动的改进循环。

这是整个系统最核心、技术含量最高的部分。我们用文章重点描述的租赁房产案例来具体说明这个循环是怎么运转的。

在美国个税申报里，租赁房产收入要填在 Schedule E 这张附表上。对于会计师来说，处理这类数据的难度在于源文件非常混乱：可能是客户手写的记账本，可能是 Excel 表格，可能是物业管理公司发来的各种格式的文件。而且往往一个客户同时有好几处租赁房产，信息分散在不同的文件里，需要正确地对应和整合。

其中有一个字段叫做 fair rental days，中文叫做"公平出租天数"，也就是房子在这一年里实际出租给租客的天数。这个字段很重要，因为它直接影响到允许扣除的费用计算。但 Tax AI 在上线初期经常漏掉这个字段——系统要么完全没有填这个值，要么填的值和会计师后来确认的值不一样。

这个问题是怎么被发现的？不是有一个工程师坐在那里盯着输出逐条检查，而是整个 eval 管道自动把它浮现出来的。

eval 管道做了三件事。第一步，把 Tax AI 的输出和最终归档的税务申报做字段级别的比对，生成差异记录：系统预测的是什么值，会计师最终填的是什么值，这个差异看起来是不是真正的系统问题。第二步，把相似的差异记录分组，把重复出现的模式和偶发的噪声分开。比如说，如果几十份申报表都出现了 fair rental days 字段缺失的情况，这就不是偶然，而是一个系统性的问题。第三步，经过人工审核确认之后，把这个发现变成一个有明确成功条件的 eval 目标。

这个 eval 目标，就是接下来 Codex 任务的输入。

Codex 拿到这个任务的时候，它面对的不是一个模糊的描述，不是一句"fair rental days 字段有时候会有问题，你去看看"。它拿到的是一个完整的、结构化的任务包：包含了代表性的源文件样本，对应这些样本的完整 production trace，预期的正确输出，可以直接在仓库里运行的 eval 命令，以及相关的代码仓库上下文。

有了这些上下文，Codex 做的事情就像一个有经验的工程师在处理一个信息完整的 bug 报告。它会系统性地检查整个处理管道：源文件选择逻辑有没有正确地识别和选中包含租赁信息的文件；提取 schema 里有没有定义 fair rental days 这个字段；映射器的代码里有没有处理这个字段的逻辑；沿着代码路径一步步往下追，找出究竟是在哪个环节出了问题。

它还要判断，这是一个不支持的字段，还是提取模式写错了，还是源文件选错了，还是映射器有 bug，又或者是 eval 的评分标准本身把正常的工作流变化误判成了系统错误。

根据找到的根本原因，Codex 实施对应的修复：可能是扩展提取 schema，在里面加入 fair rental days 字段的定义；可能是改善源文件选择逻辑，让系统更准确地找到包含租赁天数信息的原始文件；可能是更新税务引擎映射器的逻辑；也可能是修正 eval 的评分标准，避免正常的工作流差异被误计为错误。

修复完成之后，Codex 重新跑针对这个具体问题的专项 eval，然后跑更广泛的回归测试套件，确保这次修改没有引入新的问题，最后把候选的 pull request 提交给工程师审核。工程师确认没问题，合并进主分支，下一个版本的 Tax AI 就解决了这个问题。会计师下次处理类似的租赁房产申报时，不需要再手动填这个字段了。

这里有一个细节我特别想单独说一下，因为它是这个系统能够安全运转的关键：不是所有的从业者修正都会自动触发 Codex 任务。文章里明确写道，一个从业者修正必须经过 eval 管道的捕获、相似差异的分组聚合、人工确认是真实的系统性问题，并且被归类成一个有明确边界和成功条件的工程任务之后，才会被送给 Codex 处理。

这个过滤机制非常关键。如果你把所有的用户修正都丢给 Codex 去自动处理，它会疲于应付各种背景各异、很多并不需要修的"问题"，改进效果会非常差，甚至可能把系统改坏。但是经过 eval 管道的结构化处理之后，Codex 拿到的每一个任务，都是边界清晰、有充分证据、有明确验收标准的工程问题。在这种条件下，Codex 才能真正发挥出快速迭代的价值。

文章还专门说明了这套自动化的适用范围，我觉得这一点非常重要：这套 Codex 驱动的改进循环只作用于产品的一个特定层——负责从源文件提取数据并映射到税务工作流的那一层。工程师仍然负责整体架构设计、产品方向决策和版本发布管理。从业者仍然负责审核最终的申报内容和签批归档。Codex 负责的是中间那一层繁重的、重复性的工程迭代工作。

这种分层设计，我个人认为是整个系统里最有智慧的设计决策之一。你可以把它理解成一种"自动化的边界意识"：不是把所有的工作都交给 AI，而是精确识别出哪一层工作是重复性的、可以被安全自动化的，然后在那一层建立自动化，同时在关键节点上保留人的判断和监督。如果你的边界划得太宽，AI 开始接管不该接管的决策，风险就来了。如果你的边界划得太窄，规模效益就出不来。

我们来看一下这套系统实际产生的结果。文章提到，租赁房产这个场景，从开始攻关到在专项 eval 上达到百分之九十的精确率和召回率，花了大约六周时间，而且期间需要相当密集的工程监督投入。

但这六周的工作积累出了一套可以复用的基础：提取 schema 的设计范式、标准化的 eval 规范和测试用例库、通用的 trace 分析方法、以及处理这类复杂场景的实现模板。正是因为有了这些积累，后续支持同样复杂的 Schedule C——自雇收入表——和 Schedule A——逐项扣除表，所花的工程成本就显著降低了。

每攻克一个复杂场景，都在降低攻克下一个复杂场景的边际成本。这是一种技术上的正向复利效应，也是文章标题里"自我改进"这四个字真正的含义——不只是单个场景的准确率在提升，整个系统攻坚新场景的能力也在持续提升。

文章在结尾分享了一个让我印象很深的案例。有一位资深会计师，去年这个时候花了一百八十小时在税务准备工作上，今年只花了十五小时。省出来的时间，她分成了两部分来用：一部分用来给每一位客户打电话，亲自讲解他们的申报情况，提供以前根本没有时间去做的高接触度客户服务；另一部分用来开发新客户，拓展新的业务线。

这个例子说明了 AI 在专业服务领域落地的一个规律：它最好的用法不是简单地用 AI 替代人，而是通过接管繁重的数据处理工作，把专业人员从重复性的机械劳动里解放出来，让他们有更多的时间和精力去做真正需要专业判断、人际关系和客户信任的工作。这位会计师不是被 AI 取代了，她是被 AI 升级了。

好，现在我们来聊聊这篇文章对你在实际工作里意味着什么，有哪些东西可以直接拿去用，又有哪些坑需要提前避开。

第一点，从系统设计的第一天起就规划完整的 trace，而不是等出了问题再补。不管你在做什么 AI agent 系统，设计阶段就要问自己这个问题：如果这个 agent 在某份真实数据上表现不好，我能不能在不到一小时内定位出是哪个处理环节出了问题？如果你的系统只有输入和最终输出，中间是个黑箱，那你后期的改进只能靠人工盯着输出逐条猜。从第一天开始就设计结构化的 trace，记录每个中间步骤的输入、输出和来源依据，这个前期投入在系统进入生产环境之后会有非常高的回报。

第二点，把 eval 设计当成产品开发的一部分，而不是事后补的质量检查。文章里反复强调，Codex 的任务必须有明确的成功条件，也就是必须有可以自动运行的 eval 来验证一个修改是否真正解决了问题。如果你在产品上线之前就建立了清晰的质量指标和对应的 eval 套件，那么当生产环境里出现问题时，你就能很快把它转化成一个可以分配给 coding agent 的结构化任务。如果等上线之后才想"我该怎么衡量质量"，改进循环就根本转不起来。

第三点，把用户或从业者的纠错行为设计成结构化的信号，而不是只知道"这个值被改了"。关键在于上下文：纠错发生在处理流程的哪个节点，修正前的值是什么，修正后的值是什么，这个修正是在系统刚输出时发生的还是在工作流的后期发生的，类似的修正在多少份数据上出现过。有了这些上下文，你才能区分真正的系统错误和正常的工作流变化，你的改进信号才是有价值的数据而不是噪声。这里的投入，本质上是在给你的改进循环建立高质量的原材料供应链。

第四点，给 coding agent 的任务质量决定了它产出的质量。这是我个人在使用各种 coding agent 时体会最深的一点。文章里描述的 Codex 任务，不是"帮我修 fair rental days 字段的 bug"这样模糊的一句话，而是包含了代表性的源文件样本、完整的 production trace、预期的正确输出、可以直接运行的 eval 命令，以及相关的代码仓库上下文。这些要素合在一起，才能让 coding agent 有足够的信息去做有效的诊断和修复。垃圾输入，垃圾输出，这个道理在 Codex 这样的 coding agent 上同样适用，而且效果非常显著。你在组织任务上下文上多投入一个小时，可能抵得上 coding agent 多跑几十次迭代。

第五点，在改进循环的入口和出口都要保留人工判断的节点。注意，这不是在说 AI 不可靠所以要人把关这种保守思路，而是在说改进循环的结构设计问题。在 Tax AI 里，人工判断主要出现在两个地方：一是在 eval 管道识别出问题之后，由工程师和从业者确认这是真正需要修的系统问题，过滤掉工作流噪声；二是 Codex 完成修复并提交 pull request 之后，由工程师做最终的代码审核。这两个节点，一个在循环入口确保改进方向正确，一个在循环出口确保改进内容安全。有了这两道关，自动化才能在一个有边界的范围内安全地大规模运行，而不会把系统改跑偏。

最后，好，我们来收个尾。

这篇文章的核心论点是：在依赖专业判断的垂直领域里，你可以系统性地构建一套让 AI agent 在生产环境中越用越好的自我改进机制。但这需要三件事同时设计到位：和领域从业者的紧密持续协作，能够捕捉完整处理过程的 production trace 基础设施，以及由 eval 驱动的 Codex 改进循环。这三件事缺一不可，而且不能等系统上线之后再临时补，必须在产品设计阶段就一并考虑进去。

我个人认为，这篇文章最有价值的地方，不是"AI 可以做税务准备"这个结论——这个结论今天来看已经不令人惊讶了。真正有价值的是它展示了一套可以复制的工程方法论：如何在一个需要专业判断、不允许频繁出错的垂直领域里，把 AI 产品从"能用"做到"越用越好"。这套方法论里关于 trace 设计、eval 规范、有界自动化和人工节点设置的思路，在法律、医疗、金融审计，乃至任何一个对准确性有高要求的专业服务领域，都有直接的参考价值。如果你正在做类似的 AI 产品，强烈建议你把这篇原文完整读一遍。
