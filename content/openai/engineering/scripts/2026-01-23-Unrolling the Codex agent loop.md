首先来了解一下 Codex 是什么。Codex 在 OpenAI 的产品体系里是一套产品家族的名字，涵盖了 Codex CLI、Codex Cloud 和 Codex 的 VS Code 插件。我们今天聊的核心是 Codex CLI，也就是运行在你本地电脑上的跨平台软件 agent。你可以把它理解为一个真正能干活的 AI 程序员：你说"帮我写一个单元测试"，它不只是给你一段代码文字，它会真的在你电脑上创建文件、写入代码、执行测试命令、查看报错信息，然后继续修改，直到测试通过为止。这和你在聊天窗口里问 ChatGPT 要代码是完全不同的两件事。普通的聊天 AI 只是给你文字，而 agent 是直接操作你的本地环境。

好，现在我们来讲第一个核心概念：agent loop 到底是什么，它的基本工作方式是怎样的。

你可以把 agent loop 想象成一个不断旋转的齿轮。每次旋转，它做以下几件事：第一，接收用户的输入，也就是你说的那句话或者你提的那个问题；第二，把这个输入组装成一个 prompt，也就是发给语言模型的完整指令文本；第三，把 prompt 发给语言模型做推理，这个过程叫做 inference，推理或者采样；第四，语言模型输出结果，这个结果要么是一条直接回复给用户的最终答案，要么是一个工具调用请求；第五，如果是工具调用请求，agent 就去执行这个工具，比如运行一个命令行命令，然后把结果记下来，附加到 prompt 里面，再返回第三步重新推理；第六，一直重复这个过程，直到语言模型输出一条最终的用户消息，表示任务完成。

文章把用户发一条消息到 agent 给出最终回复的完整过程，称为一个 turn，即一轮对话。一个 turn 里面，可能包含几次、几十次甚至上百次推理加工具调用的来回循环。

举个具体的例子。假设你告诉 Codex："帮我找出项目里所有导入了 os 模块的 Python 文件。" agent 收到这个请求后，可能会先调用 shell 工具执行 grep 命令搜索文件，然后把结果发给模型看，模型可能觉得还需要再深入查一下某个文件，又发起一次工具调用，再看结果，最终整理出一个完整的文件列表，生成一条最终消息告诉你结果。整个过程中，用户只说了一句话，但 agent 和模型之间可能来回交互了四五次。

有一个细节文章特别强调，我觉得很值得记住：agent 的"输出"并不仅仅是最后那条文字消息。更多时候，agent 的主要输出是它在你机器上实际做的事情，写的代码、改的文件、跑的脚本。最后那条"我已经完成了你要求的修改"这样的消息，只是一个信号，告诉你 agent 这轮工作结束了，控制权交回给你了。这个观念的转变对于理解 agent 的本质很重要，特别是对于习惯了聊天式 AI 的用户来说。

还有一个非常关键的机制：每次发送新消息时，必须把整个历史对话都附在 prompt 里面一起发给模型。这是因为语言模型本身是没有记忆的，它看到的只有当前这次发给它的 prompt 里的内容。如果不把历史带上，模型就完全不知道之前发生了什么。这个设计导致了一个显而易见的问题：对话越长，prompt 越大。每个模型都有一个上下文窗口，context window，这是模型单次能处理的最大 token 数量，token 是文本的最小处理单位，大概每个中文字对应一到两个 token。一旦 prompt 的 token 数量超过上下文窗口的上限，模型就没法继续工作了。这个问题叫做上下文窗口管理，是 agent 工程里最重要的挑战之一，我们后面会详细讲。

现在来讲第二个核心点：Codex 是如何构建发给模型的 prompt 的。

Codex CLI 使用的是 OpenAI 的 Responses API 来调用模型。Responses API 是 OpenAI 专门为 agent 场景设计的一个接口，你可以把它理解成比普通的聊天接口更强大的版本，支持工具调用、流式输出、多轮对话等功能。

值得一提的是，Codex CLI 的 API endpoint 是完全可以配置的。你可以接 OpenAI 官方接口，可以用 ChatGPT 账号登录，可以走 Azure 云，甚至可以让 Codex 跑在完全本地的环境里，比如接 ollama 零点一三点四或者 LM Studio 零点三点三九以上的版本，这样整个 agent 从头到尾都在你自己的机器上跑，数据完全不出门。对于很多有数据安全要求的企业客户，这个选项非常有吸引力。

那么 Codex 发给 Responses API 的请求里，主要包含哪些内容呢？文章聚焦在三个最重要的字段：instructions、tools 和 input。

先说 instructions，也就是指令字段。这是告诉模型它的角色和行为准则的系统级指令。Codex 会先从用户的配置文件里读取，如果用户指定了自定义指令，就用那个；如果没有，就用 Codex 仓库里内置的、专门为当前模型优化过的基础指令。文章里提到，针对不同的模型版本，Codex 仓库里有不同的提示词文件，比如针对 GPT 五点二 Codex 版本就有一套专属的提示词文件。这说明模型和 agent 的配合不是万能的，针对不同模型的特性，指令需要专门调优。

再说 tools，工具列表字段。这是告诉模型有哪些工具可以调用的。Codex 提供的工具来自三个来源：第一类是 Codex CLI 自带的工具，最核心的是 shell 工具，让模型可以执行命令行命令，这是 Codex 能在你电脑上真正干活的根本；第二类是 Responses API 本身提供的一些工具；第三类是用户通过 MCP 服务器提供的自定义工具。MCP 是 Model Context Protocol 的缩写，模型上下文协议，是一套让外部工具和 AI 模型交互的标准接口，你可以把它理解成给 AI 装插件，比如你可以通过 MCP 把你的数据库、你的内部 API、你的文件系统暴露给 agent 使用。

最后说最复杂的 input 字段。这是一个有序的消息列表，文章详细列出了 Codex 在用户消息之前会向这个列表里注入的四类内容。

第一类是一条 role 等于 developer 的消息，内容是沙盒规则，也就是描述 Codex 的 shell 工具应该在什么范围内工作、有什么权限边界。这里有一个非常重要的安全说明：这个沙盒规则只适用于 Codex 自带的 shell 工具，如果用户接入了 MCP 服务器提供的第三方工具，那些工具的安全边界是 MCP 服务器自己负责管控的，Codex 不会也没有能力去约束它们。这个边界一定要清楚。

第二类是可选的 developer 消息，来自用户的 config.toml 配置文件里的 developer_instructions 字段。这是给开发者级别的全局自定义指令留的口子，让你可以把自己的偏好和约束注入进去。

第三类也是可选的，是一个 user 消息，包含聚合自多个来源的用户指令。这个设计比较精妙：它不是来自单一文件，而是从多个位置读取然后合并的，包括用户 Codex 主目录里的 AGENTS.md 和 AGENTS.override.md 文件，以及从项目的 Git 根目录一路往下找到当前工作目录，每个文件夹里的 AGENTS.md 等项目文档文件，还有用户配置的技能 skills 的元数据。这些内容按照越具体的排越靠后的原则排列。这个设计的逻辑是：语言模型在处理 prompt 时，更靠后的内容通常有更大的影响力，所以把更具体的、更针对当前项目的指令放在后面，让它们在权重竞争中胜出。

第四类是必选的环境上下文消息，告诉 agent 当前的工作目录是哪里、用的是什么 shell。这是因为 agent 需要知道它在什么环境里工作，才能生成正确的命令。

在这四类内容之后，才是用户实际发出的那条消息。所以你可以想象，即使用户只是说了一句话，Codex 在发给模型之前，已经准备了大量的上下文背景。这些背景是 agent 能够正确、安全、高效工作的基础。

另外值得一提的是 role 字段的设计。每条消息都有一个角色，可以是 system、developer、user 或者 assistant，优先级依次递减。这个分层设计有一个重要的作用：让更高优先级的约束更难被低优先级的内容覆盖。比如系统级别的安全规则，用 system 或者 developer 角色设置，用户的输入是 user 角色，即使用户试图通过自己的消息来绕过安全规则，优先级机制也会让模型更倾向于遵守高优先级的约束。这在 agent 的安全设计里是很重要的一道防线。

值得注意的是，服务器端，也就是 OpenAI 的 Responses API 服务器，会把 instructions 和 tools 以及服务器自己生成的 system 消息排在 input 内容的前面。这个顺序是服务器决定的，客户端无法控制，这是一个值得在自己构建系统时记住的架构细节。

好，现在来讲第三个核心点：当 Codex 把请求发出去之后，服务器是怎么响应的，agent 又是如何处理这个响应的。

Codex CLI 向 Responses API 发出请求之后，服务器不是等所有内容生成完了再一次性返回，而是用 SSE，也就是 Server-Sent Events，服务器发送事件，这种方式把响应实时地流式推送过来。SSE 是一种 HTTP 协议机制，可以让服务器持续地向客户端推送数据，不需要客户端反复去问"好了吗好了吗"。你在用 ChatGPT 时看到文字一个一个出来的打字效果，背后就是这个机制在起作用。

每一个 SSE 事件都是一小块 JSON 数据，类型名字以 response 开头，比如 response.output_text.delta 这样的事件，是用来驱动 UI 流式展示的。Codex 消费这些事件流，做两件事：第一，实时更新界面，让用户看到模型在打字；第二，把这些事件转换成内部对象，作为下一次发请求时 input 字段里的新增内容。

文章给了一个具体例子来说明这个过程。假设第一次推理的结果包含两个输出项：一个类型为 reasoning 的推理过程，还有一个类型为 function_call 的工具调用请求。那么当 Codex 要发第二次请求时，这两个输出项必须被完整地包含在 input 字段里。这样，新的 prompt 就是旧的 prompt 加上这两条新内容，新的 prompt 是旧的 prompt 的精确前缀扩展。

"精确前缀扩展"这五个字非常关键，文章里特意强调这是有意为之的设计，目的是为了利用 prompt 缓存来提升性能。这就引出了第四个核心点，也是这篇文章技术含量最高、对工程师最有参考价值的部分。

我们来聊聊性能问题，以及 prompt caching 是怎么解决这个问题的。

有一个很直观的计算：如果每次向 Responses API 发请求都带上完整的历史对话，而对话历史在不断增长，那么随着对话进行，你总共发出去的 JSON 数据量，会是对话轮次的平方级别增长。第一轮发了一点，第二轮发了两点，第三轮发了三点，加起来就是一加二加三……就像高斯求和问题一样，最终是平方量级的。文章里非常坦率地承认了这一点，说 agent loop 在发送的 JSON 数据量上确实是平方的。

那为什么不用 previous_response_id 这个参数来优化呢？Responses API 是支持这个参数的，你只需要告诉服务器"上一次响应的 ID 是什么"，服务器自己去找历史记录，你不需要把全部历史都发过来，网络传输量就从平方降到了线性。

Codex 团队给出了两个放弃这个参数的理由，都很有说服力。

第一个理由是保持无状态。用了 previous_response_id，服务器就必须存储每次响应的结果，才能在下次请求时找到它。不用的话，每次请求就完全独立，服务器不需要存任何东西。这大大简化了服务器端的实现。对于一个需要服务数以百万计用户的系统，无状态的设计往往意味着更好的可扩展性、更低的运维复杂度，以及更强的容错能力。

第二个理由涉及企业合规，这个更有意思：为了支持 ZDR 客户。ZDR 是 Zero Data Retention，零数据留存，是 OpenAI 向企业客户提供的一种隐私保护选项。选择了 ZDR 的客户，OpenAI 保证不会持久化存储他们通过 API 发送的任何数据。如果使用 previous_response_id，服务器就必须持久化存储历史响应，这和 ZDR 的承诺直接冲突。所以为了让 ZDR 客户也能无缝使用 Codex，Codex 选择不用 previous_response_id，保持每次请求完整自包含。文章还补充了一个细节：ZDR 客户的 encrypted_content，也就是加密的推理内容，可以在服务器端解密，因为 OpenAI 保存的是解密密钥，而不是数据本身，这个区分在法律上和技术上都很精妙。

好，确定了发送数据量是平方的，那推理成本也是平方的吗？token 的处理才是真正昂贵的地方。这里 prompt caching 就登场了。

Prompt caching，提示词缓存，是语言模型推理的一种优化机制。当你发给模型的 prompt 和之前某次请求的 prompt 有相同的前缀时，服务器可以直接复用上次计算这段前缀的中间结果，不需要重新计算。换句话说，只有 prompt 里新增的那部分才需要真正计算，已有的前缀部分是近乎零成本的。这样，虽然发送的 JSON 数据量是平方的，实际消耗的计算量却是接近线性的，因为每次只有新增的内容是真的新算了。

这个优化的前提是什么？精确的前缀匹配。正是因为 Codex 在构建每次请求的 input 时，采用了"始终是前缀扩展、绝不修改已有内容"的原则，才能稳定地利用这个缓存机制。如果你每次都去修改历史里某条消息，哪怕只改了一个字，整个前缀就不匹配了，缓存全部失效，每次都要重新计算全部 token，成本立刻飙升。

文章里引用了 OpenAI 自己的文档里关于 prompt caching 的最佳实践，原话大意是：把静态的内容放在 prompt 的前面，把动态的、会随请求变化的内容放在后面。这和 Codex 构建 prompt 的方式完全一致：系统指令、工具列表、用户指令这些不变的东西在前面，每轮对话的消息和工具调用结果在后面。

那什么情况下会导致缓存失效，产生 cache miss 呢？文章列举了几类情况：在对话中途改变可用的工具列表；切换目标模型，比如中途从一个模型换到另一个；改变沙盒配置、审批模式或者当前工作目录，因为这些变化会改变 prompt 里靠前的那些内容，破坏前缀的不变性。

文章里还专门提到了一个真实踩过的 bug，我觉得这段是全篇最有教育意义的部分之一。当 Codex 加入 MCP 工具支持的时候，团队发现 prompt 缓存会莫名其妙地失效。功能完全正常，就是缓存不命中，成本悄悄变高了。排查了一番，发现是因为在构建工具列表的时候，MCP 工具的排列顺序不稳定，有时候 A 工具排在前面，有时候 B 工具排在前面，导致每次发给模型的工具列表顺序都不一样，前缀自然就不匹配了，缓存全部失效。修复方案也很简单：保证工具列表每次都按照固定的顺序排列。

这个 bug 告诉我们，在 prompt caching 敏感的 agent 系统里，任何看似无关紧要的顺序问题都可能导致隐性的性能退化。更让人担心的是，这种问题很难发现，因为功能上完全正常，只是账单悄悄变大了，你还以为是模型变慢了。MCP 服务器特别容易踩这个坑，因为 MCP 服务器甚至可以在运行中通过 notifications/tools/list_changed 这样的通知来动态改变它提供的工具列表，Codex 必须对这些变化保持警惕。

针对对话过程中发生的配置变化，Codex 团队也采取了一个很聪明的策略：不去修改 input 列表里已有的消息，而是在列表末尾追加一条新消息来反映这个变化。比如审批模式变了，就在末尾追加一条新的 developer 消息，格式和之前那条一模一样但内容更新；工作目录变了，就追加一条新的 user 消息描述新的环境。这样 prompt 的前缀保持完全不变，缓存依然有效，新变化的影响只体现在末尾新增的部分上。这个细节充分展示了 Codex 团队在 prompt 工程层面的精细化程度。

我们现在来讲第五个核心点：上下文窗口管理，也就是当对话越来越长快撑满的时候，Codex 怎么应对。

任何一个正常使用的 agent 会话，只要任务足够复杂，迟早会遇到上下文窗口快满的问题。Codex 的解决方案叫做 compaction，压缩，也可以叫会话压缩。

早期的实现方式比较原始，需要用户手动输入 /compact 命令，Codex 收到后，把当前的完整对话连同一段要求总结的指令一起发给模型，让模型生成一段摘要文字，然后用这段摘要替换掉之前所有的历史对话，从一个更轻量的起点继续。这个方案能用，但有明显的缺陷：首先，需要用户自己判断什么时候该压缩，这要求用户对 token 消耗有足够的感知；其次，基于文字摘要的压缩不可避免地会丢失信息，因为模型的推理过程、工具调用的细节很难完整地用文字摘要还原。

后来，Responses API 进化出了一个专门的接口 /responses/compact，提供了更高质量的压缩方案。这个接口不是简单地让模型写一段总结文字，而是返回一个特殊的压缩结果，其中包含一个 type 为 compaction 的项目，里面有一个加密的内容字段，叫做 encrypted_content。

这个加密内容保存的不是人类可读的文字摘要，而是模型对原始对话的内在理解的某种紧凑表示。当 agent 用这个压缩结果继续对话时，模型通过解密这个内容来恢复对之前对话的理解，精度远超文字摘要。文章里没有详细描述这个加密内容内部的结构，但从功能描述来看，它更像是把模型对这段对话的深层理解做了一个快照保存下来，而不是把对话翻译成另一段文字。

我个人认为，这个设计的思路非常聪明，它把压缩的工作从"让另一个模型把内容复述一遍"变成了"让模型自己保存自己的理解状态"，信息损失要少得多。就好比你让一个同事在晚上下班之前，不是让他把今天所有的工作内容写一遍给你看，而是让他把他脑子里对这个项目的完整理解打包存起来，明天直接恢复，效率和准确性自然都更高。

现在，Codex 会在对话的 token 数超过一个可配置的阈值 auto_compact_limit 时，自动触发这个压缩接口，用户完全不需要手动干预。这个自动化让 agent 的使用体验大大提升，用户不需要关心底层的 token 管理，只管和 agent 对话就好。

关于 ZDR 客户，这个机制同样适用。OpenAI 只保存解密密钥，不保存实际数据，所以在服务器端对 encrypted_content 进行解密和重新处理，整个过程不违反零数据留存的承诺。在合规和功能之间，这个设计找到了一个非常优雅的平衡点。

好，五个核心点都讲完了。现在来聊聊这篇文章对你实际工作的意义，如果你在构建自己的 AI agent 或者基于语言模型的应用，有哪些经验可以直接拿来用。

第一点，prompt 结构设计要遵循"静前动后"的原则。把系统指令、工具定义、少量示例这些不变的内容放在 prompt 最前面；把每轮对话的历史消息、工具调用结果这些动态内容放在后面。这样做的直接收益是最大化 prompt 缓存的命中率，把推理成本从平方级别压低到接近线性级别。对于调用量较大的生产级应用，这个优化的效果是非常显著的，可以节省大量的 API 费用。如果你平时用的某个 API 账单突然变贵了，不妨先检查一下自己的 prompt 结构，看看有没有把静态内容放在了后面。

第二点，要特别注意工具列表的枚举顺序。如果你的 agent 支持动态的工具列表，比如接入了第三方插件或者 MCP 服务器，一定要保证每次生成工具列表时的顺序是稳定可复现的。可以简单地对工具名做字母排序，或者维护一个固定的顺序配置。这个问题很容易被忽视，但它对 prompt 缓存的影响是致命的，而且很难通过功能测试发现，只会在账单上默默体现出来。Codex 团队踩过这个坑，给我们省了踩的时间。

第三点，配置变更要用追加而不是修改。如果 agent 在运行中需要更新配置，比如切换权限、改变工作目录、更新用户指令，不要去修改历史消息列表里已有的内容，而是在列表末尾追加一条新消息来反映变化。这样可以保持 prompt 前缀的稳定性，维护缓存效果。每一次不必要的前缀修改，都是一次完整的缓存失效，成本蹭蹭往上涨。

第四点，提前设计上下文管理策略。很多开发者在做 agent 的时候，把注意力全放在功能实现上，等到真实用户使用之后发现上下文满了报错，才开始想怎么处理。正确的做法是在设计阶段就规划好：什么时候触发压缩、用什么方式压缩、压缩后如何恢复上下文的连贯性。如果你用的是 OpenAI 的接口，/responses/compact 是现成的好工具；如果用的是其他提供商，要自己实现相应的压缩逻辑，可以是基于文字摘要的，也可以是滑动窗口保留最近 N 轮，总之要有预案，不能等问题暴露了再临时补救。

第五点，理解角色权重，用好分层设计。系统指令、核心约束、安全规则这些放在高优先级角色下，用户可自定义的内容放在低优先级角色下。这不仅是提升 agent 能力的方法，也是防止 prompt 注入攻击的重要手段。当用户试图通过输入内容来干扰或者绕过 agent 的安全规则时，分层的优先级机制可以提供一定程度的保护。很多 agent 的安全漏洞，本质上就是因为没有做好这个层级隔离。

第六点，清楚 MCP 工具的安全边界。如果你给 agent 接入了 MCP 服务器提供的第三方工具，要明白 Codex 的沙盒只保护 Codex 自带的 shell 工具，MCP 工具的安全管控由 MCP 服务器自己负责。在集成第三方 MCP 服务器之前，要仔细审查它的安全策略，了解它能访问什么资源、会产生什么副作用。不能想当然地认为 agent 框架会替你把好这道关，安全责任是分层的，搞清楚每一层的边界才能真正做到安全可控。

我还想说一个更宏观的观察。这篇文章展示的不只是技术方案，更是 OpenAI 工程团队做决策的思维框架：每一个看似简单的设计选择背后，都有功能、性能、安全、合规、用户体验等多个维度的权衡，而不是追求某一个指标的极致。放弃 previous_response_id，表面上看是"少用了一个功能"，背后是为了无状态设计带来的运维简单性、为了 ZDR 合规、为了更广泛的客户支持。自动压缩替代手动压缩，表面上看是一个用户体验小优化，背后是对 agent 使用模式的深刻理解以及相应的接口设计投入。这种思维方式，对我们做任何软件系统的设计都有借鉴价值：在真实的约束条件下找到整体最优的方案，而不是在真空中追求单一维度的完美。
