今天我们要聊的这篇文章，英文标题叫做 "Harness Engineering: Leveraging Codex in an Agent-First World"，我把它翻译成"线束工程：在以 Agent 为先的世界里，如何真正驾驭 Codex"。这篇文章发表于二〇二六年二月十一日，作者是 OpenAI 的技术成员 Ryan Lopopolo。

今天是二〇二六年九月九日，距离这篇文章发表已经过去将近七个月了。在 AI 领域，七个月是很长的时间，我需要先帮你定一下位。

二〇二六年初，大语言模型的能力已经有了质的飞跃，GPT 五刚刚发布不久，各家大厂的 coding agent，也就是专门的编程 agent，开始从"智能代码补全工具"向"能自主完成完整工程任务"的方向演进。Codex 是 OpenAI 旗下的编程 agent，它可以接受自然语言描述的任务，自主地写代码、运行测试、提交 PR。PR 就是 pull request，代码合并请求，是工程团队里日常协作的基本单位。当时整个行业都在问同一个问题：这些工具真的能在真实的、复杂的工程场景里可靠地工作吗？

这篇文章给出的不是理论上的回答，而是一个来自 OpenAI 内部的真实工程实验的完整总结。实验持续了五个月，从无到有构建了一款有真实用户的产品，全程一行代码都不手写。如果你现在正在考虑如何在团队里认真落地 AI 编程工具，而不只是用它做个代码补全，那这篇文章是目前我见过的最有操作价值的一手经验。因为它讲的不是"AI 能写多好的代码"，而是"工程师需要建设什么样的环境，才能让 AI 持续可靠地工作"。这个问题，正是当前整个行业最核心的挑战之一。

好，我们正式进入今天的内容。

先来说背景。文章的背景是这样的，OpenAI 内部有一个工程团队，他们给自己设了一个极端的约束：用五个月时间，构建一款真实可用的软件产品，但在整个过程中，一行代码都不手写。所有代码，包括应用逻辑、测试、CI 配置也就是持续集成配置、文档、可观测性系统，还有内部工具，全部由 Codex 来生成。

第一次提交发生在二〇二五年八月末，是一个完全空白的代码仓库。连最开始的仓库骨架，包括目录结构、CI 配置、代码格式规则、包管理器设置、应用框架，还有那个给 agent 提供工作指引的 AGENTS.md 文件，也全都是 Codex 在 GPT 五的驱动下、参照一小组现有模板生成的。从第一行开始，这个仓库就是由 agent 来塑造的。

为什么要这么极端？作者解释说，他们刻意选择这个约束，是为了逼自己真正搞清楚：当工程团队的主要工作不再是写代码，而是设计环境、表达意图、构建反馈循环，到底需要做哪些事，才能让 agent 稳定可靠地工作？换句话说，这不是为了证明"AI 能写代码"，而是为了搞清楚"要让 AI 成为真正的生产力引擎，工程师需要建设什么"。

五个月之后的结果是：仓库里有大约一百万行代码，涵盖应用逻辑、基础设施、工具链、文档和内部开发工具。整个过程里大约有一千五百个 PR 被提交并合并。最开始只有三名工程师驱动 Codex，人均每天产出大约三点五个 PR，随着团队扩展到七人，人均吞吐量还在继续上升。而且这不是为了产量而产量，这款产品在 OpenAI 内部已经有了每天使用的真实用户，也有了外部的 alpha 测试用户。文章估计，他们用大约十分之一的时间，做出了手写代码需要全部时间才能完成的工作量。

好，背景清楚了。接下来我们逐层拆解文章的核心洞察。我选了五个最值得展开讲的点，我们一个一个来。

第一个点：人类掌舵，Agent 执行。

文章的核心哲学用一句英文说就是 "Humans steer. Agents execute."，人类来掌舵，agent 来执行。

这听起来很简单，但真正落地的时候，思维方式要发生非常大的转变。

在传统的工程团队里，工程师的核心输出是代码。即使用了 AI 辅助工具，工程师也在亲自操作代码编辑器，逐行审查，手动调试。而在这个实验里，工程师的日常工作完全不同了，他们的主要产出不再是代码，而是"描述"，是意图的精确表达，是对任务的框定和对 agent 工作结果的验证。

人类工程师几乎完全通过 prompt 来与系统交互。prompt 是你给 AI 的自然语言指令。工程师描述一个任务，启动 agent，让它开 PR。为了把 PR 推向完成，他们会让 Codex 在本地审查自己的变更，在本地和云端请求额外的 agent 审查，响应人工或 agent 给出的反馈，在一个迭代循环里不断完善，直到所有 agent 审查者都满意为止。这个流程里，人工审查 PR 是可选的，不是必需的。随着时间推移，他们把几乎所有审查工作都推给了 agent 来做，实现了真正的 agent 对 agent 的审查流程。

作者提到了一个非常重要的思维转换：当某件事失败了，正确的反应不是"让 agent 再试一次"，而是停下来问："这里缺少什么能力？怎样让这个能力对 agent 来说既可理解又可执行？"因为只有把解决方案编码进工具链或文档，这个问题才会永远消失，而不是在每次运行时反复出现。

文章还提到，让 Codex 能直接使用标准开发工具，比如 gh 这个 GitHub 命令行工具、本地脚本、仓库内置的技能模块，来自主收集上下文信息，而不需要工程师手动复制粘贴。这是一个很重要的细节：如果 agent 必须依赖人来中转信息，那人就变成了瓶颈。

我个人认为，这个从"写代码的工程师"到"设计系统的工程师"的转变，是深刻的，对很多人来说需要主动地去适应和接受。

第二个点：给 Codex 一张地图，而不是一本百科全书。

这是文章里我认为最有操作价值的洞察，也是很多团队最容易犯错的地方。

很多团队在开始用 agent 写代码的时候，第一个本能反应就是：把所有规则、约定、架构说明都写进一个大文件里，然后让 agent 每次都读它。这个团队也试过。然后发现，这个方法在几个地方系统性地失败了。

首先是 context 的稀缺性问题。Context 是 agent 每次运行时能看到的信息总量，这是一个有上限的稀缺资源。一个体积很大的指令文件会占用大量的 context 窗口，把真正要处理的任务代码和相关文档都挤掉。结果是 agent 要么漏掉关键约束，要么针对错误的目标做优化。

其次，太多的指导等于没有指导。当所有内容都标注为"重要"，agent 就无法分辨什么真正重要。它会开始局部地做模式匹配，而不是有目的地推理整个问题。

第三，这个文件会快速腐烂。一个庞大的规则手册很快就变成了一堆过时规则的墓地。Agent 分不清哪些还有效，人也懒得维护，文件变成了一个"危险的吸引物"，看起来有内容，但内容已经不可信了。

第四，单一的大文件很难做机械化的验证，覆盖率、新鲜度、交叉引用这些质量检查都不好做，偏差是不可避免的。

所以他们把 AGENTS.md 从百科全书变成了目录。这个文件本身大约只有一百行，它的作用是一张导航地图，告诉 agent 在什么情况下去哪里找什么信息。真正的知识库在一个结构化的 docs 目录里，被当作权威的信息来源来对待。里面包含设计文档，建有索引，包括验证状态和核心理念。架构文档，提供领域和包层次的顶层地图。质量文档，对每个产品领域和架构层打分，随时间追踪差距。

计划被当作一等公民来对待。小改动用轻量级的临时计划，复杂工作用专门的执行计划，记录进展和决策日志，而且这些全部提交到仓库里。活跃计划、完成的计划、已知的技术债，都版本化地放在一起，让 agent 不需要依赖任何外部系统就能工作。

这套设计实现了他们说的"渐进式披露"，agent 从一个简洁稳定的入口出发，被明确告知下一步去哪里找信息，而不是一开始就被淹没在海量内容里。

而且他们在机械化层面强制执行这套结构。有专门的 linter，也就是代码检查工具，和 CI 任务，来验证知识库是否是最新的、有没有正确的交叉引用、结构是否合规。还有一个定期运行的"文档园丁" agent，专门扫描过时或不反映真实代码行为的文档，自动开 PR 修复。

文章里有一个类比让我觉得非常精准。他们说，给 agent 提供上下文信息的方式，就像是给新员工做入职培训。你不会在第一天就把公司所有的文档都甩给一个新人，你会先给他一个概览，告诉他什么时候去哪里查什么，然后随着他的工作深入，再逐步暴露更多细节。这套逻辑对 agent 完全一样。

还有一个很重要的点：那个在 Slack 上讨论了两个小时才确定的架构选型，那个在周会上对齐的团队规范，如果没有写进仓库，对 agent 来说就等于不存在。Agent 只能看到仓库里的信息，仓库之外的知识对它来说是不透明的，就像一个三个月后加入的新员工完全不知道那些历史决策一样。这个洞察倒逼团队养成把重要决策文档化落入仓库的习惯。

第三个点：严格的架构约束，让 agent 高速而不腐化。

这个点是整篇文章技术含量最高的部分，也是最反直觉的一个地方。

通常我们觉得，严格的架构约束是几百人的大团队才需要操心的事。小团队快速迭代，先把功能做出来，架构等规模上去之后再说。

但这个团队的实践给出了完全相反的结论：在 agent 驱动开发的场景里，严格的架构约束不是大团队的奢侈品，而是小团队早期就必须建立的基础设施。原因很简单：agent 的输出速度比人快得多，如果没有刚性的约束，技术债会以指数级速度积累，快到你根本来不及处理。

他们建立了一个非常刚性的架构模型。每个业务领域被划分成固定的几个层次，依赖方向是严格单向验证的，只允许有限的几种连接方式。举个具体例子，一个叫做"应用设置"的业务领域，代码只能按照"类型层→配置层→数据仓库层→服务层→运行时层→界面层"这个固定顺序向前依赖，不能反向，也不能跨层跳跃。跨领域的通用关注点，比如身份认证、连接器、遥测系统、功能开关，只能通过一个叫做 Providers 的单一显式接口进入系统，其他方式全部被禁止，而且是机械化地禁止。

这些规则通过自定义 linter 和结构性测试来强制执行。值得一提的是，这些 linter 本身也是 Codex 写的。

为什么这样做对 agent 特别重要？因为 agent 在推理时需要明确的边界。如果架构是松散的，agent 就不知道应该把一段逻辑放在哪里，边界在哪里。它会做出局部看起来合理但全局不一致的决策，久而久之，代码库就变成了一堆互相纠缠的乱麻，而且因为速度快，乱的比人工开发要快得多。

有了严格的层次约束之后，agent 在任何时候都能清楚地推断：我现在在哪一层工作，我可以依赖什么，我绝对不能依赖什么。这大大压缩了 agent 需要自行做判断的空间，让它可以专注在具体任务本身。

一个非常精妙的细节：他们会让 linter 的报错信息里直接包含修复指令。这样当 agent 的代码违反了一条规则，报错信息本身就成了 agent 修复代码的输入。把约束执行和修复指导融合在一起，形成闭环，而不是让 agent 面对一个无法理解的错误码停在那里。

除了架构层约束，他们还有一组"品味不变量"，用他们的话说。比如，强制要求结构化日志，schema 和类型的命名约定，文件大小上限，特定平台的可靠性要求，全部通过自定义 linter 静态执行。

文章还提到一个关于技术选型的洞察，是我觉得很多人会忽略但非常值得记住的：他们倾向于选择"无聊的技术"。API 稳定、可组合性好、在训练数据里有大量覆盖的技术，agent 对它们的理解更深，犯错概率更低。有时候，他们甚至选择让 agent 重新实现某个功能，而不是依赖一个行为不透明的第三方库。文章举了一个具体例子：他们没有用 p-limit 这个通用的并发控制包，而是让 agent 实现了自己的并发映射工具，这个工具与他们的 OpenTelemetry 遥测系统紧密集成，有百分之百的测试覆盖率，行为完全符合运行时预期。这不是反对用第三方库，而是一个有意识的成本收益判断。

第四个点：让 agent 能看见整个系统，包括界面、日志和指标。

随着代码吞吐量提升，他们的瓶颈变成了人工质量验证的容量。人的时间和注意力是固定的稀缺资源，所以他们的解法是：把尽可能多的质量验证工作给到 agent 自己来做。

他们做了几件很有代表性的事情。

第一，让应用可以按 git worktree 独立启动。Worktree 是 Git 里的一个功能，允许在同一个代码仓库里同时维护多个独立的工作目录，每个目录对应不同的代码状态。这样 Codex 就可以为每个待验证的变更启动一个完全隔离的应用实例，在这个实例里做验证，不影响任何其他正在进行的工作，验证完成后这个实例就销毁了。

第二，他们把 Chrome DevTools Protocol，也就是 Chrome 浏览器的开发者工具协议，接入了 agent 的运行时环境，为 agent 提供了操作 DOM 快照、截图和页面导航的能力。这意味着 Codex 可以真正地"看到"用户界面，可以复现 bug，验证修复，推理 UI 行为，而不只是看代码本身。

在可观测性方面，他们为每个 worktree 提供了一套短暂存在的本地可观测性工具栈。Codex 可以用 LogQL 查询日志，用 PromQL 查询指标，任务完成后这套工具就随着 worktree 一起销毁，完全隔离，完全干净。

这带来的效果是实质性的。你现在可以给 agent 这样的 prompt："确保服务启动在八百毫秒以内完成"，或者"这四条关键用户旅程里没有任何一个追踪跨度超过两秒"。这些 prompt 涉及真实的运行时行为，以前是只有人才能做的验证工作，现在 agent 可以独立完成了。

文章里有一句话让我印象很深：他们经常看到单次 Codex 运行在一个任务上工作超过六个小时，而且通常是在工程师睡觉的时候。这几乎是 agent 工作方式最吸引人的特性之一，它可以在你不在的时候持续地推进。

第五个点：全自主的端到端流程，加上持续的"垃圾回收"。

文章描述了一个让人印象深刻的全自主工作流。给 agent 一个单一的 prompt，它现在可以完成：验证代码库当前状态，复现一个报告的 bug，录制视频展示这个失败，实现修复，通过驱动应用来验证修复，再录制一个视频展示解决结果，开 PR，响应 agent 和人工的反馈，检测并修复构建失败，只在需要人工判断的时候才上报给人类，然后合并变更。

这几乎是一个完整的软件交付流水线，人类只在关键的决策点介入。

但文章也坦诚地指出了全自动化必然带来的新问题：agent 会复制仓库里已有的模式，包括不好的模式。随着时间推移，这必然导致代码库的漂移和质量下降。他们最初的解决方案是人工清理，每周五专门花百分之二十的时间清理所谓的"AI 垃圾"。这当然无法扩展。

于是他们建立了一套叫做"黄金原则"的机制，配套一个持续运行的自动清理流程。黄金原则是一组有见地的、机械化的规则，让代码库对未来的 agent 运行始终保持清晰和一致。例如，他们偏好使用共享工具包而不是各处手工实现的辅助函数，这样不变量就集中在一个地方，而不是分散在整个代码库里。又例如，他们不允许"YOLO 风格"地探测数据，也就是靠猜测数据的形状来工作，必须在边界处做验证，或者依赖有类型定义的 SDK，这样 agent 就不会在猜测的数据结构上建东西。

然后他们跑了一组后台 Codex 任务，定期扫描偏差，更新质量评分，开目标明确的重构 PR。大多数这种 PR 可以在一分钟以内审查完并自动合并。

文章用垃圾回收来类比这个过程。技术债就像高利贷，持续小步还债几乎总是比让它积累然后一次性解决要好得多。人工品味只需要表达一次，被编码进黄金原则，然后被持续地强制施加到每一行代码上。这让他们能够每天发现并修复不好的模式，而不是让它在代码库里悄悄蔓延几周，等到量变引起质变才发现。

好，五个核心点讲完了。我们现在来聊聊这对你实际工作意味着什么，以及有哪些坑是要提前规避的。

先说你现在就能开始做的事情。

如果你已经在用 AI 编程工具，不管是 Codex、Claude、Cursor 还是 GitHub Copilot 的 agent 模式，第一个立竿见影的改进是：认真设计你给 agent 的说明文件，也就是类似 AGENTS.md 的东西。不要试图把所有东西都塞进去。你的目标是给 agent 一张导航地图。你可以在这个文件里说明代码库的整体结构，列出关键文档的位置，说明哪些决策是已经固定的，哪些地方 agent 有自由裁量的空间，哪些行为是绝对禁止的。篇幅控制在一百行以内，剩下的内容通过指向专门的文档。

第二件事，从今天开始养成把重要决策写进仓库的习惯。那个解释"我们为什么不用这个框架"的 Slack 讨论，那个说明"这里为什么要用这个设计模式"的会议对齐，如果不落入仓库，对 agent 来说就等于不存在。你不需要写得很长，一两段话说明背景和结论就够了，放进 docs 目录，给它一个清晰的文件名。这些文档日积月累，就成了 agent 理解你的业务域和工程决策的核心依据，也成了新人入职时的重要参考。

第三件事，优化你的 linter 和 CI 系统的报错信息。很多团队的自动化报错只会告诉你"规则 X 被违反了"，但不告诉你怎么修。如果你希望 agent 能自动修复这些问题，就要把修复指导直接写进报错信息里。比如，与其说"文件行数超限"，不如说"文件超过了五百行，考虑把 Y 部分逻辑提取成独立的模块"。这对人类开发者也是有价值的，但对 agent 来说尤其关键，因为报错信息就是 agent 的修复线索来源。

然后说说需要团队层面推进的事情。

最重要的是：把团队的"黄金原则"显式化，并且让它们机械化。你们团队关于代码风格和架构有没有共识？这些共识现在是活在人的脑子里、口口相传，还是已经被编码进了工具链？如果只是口口相传，在以 agent 为主的工作流里，这些共识对 agent 来说是不存在的。

一个实际可行的做法是：开一次专门的工作坊，让团队成员把各自脑子里的"好代码应该是什么样的"写下来，讨论哪些规则值得机械化执行，然后把它们写成 linter 规则或者测试。这个过程本身就很有价值，因为它会暴露团队成员之间未对齐的假设，让你们在早期就解决分歧，而不是让这些分歧通过 agent 悄悄地被放大到整个代码库的每一个角落。

另一个值得投入的方向是让你的应用更容易被 agent 驱动来做端到端验证。最简单的起点是：你能不能写一个脚本，让应用在隔离环境里启动，然后跑一组基本的功能检查？如果能做到这一步，你就已经给 agent 提供了一个最基本的"感知能力"，让它可以在本地验证自己的改动是否真的工作，而不只是凭借代码推理来猜测。

还有一个容易被忽略的实践：把执行计划提交到仓库。对于跨越多天的复杂任务，把当前的进展、已做的决策、下一步要做什么，用一个 markdown 文件记录下来，提交到仓库。这样即使 agent 会话中断了，下一次启动的 agent 也能从上次停下来的地方继续，而不是完全从头开始，避免大量重复工作。

然后是要主动规避的坑。

第一个坑：不要期待 agent 在一个没有结构的环境里可靠工作。文章反复强调，他们早期进展慢，不是因为模型不够强，而是因为环境没有设计好。如果你发现 agent 经常出错、偏离方向、或者做出奇怪的决策，先不要怪模型，先检查环境：文档够不够完整清晰？架构约束够不够明确？工具链给出的反馈够不够及时、够不够有信息量？很多时候，问题不在模型，在环境。

第二个坑：不要忽视代码库的漂移。如果你没有建立持续的清理机制，agent 会复制并放大现有的模式，包括坏的模式。你今天写的一个临时解决方案，三个月后可能已经被 agent 照葫芦画瓢地复制到了几十个地方。建立某种定期回顾机制，哪怕最开始是人工做，每周检查一次代码质量，把发现的模式问题写成规则，然后让规则逐步自动化。

第三个坑：技术选型要有意识地考虑 agent 的可理解性。文章里说，他们倾向于选择 API 稳定、可组合性好、在训练数据里覆盖充分的"无聊技术"。这不意味着不能用新技术，但要有意识地评估：引入这个技术之后，agent 处理相关代码时出错的概率会不会明显上升？如果答案是肯定的，引入成本就不只是你的学习曲线，还叠加了 agent 的不可预测性成本。

第四个坑：不要把人工审查能力和 agent 审查能力混淆。文章里他们说人工审查是可选的，但这是在他们已经建立了完整的 agent 审查体系、有充分的测试覆盖和机械化约束的前提下说的。如果你的团队还没有建立这些，就直接跳到让 agent 自主合并 PR，那是在冒险。先投资好审查的基础设施，再逐步减少人工审查的比例，而不是反过来。

最后，我想说说心态上的一个深层转变。

文章里有一句话说得非常准：工程纪律并没有消失，它转移到了脚手架上，而不是代码本身。过去工程师的专业能力体现在亲手写出好的代码上，但在 agent 为主的工作流里，专业能力体现在设计出好的环境，让 agent 能持续可靠地产出好的代码。

这就像是从"我是一个好厨师"到"我是一个设计了好厨房的人"。核心能力从具体操作技艺转向了系统设计能力。这个转变不是降级，而是在另一个更高的层次上发挥能力。一个能设计出让 agent 稳定高效工作的工程环境的人，在这个新的范式里所创造的杠杆效应，远远超过一个只关注自己那部分代码写得多好的工程师。

好，今天我们聊了 OpenAI 工程团队用五个月、零手写代码构建真实产品的这篇文章。核心的几个工程原则值得再浓缩一遍：人类掌舵 agent 执行，用渐进式披露管理 agent 的上下文，用刚性的架构约束让高速工作不产生混乱，把可观测性和界面开放给 agent 让它自己做质量验证，用持续运行的黄金原则机制做代码库的"垃圾回收"。
