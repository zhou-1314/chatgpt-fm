想象一下这个场景：你正在用语音和AI对话，刚刚说到一半，它就突然开口回应，把你后半句话直接截断。或者反过来，你说完了停下来等着，结果AI沉默了两三秒，才慢慢吐出第一个字。

这两种体验，相信用过早期语音助手的朋友都不陌生。它不像和人聊天，更像是在打对讲机——按键、说话、松键、等待、再重复。这个节奏的别扭，是语音AI这个方向长期以来没解决的根本问题。

先说背景，为什么 OpenAI 要费这么大劲重新设计语音系统？

早期的语音AI，包括 OpenAI 自己的前两代系统，都有一个根本性的架构限制：它们是"轮次制"的。所谓轮次制，就是说用户说一段话，AI 听着，用户停下来，AI 处理，然后回复，用户再说，如此往复。就像打乒乓球，一来一回，非常机械。

在这个流程里，有一个关键的小角色叫"轮次检测器"，英文是 turn detector。顾名思义，它是一个相对轻量的模型，专门用来判断一件事：用户是不是说完了？只有轮次检测器判断"用户停了"，后面的大语言模型才能开始工作。

你可能会问，这有什么难的？检测一个停顿不就行了？

实际上难度很大。人说话的时候，停顿有很多种类型：思考的停顿、换气的停顿、犹豫时拖出来的"那个……"，有时候是句子中间的语气停顿，有时候才是真正说完了。轮次检测器必须实时判断这是哪种情况。

猜早了，用户还没说完就被打断，体验极差。猜晚了，AI 在用户已经停下来之后迟迟不回应，对话变得拖沓。用文章原话来说，轮次检测器面临的是"猜早了打断用户，猜晚了感觉迟钝"的两难困境——这是一个谁都不想接的烫手山芋。

而且轮次检测器只是整个流水线的第一步。即便它判断正确了，大语言模型才能开始工作。这在整个响应链里强行插入了一个不确定的等待环节，而且这个等待的长短还受到每个人说话习惯的影响，很难做到稳定的低延迟。

更早期的"级联系统"问题更严重。所谓级联，就是把语音识别、大语言模型、语音合成三个步骤串联起来，一个接一个跑。这种架构不仅把延迟叠加了三倍，还会丢失语音中大量的非语言信息：语调的高低、语速的快慢、停顿的节奏——这些在把语音转成文字的过程中全部消失了。AI 只知道你说了什么，却不知道你怎么说的。

后来出现了语音到语音的端到端模型，直接处理音频输入和输出，跳过了文字转录的中间步骤。这确实改善了延迟，也保留了更多语音细节。但根本架构没变——轮次检测器还在，对话依然是轮次制的。

GPT-Live 要做的，是把这个根本问题从架构层解决掉。

GPT-Live 的核心创新，用两个字总结：全双工。英文是 full-duplex。

全双工是什么意思？我们用一个大家都熟悉的类比。对讲机是半双工的：一次只能一个人说话，说完要按下接收键才能听到对方。两个人不能同时开口，必须一个等另一个说完。

电话是全双工的：你可以在说话的同时听到对方说话，两个方向的声音互不干扰。就算两个人同时开口，信道也不会崩，只是两个声音叠在一起，但物理上是完全支持同时传输的。

以前的语音AI是对讲机模式，用户说一段发送出去，AI 听、处理、回复，然后等用户下一段。GPT-Live 是电话模式，语音模型可以在听你说话的同时出声，也可以在自己说话的同时倾听你说的话。它不需要等一个"停话检测"的信号才能开始思考和回应。

这意味着轮次检测器这个角色，从整个系统里彻底消失了。音频流连续地进入模型，模型自己控制什么时候开口、什么时候保持安静、什么时候在对方说话时插入一句"嗯嗯"。就像真正的人类对话，不需要任何外部裁判来管控说话权。

全双工模型解决了谁来决定何时说话的问题，但要让整个系统在生产规模下稳定跑起来，还需要一套围绕"让音频流不间断"构建的专门架构。

OpenAI 在架构上做的最关键决策，是把媒体流路径和应用逻辑严格分离。

具体来说，音频在客户端和语音模型之间走一条专用的快速通道，这条通道只做一件事：保证音频帧按时到达。而工具调用、搜索、业务逻辑这些操作，走另一条独立的异步通道，两者互不干扰。

这样设计的好处非常清晰：即使某个工具调用很慢，或者某个后端服务卡住了，它只会延迟自己的结果，但无法打断音频流的传输。把慢的东西隔离在慢的通道里，让快的通道保持纯净。这是整个 GPT-Live 系统的架构哲学。

为了让这条快速通道足够可靠，他们把媒体前端和推理逻辑从 Python asyncio 重写成了 Go 语言。这个选择不难理解：Go 在网络处理和协程调度上，延迟的可预测性要远优于 Python。实测结果也印证了这一点：重写之后，新系统的 P95 延迟——也就是95%的请求所经历的最大延迟——等于旧 Python 系统的 P50，也就是中位数延迟。换句话说，新系统最差情况下的延迟，和旧系统的平均水平相当。这个改善幅度是相当显著的。

传输层用的是 WebRTC，这是一个专为实时媒体通信设计的协议。它对网络问题非常健壮：丢包、时钟漂移、网络切换，都有成熟的处理机制。比如数据包迟到了，WebRTC 会悄悄拉长音频填补间隙，然后稍微加速播放追回实时进度，用户基本感知不到这些操作。

接下来讲有状态推理，这是实现连续对话最有挑战性的技术问题之一。

普通的大语言模型推理是无状态的：你发来一个请求，模型处理完了返回结果，一次性的。下次请求来了，模型对之前发生的事情一无所知，需要你把上下文重新带过来。

语音对话完全不一样。它是持续进行的，可能持续几分钟甚至几十分钟。这就要求推理是有状态的——模型必须一直记着整个对话的上下文，而且这些状态需要在模型实例上持久存在，不能每次都从头开始。

这里有一个关键概念叫 KV cache，键值缓存。当模型处理过一段输入之后，它会把这些输入对应的注意力键和值——这是 transformer 架构里的核心计算结果——存下来。下次处理新内容时，旧的键值对直接复用，不用重新计算。这极大地减少了推理的计算量和延迟。

有状态推理带来了两个很现实的运维挑战。

第一个挑战是模型实例的替换。大规模系统里，模型实例会因为各种原因需要更换：机器故障、版本升级、负载均衡调度。在无状态系统里，这很简单，新实例接手就行了。但在有状态系统里，整个对话上下文——可能几十分钟积累的内容——都绑定在当前实例上。怎么做到对用户无感知地切换？

OpenAI 的解决方案叫"无缝切换"。具体流程是这样的：当需要切换的时候，系统在旁边预热一个新的模型实例，把当前对话的完整上下文填充进去——这个过程叫 prefill，也就是预填充。然后同时让新旧两个实例并行运行推理，等新实例完全就绪之后，再把流量切过去。整个切换过程中，语音对话一刻不停，用户完全感知不到中间发生了什么。

打个比方，这就像高速公路上的隧道并联施工：旧道还在通车，旁边新道悄悄建好，等新道通了，直接把车流引过去，中间不堵车。

第二个挑战是上下文长度超限。随着对话越来越长，累积的上下文可能超出模型的上下文窗口限制。这时候需要做"上下文压缩"，英文叫 context compaction：把过去的对话浓缩成一个更短的摘要，删掉不那么重要的细节。

听起来简单，但有两个实际问题。一是压缩操作本身耗时；二是上下文内容变了之后，之前缓存的 KV cache 全部失效——因为那些键值对是基于原来那段上下文算出来的，上下文一变，以前的计算就不能用了，需要重新 prefill。在对话进行中做这件事，会产生明显的停顿。

OpenAI 的应对方案依然是受管切换的思路：当前实例继续和用户正常对话，后台悄悄进行上下文压缩，压缩完了准备好新实例，再无缝切换过去。用户感知到的，只是一场流畅的对话，完全不知道背后发生了什么。

这种"把繁重工作甩到后台、前台保持流畅"的设计原则，是 GPT-Live 整体架构的核心哲学。

好，接下来说另一个很有意思的设计：异步委托。

GPT-Live 的语音模型负责日常的流畅对话，反应快、延迟低。但有些问题是它搞不定的：需要联网搜索最新信息，需要深度推理的复杂问题，需要调用各种工具的任务。这些场景怎么办？

答案是不用一个模型解决所有问题，而是委托给更强的模型。GPT-Live 可以在不中断语音对话的情况下，把这类任务异步地交给 GPT 五点五这样的前沿模型处理。语音模型继续和用户保持流畅交流，可能说一些"我在帮你查一下"之类的过渡语，而 GPT 五点五在后台完成推理和工具调用，完成后把结果回传给语音模型，语音模型再用口语化的方式呈现给用户。

这个设计非常优雅，但有一个硬性的工程约束：委托路径必须足够快。语音模型能帮你撑场子，说一两句过渡语，但不能无限期地等下去。如果 GPT 五点五花了三十秒才回来，用户早就不耐烦了。

为了让委托足够快，OpenAI 做了几件事。

第一，在语音会话开始的时候，提前给前沿模型创建好推理会话，把初始的对话上下文预先填充进去。这样，当第一次委托请求来的时候，prompt 已经处理好了，不需要从零开始，直接开始推理就好。

第二，用稳定的会话亲和性，也就是同一个用户的连续委托请求，始终路由到同一个前沿模型实例。结合 prompt 缓存技术，每次委托的冷启动成本大幅降低，因为很多上下文已经在缓存里了。

第三，精心调整推理参数：缩短推理深度，限制输出长度，精简工具的 schema，减少模型和工具之间来来回回的次数。每一个可以节省时间的旋钮都拧到合适位置。

文章把从路由、提示处理、推理到工具调用的完整链路，都纳入了"响应速度预算"的范畴来管理。这个角度非常有工程实践意义——委托路径不是一个独立的后台任务，而是对话体验的一部分，必须一起优化。

我个人认为，这种"说话模型"加"思考模型"的两层架构，是目前语音AI最成熟的设计路线。说话模型专注实时流畅，思考模型专注质量深度，两者通过异步机制协同，谁也不拖累谁。这比试图用一个模型同时做好两件事，要现实得多。

接下来讲一个不那么显眼但同样重要的工程问题：消息分割，英文叫 message segmentation。

GPT-Live 的语音模型处理的是连续的音频流，这没有问题。但 ChatGPT 的界面展示、分析记录、安全审核系统——这些下游系统处理的都是离散的消息：一条用户消息、一条 AI 回复，整整齐齐地排在那里。有人需要把连续的音频流翻译成这些下游系统能理解的离散消息。

这个工作听起来很简单，实际上非常棘手。

难点在于人说话会重叠，会互相打断。你想象一个典型的场景：用户还在说话的时候，AI 说了一句"嗯嗯"表示在听。这算一条 AI 消息吗？如果算，这条消息在时间线上怎么排？

或者，AI 在用户说话中途插了一句有实质内容的话，这该不该作为独立的一条 AI 消息记录下来？

再或者，用户说了一半停了五秒，然后继续说，这是一条消息还是两条消息？

系统必须根据实时转录文本和时间信号，不断推断谁在说话，并构建消息队列。最新的那条消息始终是"暂定"的——它的文字内容、时间戳、说话人归属，都可能随着后续音频的到来而改变。只有当某个说话人连续主导了足够长时间，归属足够可靠了，这条消息才会被正式定稿。

为了服务不同的下游需求，系统维护两个视图：一个是推测视图，反映当前最新的估计，可能随时更新，供界面展示用；另一个是权威记录，只记录已定稿的消息，供日志和分析管道用。

这本质上是在"新鲜度"和"确定性"之间找一个动态平衡。定稿太早，历史记录碎片化，顺序可能乱；等太久，下游系统拿不到数据，依赖它的功能也跟着慢。这是个没有完美答案的工程权衡，只能根据实际场景来调参。

好，现在来聊最后一个重大技术：连接建立的优化。

用户点击"开始对话"，到系统真正开始传输音频，中间需要多长时间？这段时间直接影响用户的第一印象，也是文章里花了大量篇幅讲的部分。

WebRTC 是 GPT-Live 的传输基础，专门为实时媒体设计的协议。但 WebRTC 有一个历史包袱：建立连接需要很多次握手，在客户端和服务器之间来来回回。建立标准的 WebRTC 连接，需要六个来回——六个 round trip——才能把媒体通道和数据通道全部建立好。

六个来回是什么概念？在延迟稍高的网络环境下，一个来回可能需要五十到一百毫秒。六个来回加起来，光这个建立过程就可能需要三四百毫秒甚至更多。话还没说，时间就过去了。

为什么需要这么多来回？因为 WebRTC 是由多个独立的协议叠加构成的，每个协议被设计的时候，都不知道自己会和其他协议一起用，于是各自都带了自己的握手步骤，甚至都有自己的反攻击机制。等它们被叠在一起用的时候，很多工作就重复了。文章里说，WebRTC 的设计年代比 QUIC 这类现代协议早，没能受益于后来那种"减少来回次数"的设计理念。

OpenAI 分析了整个 WebRTC 协议栈，开发出了一套叫做 WARP 的协议扩展，全称是 WebRTC Abridged Roundtrip Protocol，我把它译为"WebRTC 精简握手协议"。WARP 的目标是：通过一系列向后兼容的协议改进，把连接建立从六个来回压缩到一个。

WARP 具体包括几项技术。第一，把 DTLS 握手——数据报传输层安全握手——附着在 ICE 探测包上一起发送，省掉一次独立的握手流程。第二，使用 DTLS 一点三版本，它的握手本身比之前的版本更快。第三，预先协商 SCTP 握手——流控制传输协议握手。第四，预先协商数据通道，而不是用动态协商机制在连接时现场开通。

这四个优化的共同逻辑：把原来必须在连接建立时完成的工作，尽可能提前做或者合并做，减少总的来回次数。就像办理入职手续，与其一个部门一个部门排队跑，不如提前把所有材料都准备好，一次性搞定。

值得一提的是，OpenAI 把 WARP 做成了开放规范，而不是私有技术。他们正在通过 IETF 的 TSVWG 工作组推进标准化，libwebrtc 和 Pion 这两个主流的 WebRTC 实现库已经加入了 WARP 支持。这说明 OpenAI 不只是自己用，而是在推动整个 WebRTC 生态往这个方向走。

除了 WARP，他们还开发了一个叫"即时连接"的机制，英文叫 Instant Connect。

WebRTC 在连接之前，需要先交换 SDP 参数——会话描述协议参数。这是双方协商"用什么编解码器、走什么网络路径"的过程，也需要一次网络来回。

Instant Connect 的思路是：在用户还没点"开始"的时候，就提前在后台把这些参数谈好存起来。当用户真的点击连接，服务器一收到第一个 UDP 数据包，就能立即用预先协商好的参数建立会话，不需要再等信令交换。

如果预先谈好的参数过期了或者失效了也没关系——正常的信令流程已经在并行进行，系统可以无缝回落到正常流程，不产生额外延迟。这是一个"有则用，无则降级"的典型设计。

结合 WARP 和 Instant Connect，从用户点击到音频流开始传输的时间被大幅压缩。理论上，一个 UDP 数据包就能启动完整的媒体会话，服务器可以立刻响应，让整个系统开始做用户真正关心的事：听和说。

接下来说说他们怎么测试的，这部分同样非常值得关注。

GPT-Live 正式上线之前，OpenAI 做了一个影子测试，英文叫 shadow test，有时也叫 silent test。做法是：把少量生产流量，悄悄同时路由到旧系统和新系统。旧系统正常服务用户，用户听到的仍然是旧系统的声音。新系统以只读模式并行运行推理，不把结果发给用户，也不影响任何人的使用体验。流量比例从小到大慢慢增加。

这种方式的核心价值：用真实的客户端、真实的网络条件、真实的用户行为来压测系统，同时零风险。短时间的人工负载测试永远无法完全模拟生产环境的复杂性，但影子测试可以。

实际测试暴露出了好几个意想不到的问题。

第一，容量模型需要重建。以前估算容量，主要看 GPU 能处理多少推理请求。但语音会话是持续的长连接，每时每刻都在发送音频帧，这意味着 CPU 侧的流处理器、队列、网络连接都必须全程跟上。实际测试中，某个辅助组件在比预测更早的时候触碰到瓶颈，导致推理请求开始堆积，延迟急剧恶化。他们因此重新定义了容量问题：从"GPU 能跑多少请求"改成"系统能维持多少个并发会话，同时保证每一帧按时到达"。这一个措辞的改变，背后是整个容量规划思路的转变。

第二，地理位置成了头等大事。把会话路由到地理位置遥远的数据中心，会在启动和流传输的多个环节增加延迟。他们开始把模型发布和区域容量、流量调度配置捆绑在一起验证，并按来源地理位置拆分分析延迟数据。把推理节点部署在离用户更近的地方，效果明显，但这也强化了一个更大的教训：端到端的响应速度取决于路径上的每一个服务，不只是模型服务器。

第三，只有长时间运行的会话才会暴露的问题。内存压力、持久化压力、重连时的状态恢复、客户端正常断开时的竞争条件——这些在短时负载测试里几乎看不到，因为它们依赖时间积累和跨服务的状态变化。只有真实用户在真实使用，才会触发这些路径。

第四，可观测性需要大幅升级。他们发现有些监控指标把不同来源的延迟混在一起计算，某些 dashboard 的聚合数字掩盖了个别不健康的推理实例，测试环境和生产环境之间有配置漂移。于是他们新增了更细粒度的遥测数据，加入了已知正常配置的校验机制，设计了分阶段放量的流程，以及快速隔离或禁用单个路径的能力。影子测试最终成了一次真正的发布演练，不只是测试系统能接多少流量，更是测试团队能多快发现问题、控制问题、恢复问题。

好，那这篇文章对我们的实际工作有什么意义？

如果你在开发语音相关的 AI 产品，这篇文章里最值得借鉴的架构原则是：媒体流路径和应用逻辑必须严格分离。不要让工具调用、数据库查询、业务逻辑和音频传输共用同一套系统。慢的东西必须在隔离的通道里跑，快的通道必须保持纯净。这一条原则比任何具体的技术选型都更重要。

关于"说话模型"加"思考模型"的分层模式，如果你在用 API 构建语音应用，完全可以借鉴这个思路。用延迟低的轻量模型处理实时的对话交互，用能力强的大模型处理需要深度推理的任务，两者异步协作，而不是串联等待。这样既保证了响应速度，又保证了回答质量，而且两层可以独立优化、独立迭代。

在测试方法上，影子测试这个模式非常值得学习。特别是实时系统和有状态系统，短时负载测试能发现的问题非常有限。如果你有条件，在正式发布之前做一段时间的影子测试，会发现很多只在真实生产环境和真实使用时间长度下才会出现的隐患。提前发现，比上线后暴露要好得多。

关于 WARP 协议的标准化进展，如果你在构建基于 WebRTC 的实时应用，libwebrtc 和 Pion 已经有 WARP 支持了，值得关注。对于冷启动延迟敏感的场景，这可能是一个显著的改善机会，而且是不需要改动上层业务逻辑就能获得的优化。

最后，文章里提到 GPT-Live API 即将开放。如果你在等一个低延迟、全双工的语音 AI 开放接口，可以提前关注这个动向，做好技术准备和产品设计上的预研。

好，来做一个收尾。

今天这篇文章，核心展示了 OpenAI 如何在六个月内从架构层重新设计语音 AI 系统：全双工模型移除了轮次检测器；媒体路径和应用逻辑的分离保证了音频流不间断；无缝切换和上下文压缩解决了有状态推理的运维难题；异步委托让深度推理不打断对话流畅性；WARP 和 Instant Connect 把连接建立从六个来回压缩到一个 UDP 包；影子测试则把大量隐藏问题在上线前就暴露了出来。

我个人认为，这篇文章最有价值的地方不只是哪一个具体技术点，而是展示了一种工程思路：在实时系统里，延迟不是加几个优化就能解决的点问题，而是一个贯穿全栈的系统性约束，必须在每一层——模型推理、上下文管理、传输协议、地理部署、测试方法——都围绕同一个目标来设计和权衡。这个目标，文章用了一句话来概括，也是整篇文章最好的注脚：让声音流动。
