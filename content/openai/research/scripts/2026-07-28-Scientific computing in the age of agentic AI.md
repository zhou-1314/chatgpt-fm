各位好，欢迎收听 ChatGPT FM。今天这期我们聊一篇来自 OpenAI 官网 research 板块的文章，英文标题是 Scientific computing in the age of agentic AI，我的中文翻译是「智能体时代的科学计算」。文章发表于二零二六年七月二十八日，距今大约六个星期，新鲜度很高，正处于 AI 编程 agent 能力快速爆发的阶段，这个背景很重要，我们之后会聊到。

为什么这篇文章值得你在通勤路上花二十几分钟听？我想给你三个理由。

第一，它不是在讲愿景，而是讲实战。OpenAI 这次发布的是一份「田野报告」，是八个真实的团队、八个真实的项目，各自写了案例总结，然后 OpenAI 把这些案例汇总归纳，提炼出共同的规律和教训。这种第一手的实操报告，比任何一篇描述 AI 潜力的文章都更有参考价值。

第二，它聚焦的是一个往往被低估的领域——科学计算软件。很多人在讨论 AI 编程 agent 的时候，想到的是写业务逻辑、做 CRUD、做 web 应用。但科学计算软件有它独特的挑战：结果必须数值上可信，代码经常是论文附带的产物而不是工程产品，用户群体是科学家而不是产品经理。这些特殊性使得 AI agent 在这里的表现和教训，比一般软件工程场景更加极端和典型。

第三，文章提出了一个我认为非常深刻的问题：当 AI 帮你生产了代码，这份代码的长期责任应该由谁来承担？这不只是科学界的问题，而是所有依赖 AI 生成代码的团队都迟早要面对的问题。

好，我们先从背景说起。

在这篇文章里，有一个词反复出现，叫做「维护差距」，英文是 maintenance gap。要理解这个词，你需要先理解科学计算软件是怎么被生产出来的。

想象一个典型的情景：一个做基因组学的研究生，在读博期间需要分析一大批测序数据，但市面上没有现成的工具能完全满足需求，于是她自己写了一套分析流程。这套代码的主要目的是为了支撑她的博士论文，代码写完，论文发出去了，代码也作为补充材料放到了 GitHub 上。

然后一件出乎意料的事发生了：其他研究者发现这个工具非常好用，开始在自己的研究里依赖它。引用次数越来越多，用户越来越多。但这个时候，这位作者已经毕业了，去了下一个职位，已经没有时间也没有资源来持续维护这个工具了。

这就是「维护差距」的典型来源：一个本来只是「研究工具」的代码，慢慢演变成了「科研基础设施」，但它从来没有按照基础设施的标准来构建和维护。它没有完善的打包，没有自动化测试，没有性能优化，没有长期支持计划。

这个问题有多严重？文章里提到了两项专门的研究，一项调查了发表论文附带的研究代码，另一项调查了组学工具，也就是基因组学、蛋白质组学这类领域用到的分析软件。结果发现，其中相当一部分软件，在一个全新的计算环境里压根儿安装不起来，或者安装好了跑起来的结果和文档里描述的完全对不上。这意味着科研人员每次用这些工具，都要花大量时间在环境配置和调试上，而不是在真正的科学研究上。

与此同时，数据本身在以惊人的速度增长。以基因测序为例，测序成本在过去二十年里已经下降到了人类基因组计划时代的百万分之一左右，产生的数据量以指数级在增加。但分析这些数据的软件，很多还是十年、十五年前写的老代码，既跑不快，也难以维护。科学发现的速度在一定程度上被软件的滞后拖住了。

这就是 AI 编程 agent 进入这个领域的背景：一个长期缺乏工程资源、背负大量技术债务、又面临数据爆炸压力的领域。

文章里提到，这次报告覆盖了八个项目，主要集中在生命科学领域，涵盖的任务类型从日常维护、针对性性能优化，到大规模编程语言迁移，再到完全从零用 GPU 原生架构重写。工具里，五个项目单独使用了 Codex，另外三个项目组合使用了 Codex 和 Claude Code。

报告提到了几个具体的工具作为代表案例，我来分别介绍一下，让大家有一个具体的感受。

第一个叫 MHCflurry。这是一个预测免疫系统如何识别蛋白质片段的工具。说得更技术一点，MHC 分子是免疫细胞表面的一种蛋白质，它的工作是把细胞内部的蛋白质片段，也就是所谓的「肽段」，展示给免疫系统，让免疫系统判断这个细胞是不是有问题。MHCflurry 就是预测 MHC 分子能不能有效展示某个特定肽段的概率，这个预测在癌症疫苗和免疫疗法的研发里非常重要。这类计算量很大，随着数据量增加需要持续优化性能。团队用 agent 帮助做了性能改进，而且改动最终被合并回了原始项目的上游仓库。这一点后面我会专门展开。

第二个叫 cyvcf2。这是一个处理 VCF 格式文件的工具。VCF 是变异调用格式的缩写，是基因组学里记录基因变异的标准文件格式，在人类遗传学和精准医疗研究里几乎无处不在。cyvcf2 的改动同样被合并回了上游项目。

第三个叫 rustar-aligner。这是一个基因序列比对工具，情况比前两个更复杂，因为原来的项目已经被废弃了，没有活跃的维护者。于是团队用 agent 帮助做了改进之后，把新版本移交给了新的社区维护者来接手。

这三条路径，合并回上游、项目依然存续并持续更新、由新的社区接手废弃项目，构成了文章里描述的几种典型处置方式。我个人觉得这个分类非常有实操价值。

好，现在我们来讲文章里最核心的五个发现，这也是我觉得对大家最有参考价值的部分，我会逐一展开讲。

第一个核心发现：研究者的角色发生了根本性的转变，从「实现者」变成了「协调者和验证者」。

文章里有一句话说得非常精准，所有贡献者都描述了一个一致的转变：研究者的工作不再是亲手实现代码，而是转向了验证和协调，也就是明确要构建什么、定义如何衡量正确性、以及决定什么时候项目可以发布。研究者仍然掌控着科学方向和质量标准，但实现速度由 agent 的辅助来提供。

这个转变听起来很美好，但我想帮大家把它想得更具体一点，因为这里面有一个微妙的认知陷阱。

假设你是一个基因组学实验室的博士后，你现在要优化一个序列比对算法。传统的方式是：你查文献，理解算法原理，然后动手写代码，写着写着踩了一个 bug，调了好几天，最后性能还是不够，再重构一遍，前后可能花几周甚至几个月。整个过程你是主力，代码从你的脑子里长出来的。

有了 agent 之后，你的工作变成了：你向 agent 描述需求，agent 很快给你一个初步实现。然后你的工作是：这个实现对不对？在相同输入下，它的输出和原来的工具一致吗？在边界情况下有没有数值上的偏差？这些判断都必须由你来做。

表面上看，你的工作变「轻」了，因为你不用再亲手写每一行代码。但实际上，你的工作变得更需要「清醒的判断力」，因为你必须比以前更清楚地知道「正确」长什么样，才能评判 agent 的输出是否达标。你的工作从「产出代码」变成了「定义标准、设计测试、做最终裁判」。

这让我想到软件工程里的一句老话：写出好的测试比写出好的代码更难，因为你必须在写测试之前先搞清楚正确答案是什么。在 agent 时代，这个道理被放大了很多倍。

第二个核心发现：agent 经常在错误时表现出过度自信，这是整篇文章里最值得警惕的一点。

文章明确说，agent 往往无法可靠地判断它的工作是否科学上有效，或者是否符合预期。而且，即使 agent 的工作里包含明显的错误，agent 也经常表现得非常有把握，很肯定地告诉你这是正确的。

你能想象这有多危险吗？如果是在写一个普通的 web 应用，agent 写错了，用户会反馈，bug 暴露出来，你可以修。但在科学计算里，一个数值上的细微偏差，可能导致整个下游分析的结论出现偏移，而你在最终报告出来之前根本不知道是在哪一步出了问题。更严重的情况是，如果一篇发表的论文依赖了有问题的分析代码，这个错误可能在被其他人引用无数次、并且影响到很多后续决策之后才最终被发现。科研里的「错误繁殖」成本极高。

所以文章特别强调，最有效的验证方式必须建立在外部参考或者可以客观衡量的验收标准上，不能靠主观感受。具体来说，文章里提到了四种方法，实践中被反复使用：

第一种是输出完全一致性检查。agent 改写或优化的代码，在完全相同的输入下，必须给出和原来代码完全相同的输出。一个数字都不能差，哪怕是小数点后第八位的差异都需要解释清楚。这种方法最严格，但也最可靠，尤其适合做代码迁移和性能优化这类「等价重写」的任务。

第二种是与现有工具的结果对比，就是用另一个独立实现的、已经被验证过的工具做参照，两个工具在同样输入下的结果应该在合理误差范围内一致。这个方法的前提是有一个可信的参照物，但在科学领域，往往存在这种「金标准」实现。

第三种是统计行为的合理性检验。比如检验输出结果的分布是否符合预期的数学性质，是否存在不应该出现的系统性偏差，随机模拟出来的数据是否能得到符合理论预期的结果。这种方法更灵活，适合没有精确参照物的情况，但需要你对领域知识有足够的理解。

第四种是用模拟数据预先建立正确答案库。在开始让 agent 实现任何东西之前，先用模拟数据生成一批已知正确答案的测试样本，然后把验证 agent 实现是否能复现这些答案作为验收标准。这个方法的优点是可以覆盖真实数据里不常见但重要的边界情况。

这四种方法有一个共同的核心思想：把「正确」定义为一个可以客观测量的东西，而不是让人用直觉去判断。这在用 agent 辅助科学计算时，是非常关键的设计原则，我个人认为这套方法在任何需要高可靠性的代码重构场景里都可以直接套用，不只是科学计算。

第三个核心发现：迭代式推进比一次到位的方式可靠得多。

文章里所有的团队都描述了类似的工作节奏：不是一开始就给 agent 一个宏大的任务然后等它交付完整方案，而是把大目标拆解成一个个小的、范围明确的子任务，每完成一步就用中间基准和测试系统来评估，然后根据评估结果来调整下一步的方向。

为什么需要这样做？因为 agent 在处理大范围、开放性的任务时，很容易偏离你真正想要的方向，而且你很难在最后才发现偏差已经积累了多深。把任务切成小块，每一块都有明确的验收标准，你能在早期就发现问题，成本低得多。

而且，迭代的节奏还有一个好处：它让你作为「协调者」能够保持对整体方向的掌控。每次迭代之后你都要重新审视：现在在哪儿、下一步应该做什么、整体目标有没有偏移。这种持续介入本身就是在保证科学方向的正确性。

第四个核心发现：「最后一英里」往往是最费时间的部分。

这一点值得单独讲，因为它非常反直觉，很多人在用 agent 的时候会被它的初始速度误导。

文章里提到：agent 通常能很快地给出一个初步实现，但把这个实现从能跑、大致正确，提升到真正可以发布的生产级别，这个过程才是最耗时的部分。解决边界情况、处理数值上的细微差异、适配各种真实数据里的特殊情况，这些加起来往往需要比生成初始实现多得多的时间。

这个规律背后有一个深层原因。agent 在生成初始实现时，主要处理的是主流路径，也就是正常输入、正常情况下的逻辑。这部分通常是算法核心，agent 能处理得不错。但科学计算里有大量的边界情况是真实数据里才会遇到的：序列数据里有缺失碱基怎么处理、数值计算遇到接近零的分母怎么办、特殊的基因型编码格式怎么兼容、某类统计量在样本量极小时的数值稳定性怎么保证，等等。这些情况在设计文档里往往没有被明确提到，在常规的单元测试里也不一定覆盖到，但一旦遇到，计算结果就可能完全跑偏。

所以文章给出的一个很重要的经验是：在项目规划阶段，不要按照「agent 能快速出初始实现」的速度来估算整个项目的工期。验证、修复边界情况、反复迭代的时间往往比生成初始实现的时间长很多，这部分时间必须在计划里留足。

第五个核心发现：长期维护的责任不能被 agent 替代，这是整篇文章里我觉得最具有前瞻性的判断。

文章里有一段话我觉得非常精准，值得仔细想一想。文章说，降低实现成本也让生产大量类似的重写版本变得更容易，这会让用户群体碎片化，分散了维护任何单一工具所需的专家注意力。这使得长期的维护责任和归属认定变得至关重要。成熟的科学软件携带着大量未文档化的约定、兼容性要求和用户信任，这些是单纯翻译源代码所无法复现的。

我来把这段话说得更直白一点。

在 agent 出现之前，重写一个科学计算工具需要大量的工程资源，只有极少数有动力且有能力的团队才会去做。这种高门槛反而起到了一种「自然过滤」的作用，保证了每个被重写的工具都是认真对待的。

现在，有了 Codex 这样的 agent，一个小团队可以在几周内完成原来需要几年工程工作才能完成的重写。这是好事，但它同时意味着：十个不同的团队可以各自重写同一个工具，产生十个版本。用户不知道该用哪个，每个版本背后的团队可能都没有长期维护的意愿和资源，最终的结果是，科学界出现了十个孤儿代码库，而不是一个被认真维护的健壮工具。这是一种纯粹的资源浪费，而且会让整个生态更加混乱。

还有一个更深层的问题：文章说，成熟的科学软件携带着大量「未文档化的约定」。这是什么意思？

你可以用 agent 把一个工具的全部源代码从 Python 二迁移到 Python 三，或者从 Python 迁移到 Rust，功能逻辑全部复现。但那些埋在历史版本里的行为——某个特定的输入格式处理方式、某个平台上的数值精度选择、某个版本之间为了向后兼容而保留的特殊逻辑——这些都不在源代码的主逻辑里，它们散落在 issue 的讨论记录里、在老用户的使用惯例里、在早期维护者脑子里的隐性知识里。如果你的新版本在这些细节上和老版本行为不一致，科研结果的可重复性就可能出现问题，而且这类问题往往很难被发现，因为没有人会想到去对比这些边缘行为。

所以文章给出了明确的建议：如果能和现有的维护者协调，就应该尽早开始，让改动合并回上游项目，而不是另起炉灶建一个分支。如果确实需要建立独立的新实现，就必须在一开始就明确谁来负责、有没有可信的长期维护计划。没有这些，今天的现代化重写可能就是明天的废弃代码，而不是科学基础设施的改善。

好，说完这五个核心发现，我还想谈一个贯穿全文的底层逻辑：工程瓶颈正在被打破，但瓶颈本身没有消失，只是移动到了别处。

文章最后说的一句话我很认同：这些案例表明，现在编程 agent 已经能加速科学计算的迭代节奏了。随着 agent 能力的持续提升，研究者将能够把更少的时间花在维持分析流程运行上，把更多的时间放在真正推进领域进步上。

但瓶颈现在在哪里？文章说得很清楚：是验证 agent 的输出，而这仍然依赖人类判断。

换句话说：以前的瓶颈是工程实现能力，你没有足够的工程师，你的科研团队没有时间和能力把代码做好。现在 agent 把这个瓶颈显著降低了。但验证的瓶颈——判断代码是否科学上正确、边界情况是否被妥善处理、长期来看谁来负责维护——这个瓶颈仍然存在，而且因为代码产出量增加了，需要被验证的东西也更多了，在某种意义上这个瓶颈反而变得更突出了。

这是一个很典型的「技术进步转移约束」的模式：效率工具提升了产能，把约束从一个地方移到了另一个地方，接下来需要做的是在新的约束点上投入精力。

好，我们来聊实践层面，对你的实际工作意味着什么。

如果你是一个工程师或者研究员，现在考虑用 Codex 或者 Claude Code 来做类似的工作，不管是科学计算领域还是其他技术领域的代码现代化任务，文章给出的这些经验直接可以拿来用。

第一条，在启动任何 agent 辅助的开发工作之前，先想清楚「正确」的定义。你怎么知道 agent 交给你的代码是对的？你的验收标准是什么？是输出完全一致性比对、还是与参考工具的结果对比、还是统计行为检验、还是用模拟数据建立正确答案库？如果你在开始之前说不清楚验收标准，你在最后也不可能说得清楚什么叫「完成了」。这个工作需要在给 agent 第一个任务之前就做好，而且它是你最重要的工作，不是 agent 的工作。

第二条，把大任务拆小。不要把「把这个工具用 Rust 重写」这种宏大目标整个丢给 agent，而是先定性哪个模块是最关键的性能瓶颈，先让 agent 重写这一个函数，验证这一个函数在覆盖测试下输出一致，然后再继续下一个。每个小步骤都有明确的验收标准，问题就能在早期暴露，而不是等到最后发现整个方向偏了。

第三条，给「最后一英里」留足时间。文章里的经验非常一致：agent 能快速给出初步实现，但处理边界情况、达到真正可发布的水准，这部分时间往往比你预期的长得多。一个粗略的经验法则是：让 agent 做初步实现可能需要一天，但后续的验证、修复、打磨可能需要一周甚至更长。在项目计划里，要给后半段留出比前半段更充裕的时间。

第四条，从项目第一天就想清楚维护问题。这份代码最终谁来负责？能提 PR 合并回上游项目最好，这样维护责任和用户基础都是现成的。如果不行，需要建立新的代码库，就必须明确有没有一个人或者一个团队愿意并且有能力长期负责。没有明确维护者的代码，不管写得多好，都是一个定时炸弹。

第五条，不要轻信 agent 的自信程度作为质量信号。文章里反复强调这一点：agent 在错误时表现得和正确时一样有把握，有时候甚至更肯定。所以你的验证流程必须是系统性的、客观的，而不是基于你对 agent 输出的「感觉」。「agent 说这个实现是正确的」不是一个验收依据，只有你自己设计的测试系统说它是正确的，才算数。

我个人还有一个延伸的观察：这篇文章描述的模式，其实不只是科学计算领域独有的，它对任何历史包袱重、工程人手少、代码质量参差不齐的领域都有直接的参考价值。企业里大量老旧的内部系统、开源社区里被遗忘的基础工具，都面临类似的处境。文章里那套「明确验收标准、迭代推进、重视最后一英里、想清楚维护归属」的原则，可以直接搬到这些场景里用。

同时，文章里也暗含了一个值得思考的技术民主化悖论。在过去，能做出高质量科学计算工具的团队，必须同时具备很强的领域知识和工程能力，这种复合型人才非常稀缺，自然形成了过滤机制。现在 agent 把工程实现的门槛大幅降低，更多的团队能产出像样的代码，这当然是好事，但同时也意味着同类工具的数量会增加，社区的注意力会被分散，没有哪一个工具能获得足够的维护资源来变得真正可靠。门槛降低了，但协调成本上升了。这个张力没有简单的答案，但是一个值得所有参与者意识到的系统性风险。

好，最后我们来做一个总结。

这篇发表于二零二六年七月二十八日的田野报告，记录了八个团队用 Codex 和 Claude Code 改善科学软件的实战经验。核心结论是：agent 确实能显著加速科学软件的开发和维护，帮助小团队完成以前需要大量专业工程支持才能做到的事情。但 agent 无法自主判断科学上的正确性，研究者的角色从「实现者」转变为「协调者和验证者」，而这个验证工作需要更清晰的标准、更系统的方法。最后一英里的打磨往往最耗时间，而长期的维护责任和社区归属，仍然必须由人来承担，这一点 agent 帮不了你。

我个人认为，这篇文章最大的价值不在于它宣告了什么令人惊叹的突破，而在于它把「用 AI 做工程」这件事从概念层面拉到了操作层面，给出了可以直接参考的失败模式和解决方案。这种踏实的田野报告，在当前这个 AI 能力快速迭代、各方都在摸索最佳实践的阶段，比任何宏大叙事都更有参考价值。如果你正在考虑用 AI agent 来做代码现代化工作，不管在什么领域，这篇文章都值得认真读一遍。
