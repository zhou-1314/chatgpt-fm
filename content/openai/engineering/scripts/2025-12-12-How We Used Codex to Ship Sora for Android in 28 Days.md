好，时间背景交代完，我们来正式进入这篇文章的内容。

Sora 是 OpenAI 的视频生成产品。你输入一段文字描述，它给你生成一段逼真的视频。二〇二五年，Sora 先在 iOS 平台发布，结果上线即爆火，用户蜂拥而至，视频生成请求把服务器打得满满当当。iOS 一发出来，下一个问题就摆在眼前了：安卓那边怎么办？

安卓平台在全球智能手机市场占据了超过七成的份额，已经有大量用户在 Google Play 上预注册，在等待安卓版上线。但那时候团队手里只有一个小小的内部原型，距离一个可以公开发布的生产级应用，差距还很远。

面对这种高压、时间紧迫的发布任务，很多大公司的本能反应是：加人。大量招募工程师，三班倒，用人海战术来解决时间问题。但 OpenAI 的团队做了一个反常识的决定。他们没有加人，反而组建了一支只有四名工程师的精锐小队，然后每个人都配上 Codex，用二十八天，从原型到全球上线，把 Sora 安卓版做出来了。

结果是什么？上线当天登顶 Google Play Store 榜首。上线后二十四小时内，安卓用户生成的视频超过一百万条。应用的崩溃率只有千分之一，换句话说，无崩溃率高达百分之九十九点九。对于一个在如此高压的时间线下赶工出来的应用，这个质量指标相当罕见。

他们为什么选择四个人而不是四十个人？文章里引用了一位叫弗雷德·布鲁克斯的美国计算机架构师的观点。布鲁克斯在一九七五年写了一本书叫《人月神话》，书里有一个著名的论断：向一个已经延期的软件项目再增加人手，只会让它更晚完成。这个规律后来被称为布鲁克斯法则。

原因是什么？因为每增加一个人，就会增加沟通成本、任务碎片化的程度、以及代码集成的摩擦。新人需要时间上手，老人需要时间带新人，在整个团队里跑通一个决策需要更多的会议和协调。当人多到一定程度，这些协调成本反而会超过额外人力带来的产出收益。

OpenAI 的团队没有无视这个法则，而是把它变成了行动的指针。既然加人有边际成本递增的问题，那就用 Codex 来放大每一个现有工程师的产出，而不是靠人海战术。这背后还有一个额外的好处：人少，沟通成本低，决策速度快，团队可以保持高度的一致性和执行效率。

要用好 Codex，首先得搞清楚它的能力边界——它在哪些地方很强，在哪些地方需要人来补。

文章里的团队给出了一个很好的类比：把 Codex 当成一位刚加入团队的资深工程师来对待。这个比喻非常有帮助，因为它同时包含了高期望和现实的局限。一个刚入职的资深工程师，技术能力很强，但他不知道你们团队的历史决策，不了解产品背后的真实用户行为，也没有内部的隐性知识。你没法直接把任务扔给他就走，你需要花时间告诉他做事方式，给他看范例，帮他建立上下文。Codex 也是一样。

文章列出了 Codex 不擅长的四件事。

第一，Codex 不擅长推断你没有明确告诉它的东西。你的团队偏好什么样的架构模式，你们的产品策略是什么，真实用户的行为习惯是怎样的，内部有哪些约定俗成的捷径——这些东西 Codex 不会自动知道，你必须主动传递给它。

第二，Codex 看不见 app 实际运行的样子。它无法打开一台设备，感受某个页面的滑动是不是有延迟，判断某个交互流程是不是让用户觉得困惑。这种来自感知和体验的判断，只有人能做。

第三，每一个 Codex 会话都需要单独进行上下文传递。你不能假设它自动知道你们团队的做事方式。每次开启新会话，你都需要把目标、约束条件、偏好的做法清楚地传递给它。

第四，Codex 在做深层架构判断时容易出偏差。如果你不加引导，它可能会在本来应该复用现有 view model 的地方新建一个；或者把本来应该放在 repository 层的业务逻辑，塞进了 UI 层。简单解释一下这里的概念：view model 是连接数据和界面的中间层，repository 是管理数据来源的层，UI 层是直接展示给用户的界面代码。把逻辑放错层，代码在功能上可能没问题，但维护起来会越来越困难。Codex 的本能是让代码「能跑起来」，而不是「长期可维护」。

那么 Codex 擅长的是什么？文章列了六个方面，我一一来说。

第一，快速阅读和理解大型代码库。Codex 对各种主流编程语言都有深刻的理解，这让它在跨语言翻译代码时特别高效——比如把 iOS 的 Swift 代码转成安卓的 Kotlin 代码，能完整保留逻辑语义。

第二，测试覆盖。文章里说，Codex 对写单元测试有着近乎异常的热情。虽然不是每一个测试都深入，但广度够，能有效防止功能回归——也就是新功能改动无意间破坏了旧功能的那种情况。

第三，应用反馈。当自动化测试流程，也就是 CI——持续集成——跑失败的时候，你可以直接把错误日志粘贴到 Codex 的提示词里，让它提出修复方案。这个「日志报错变修复代码」的工作流，Codex 处理得相当利索。

第四，大规模并行运行，而且代码可以被视为「可抛弃的」。你可以同时开很多个 Codex 会话，让它们并行探索不同的实现方案，保留好的，扔掉不满意的。把 AI 生成的代码当成实验品而不是珍贵产出，这种思维方式的转变很重要。

第五，提供新的视角。在做设计决策的时候，可以把 Codex 当成一个头脑风暴的伙伴。文章举了一个很好的例子：在设计视频播放器的内存优化方案时，团队让 Codex 去研究多个视频播放 SDK 的实现细节，它提出了几个工程师自己没时间深挖的方案，最终显著降低了 app 的内存占用。

第六，让工程师聚焦在更高价值的工作上。当 Codex 承担了大量写代码的工作，工程师就有更多时间做系统架构设计、仔细审查代码改动、深度测试产品体验。而且 Codex 本身也很擅长代码审查——它能在代码合并前就发现潜在的 bug，提升整体可靠性。这里的 PR 是 pull request 的缩写，就是提交代码改动并等待审核合并的请求流程。

搞清楚了 Codex 的能力边界，接下来最关键的问题是：怎么组织工作流，才能让 Codex 发挥出最大价值？

文章里有一句我认为是全篇最值得记住的话：「我们不需要告诉 Codex 具体该做什么；我们需要向 Codex 展示，在我们团队里，什么是正确的做法。」

这句话背后的实践是这样的：在大规模让 Codex 写代码之前，团队先自己亲手搭建了整个 app 的基础架构。具体包括：确定架构模式，建立模块化结构，设置依赖注入——这是一种让各个代码组件之间保持解耦、互不依赖的技术——，设计页面导航系统，以及亲手实现身份认证和基础网络请求的完整代码流程。

更重要的是，他们亲手从头到尾写了几个「代表性的功能」。这些亲手写的功能，遵循了他们希望整个代码库都采用的所有规范和惯例。完成这些之后，他们就用这些功能作为参考例子，告诉 Codex：「看，我们就是这么做事的。你后续做其他功能，照着这个来。」

为了让这些规范在跨越不同 Codex 会话的时候都能保持一致，团队大量使用了 AGENTS.md 文件。这是 Codex 的一种配置文件，可以放在代码库的各个目录里，里面写明了这个模块的编码规范、架构偏好、需要注意的事项。相当于给每一个 Codex 会话准备的「员工手册」。不管哪个新会话启动，它都会先读这些文件，从中获取一致的指导。一次写好，反复受益，所有会话都能从中受益。

团队也试过另一条路——直接告诉 Codex：「根据 iOS 的代码，把 Sora 安卓版给我做出来，开始。」结果 Codex 确实生成了一些代码，技术上能编译，但产品体验很差。没有清晰的架构边界，没有现成的参考范例，Codex 的单发炮式输出是不可靠的。就算不用 AI，合并数千行没有充分审查的代码本身就是一件风险很高的事情，更何况是让 AI 一次性生成。

建立了基础框架、有了参考范例之后，Codex 就能在这个有边界的沙盒里高效地独立工作。最终结果是，这个 app 大约百分之八十五的代码是由 Codex 完成的。这个比例非常高，但正因为有一个精心规划的基础架构，这百分之八十五才是可靠的、可维护的，而不是一堆技术债务。团队自己也说，提前建好基础架构，是他们整个项目里最重要的决策之一。

接下来要聊的是他们工作流里的另一个核心环节：规划前置循环。

项目早期，团队踩过一个坑。他们给 Codex 的提示词是：「这是这个功能的描述，这些是相关文件，请实现它。」有时候有效，但大多数时候 Codex 写出来的代码虽然能编译，却偏离了架构目标和设计意图。

所以他们改变了工作流，在执行之前加入了一个「规划前置」的步骤。对于任何有一定复杂度的改动，他们会先让 Codex 去理解现有的系统是怎么运作的。具体来说，让 Codex 读一组相关的代码文件，然后解释这个功能是怎么工作的：数据是怎么从 API 接口，经过 repository 数据层，再经过 view model 逻辑层，最后到达 UI 界面展示给用户的。

然后，工程师会对 Codex 的理解进行纠正和补充。比如告诉它：「你提到的那个抽象其实应该放在另一层」，或者「那个类是专门为离线模式存在的，不应该被这里复用」。经过这个「理解-纠正」的环节之后，工程师才和 Codex 一起制定具体的实施计划。这个计划看起来就像一份迷你版的设计文档：哪些文件需要修改，需要引入哪些新的状态和数据结构，业务逻辑应该按照什么路径流转。只有把计划确定好了，才开始让 Codex 按照计划一步步去实施。

还有一个实用的小技巧：当任务很长、超过了单次 context 窗口的处理限制时，他们会让 Codex 把制定好的计划保存到一个文件里，这样下一个 Codex 会话可以读取这个文件，继续执行同一份计划。context 窗口是指 AI 模型在单次对话里能处理的最大信息量，超出这个限制，模型就记不住前面的内容了。把计划存成文件，就绕过了这个限制。文章里提到，通过这种方式，他们有时候能让 Codex 无监督地连续运行超过二十四小时。

这个规划循环为什么值得花这个额外时间？带来了三个直接好处。第一，它让 Codex 可以长时间无监督运行，因为工程师知道它在执行一个经过检验的计划，不会跑偏。第二，代码审查变得更容易——你可以拿着计划去对照实现，而不是在没有上下文的情况下盯着大段代码变更发呆。第三，出了问题，先排查计划，再排查代码，调试思路更清晰。文章里说，这个动态和「一份好的设计文档给 tech lead 带来的信心」非常相似——你生产的不只是代码，而是支撑共同路线图的代码。

项目进入高峰期之后，并行管理多个 Codex 会话成为了日常。一个会话在做视频播放器功能，一个在做搜索功能，一个在处理错误逻辑，有时候还有另一个在补测试或者做代码重构。文章里说，那种感觉不像是在使用一个工具，更像是在管理一支团队。

每个会话会定期向工程师汇报进展：「这个模块我规划好了，下面是我的方案」，或者「这里有一大段新功能的代码改动，请审查」。每一个都需要你的注意力、你的反馈和你的确认。这和管理几个同时在推进工作的新工程师，感觉出奇地相似。

这带来了一个根本性的转变：开发的瓶颈，从「写代码」移动到了「做决策、给反馈、整合改动」。Codex 不会被上下文切换打断，但工程师会。大量的 Codex 会话在并行推进，而工程师的时间和注意力是有限的，这反而成了整个系统的瓶颈。

文章在这里再次提到了布鲁克斯法则，但换了一个维度来应用：你不能无限增加 Codex 会话，就期待开发速度线性提升——就像你不能一直加工程师就期待项目更快完成一样。每一个额外的「执行手」，不管是人类还是 AI，都会增加协调成本。工程师从独奏演奏者，变成了乐队指挥。速度的提升是真实的，但协调的复杂度也是真实的。

最后一个我想深入讲的技术策略，是跨平台翻译。这也是这个项目里最有创意的工程决策之一。

Sora 在 iOS 上已经有了完整的实现，这个 iOS 代码库对团队来说是一个巨大的优势——它就是安卓版的「活体规格书」。业务逻辑、数据模型、API 接口的调用方式、网络请求的处理逻辑、数据验证规则——这些东西在 iOS 和安卓上本质上是一样的，区别只是实现语言：iOS 用 Swift，安卓用 Kotlin。

文章提出了两个支撑这个策略的原则。第一，逻辑是可迁移的。不管用什么语言写，底层的应用逻辑语义相同，Codex 非常擅长读懂一段 Swift 实现，然后产出一个在行为上等价的 Kotlin 版本，逻辑语义完整保留。第二，具体的代码示例能提供极强的上下文。一个 Codex 会话，如果它既能看到「iOS 是这样实现的」，又了解「Android 项目的架构是这样的」，它的输出质量会远远高于只靠自然语言描述来指导的会话。自然语言总是有歧义，代码是精确的。

他们的做法是把 iOS、后端和安卓三个代码仓库都放在同一个工作环境里，让 Codex 可以同时访问。给 Codex 的提示词类似于：「请读取 iOS 代码里的这些数据模型和 API 接口定义，然后提出一个计划，用我们 Android 项目现有的 API 客户端和模型类，实现等价的功能。」

还有一个小技巧：在用户主目录下的全局 AGENTS.md 配置文件里，他们写清楚了各个本地代码仓库在硬盘上的路径，以及每个仓库是做什么的。这样 Codex 就能自动发现和导航相关代码，不需要在每个提示词里都重新介绍一遍代码库的组织方式。

文章里有一句玩笑话：忘了 React Native，忘了 Flutter，Codex 才是跨平台的真正未来。玩笑背后是一个很实在的洞察：他们通过翻译而不是共享抽象来实现了跨平台开发。Codex 承担了大部分翻译工作，让他们避免了双倍的实现成本。

整个项目耗费了大约五十亿个 token，用的是 GPT 五点一 Codex 模型的早期版本，也就是现在通过命令行工具、IDE 插件或网页版都能用到的那个版本。

好，讲完了这五个核心点，我们来谈谈对你实际工作的意义。这个环节我觉得是最值得你在通勤路上认真记下来的部分。

第一条可以直接拿走的经验：先建脚手架，再放 AI 进来。不要一上来就把整个需求丢给 AI，让它从零搭建。先自己建好架构骨架，亲手写几个代表性的功能，形成参考范例，然后告诉 AI：照着这个来。就像带新同事，先展示怎么做，再让他独立执行。这个投入在项目越大的时候回报越高。

第二条：认真写 AGENTS.md 文件，或者你在用的 AI 工具对应的上下文配置文件。把你的编码规范、架构偏好、需要避免的反模式，都写进去，放在代码库各个目录里。这是成本最低、收益最高的投入之一：一次写好，多个会话、多个时间点反复受益。很多人在用 AI 工具时忽略了这一步，每次都在提示词里重新解释一遍做事方式，这是在浪费自己的时间。

第三条：引入规划前置步骤。面对任何有一定复杂度的任务，不要直接让 AI 去实现，先走一个「理解-纠正-规划-执行」的循环。多出来的这几步看起来费时间，但能大幅降低后期返工的概率，也让代码审查工作更轻松——你可以拿着计划对照实现，而不是在没有上下文的情况下硬啃代码变更。

第四条：学会管理并行的 AI 会话，就像管理一支团队。不同会话可以并行处理不同任务，但你要承担起 tech lead 的角色：分配任务、检查进展、给出反馈、做集成决策。准备好让自己成为系统的瓶颈——这是好事，意味着你在做最高价值的判断工作，而不是在键盘上重复劳动。

第五条：如果你有跨平台的需求，考虑翻译策略。把已有平台上的完整实现作为 AI 的参考输入，让 AI 完成跨语言的语义翻译，而不是让它凭空重新推导逻辑。已有的代码是最精确的规格书。

第六条，最重要：要规避最大的坑——让 AI 在没有约束的情况下自由发挥。没有清晰架构边界、没有参考范例，AI 倾向于生成一个「能跑但难以维护」的系统。AI 的目标是从 A 到 B，现在。而工程师的职责是在考虑未来可维护性、可扩展性、团队协作的前提下，做出有长远价值的架构决策。这两个目标如果没有人来对齐，AI 会一直生产短视的代码。

另一个需要重视的点是代码审查。AI 生成的代码同样需要认真审查，甚至在某种程度上需要更认真的审查——因为你很容易因为代码「看起来不错」就放松警惕，而 AI 生成的代码里的问题有时候很隐蔽。文章里的团队把代码审查当成了核心工作流的一部分，而不是走形式的步骤。

这篇文章里有一个结论，我认为是反直觉的，但非常深刻：AI 辅助开发不是减少了对工程师严谨性的要求，而是提高了。AI 让你能更快地产出代码，但如果你的架构设计能力、系统判断能力、清晰表达意图的能力不够强，AI 只会帮你更快地累积技术债务。未来最有价值的工程师，是那些既有深厚的系统设计能力，又能有效与 AI 长期协作的人。
