好，让我先给大家建立背景。

OpenAI 的模型在推理阶段——也就是在实际帮你回答问题、执行任务的那个时刻——是需要实时去检索相关数据的。这不是一次性的静态配置，而是一个动态的过程：ChatGPT 在思考你的问题时，可能需要检索你的对话历史、你连接的外部知识库、或者你设置的各种数据源。支撑这一切的，是一套可扩展的数据基础设施。

其中有一个关键组件叫 Rockset。Rockset 原本是一家独立的云数据公司，专注于云原生的实时搜索和分析，二〇二四年被 OpenAI 收购。在 OpenAI 的架构里，Rockset 承担着维护一个随时更新的索引的职责：当你在 ChatGPT 里搜索对话记录，或者让助手去查阅你连接的知识库时，Rockset 就是负责快速定位相关内容的那个引擎。它还承担着同步连接器的功能，把外部数据源的更新实时同步到索引里。

Rockset 的执行层是用 C++ 写的。我们都知道 C++ 在性能和内存控制方面的优势：它给程序员提供了对 CPU 和内存的精细控制，能够把运行时开销压到极低，对于大规模数据基础设施来说这些特性非常重要。但 C++ 有一个我们也都知道的代价：它没有 Rust 那样的内存安全保障，也没有 Go 那样的托管内存模型。这意味着应用层的 bug 可能导致程序写入错误的内存地址，进而触发段错误，也就是 segfault，程序崩溃。

几个月前，OpenAI 工程师开始在生产环境里观察到 Rockset 服务出现了一些崩溃。表面上看，这些崩溃有一个共同特征：一个正常的 C++ 函数似乎执行完毕了，但在它准备返回的那一刻，却跳到了一个无效的地址。内核发现指令指针不再指向任何可执行的代码，于是把程序终止了。

工程师们看到了两种不同表现形式的崩溃，而且这两种都非常诡异。

第一种：函数返回到了空指针，也就是 NULL。按理说，栈帧里保存的返回地址应该是调用者的下一条指令地址，但它变成了零。

第二种更奇怪：栈指针寄存器本身出现了八字节的偏移。在 x86 六十四位架构里，这个寄存器叫 rsp，它记录着当前栈的顶部位置。编译器只在函数的入口和出口，也就是所谓的 prologue 和 epilogue 里直接调整 rsp。在函数正常执行的中间，没有任何理由、也没有任何合法的机制会让 rsp 无缘无故发生偏移，除非用了内联汇编、setcontext、longjmp 这类非常底层的机制——而 Rockset 的代码里根本没有用这些。

这不是 C++ 应用代码里典型的 bug 模式。一个随机的野指针写入恰好命中了栈上保存的返回地址，这在理论上是可能的，但概率极低。而 rsp 本身在没有任何底层机制介入的情况下出现偏移，几乎不可能发生。每一个假设——是应用层 bug？是编译器问题？是链接时出了问题？是某个运行时库的 bug？是 Linux 内核在信号投递或上下文切换时触发了奇怪的行为？——都有强有力的证据指向"不可能"。工程师们感觉自己在面对一个不应该存在、但就是在发生的东西。

他们的第一反应是采用传统的调试方式，也就是文章里所说的"医生模式"：深入分析几个具体的 core dump，也就是程序崩溃时内存状态的快照，提出假设，逐一排除。

为了理解他们在做什么，我需要解释两个技术背景。

第一个叫做"红区"，英文叫 red zone。在 Linux 的 x86 六十四位平台上，有一个叫做 System V ABI 的约定，它规定：rsp 以下一百二十八字节的内存区域叫红区，这个区域用户空间代码可以使用，而且内核承诺在投递信号时不会破坏它。这个约定非常重要，因为 Rockset 在崩溃发生后，信号处理函数会在崩溃线程的栈上运行，它使用的栈空间会覆盖那些已经不活跃的旧栈帧。但由于红区的保护，rsp 以下一百二十八字节内残存的信息被保留下来了。工程师们正是利用这些残存的内容，去推断崩溃前一瞬间发生了什么。

第二个背景是 Rockset 编译时使用了一个叫 fno-omit-frame-pointer 的编译选项，意思是不省略帧指针。这意味着每个活跃的栈帧都可以通过 rbp 寄存器找到，所有调用帧形成一个链表，方便调试工具遍历整个调用栈。

即使有了这些条件，调试依然困难重重。他们试图从日志里构建全量的崩溃列表，但崩溃时记录下来的栈追踪本身是损坏的——要么不准确，要么直接缺失——导致日志查询的结果既有误报也有漏报，无法得到一个可信的完整数据集。手工逐个检查 core dump 太费时间，也无法建立全貌。

与此同时，因为他们看到崩溃分散在多个地理区域和多种硬件类型上，工程师们错误地排除了硬件 bug 的可能性。这个决定后来被证明是错的，而且恰恰是因为他们当时已经在无意识地把两个不同 bug 的数据混在一起处理了。

他们把目光转向了 Linux 内核，因为 Rockset 使用信号的频率远高于一般程序。这源自一个自研的机制，叫做 coarse thread cputime clock，我们可以称它为"粗粒度线程 CPU 时间时钟"。

让我解释一下为什么 Rockset 需要这个东西。Rockset 的查询处理被分成了大量轻量级任务，这些任务都复用在同一个线程池上。好处是能高效处理高查询率的工作负载，坏处是很难追踪每个具体查询实际消耗了多少 CPU 时间，因为同一个线程可能在不同查询的任务之间来回切换。

标准的解决方案是调用 clock_gettime 这个系统调用，但这个调用对每个任务边界都调用来说开销太高了。所以工程师们用了一个变通方案：利用 timer_create 这个 API，让系统每隔几毫秒的 CPU 时间就发送一个 SIGUSR 二信号，信号处理函数里更新一个线程局部的计数器。每个具体的任务可能感觉不到时钟前进，但把所有任务的增量累加起来，就能得到对实际 CPU 时间的无偏估计。

这个机制的副作用是：Rockset 进程收到信号的频率非常高，远高于普通程序。工程师们推断，也许有某个极低概率的内核 bug 在信号投递或上下文切换时出了问题。他们去读内核源码、读 Azure 的定制内核补丁、做各种压力测试，但一无所获。

到了这个节点，他们决定换一种根本性的调试思路。

文章里用了一个非常好的比喻来描述这个转变。调试有两种大的范式。一种是医生模式：聚焦在单个病人身上，做大量的检查，从精细的证据里诊断个案，得出结论。另一种是流行病学家模式：着眼于整个病例群体，问那些单个案例无法回答的问题。这个病是什么时候开始在人群里蔓延的？是某个特定地区、特定硬件类型、特定软件版本才会出现？整个看起来像同一种病的群体里，是不是藏着好几种不同的病因？

流行病学家模式的关键前提是：你需要有高质量的、覆盖完整群体的数据。这正是工程师们之前缺少的。

于是他们做了一个决定：投入时间，建立一个能自动分析所有 core dump 的管线。

这里有一个我觉得值得特别说一下的细节：他们用 ChatGPT 来写这个分析脚本。脚本的功能是下载每个 core 文件的前缀部分，提取出寄存器状态，利用日志过滤掉已知的误报，然后把每个崩溃自动分类成"返回到空指针"、"栈指针偏移"，或者"其他"。然后把这个脚本并行跑在过去一年所有生产环境里的 Rockset core dump 上。

这，就是整个调查的转折点。

一旦有了干净的全量数据集，规律立刻就浮现出来了，而且清晰得让人有点惊讶。

"返回到空指针"这类崩溃，散布在很多个集群和地理区域里，最近频率有所上升，但没有一个明确的开始时间，也没有清晰的基础设施边界。它看起来像是随着某种条件逐渐变化而持续恶化的问题。

"栈指针偏移"这类崩溃则完全不一样。它们全部集中在同一个地理区域，有一个非常明确的开始时间，而且从来不出现在已经长时间运行的节点上。虽然涉及多台 Azure 的虚拟机，但整个模式强烈指向：有一台物理机的硬件出了问题，受影响的虚拟机都是碰巧被调度到了那台有问题的物理机上而已。

就在这一刻，工程师们意识到：他们之前一直在把两个完全不相关的 bug 混为一谈，当成同一个问题的两种表现在处理。因为两个 bug 各自的"反例"互相干扰，才导致每一条推断链都无法自洽，才会出现"每个假设都有强有力的证据反对它"的诡异局面。

有了按 Kubernetes 节点和时间戳整理的干净数据，他们很快把"栈指针偏移"的崩溃追溯到了同一台物理主机。这台机器被列入黑名单，不再接受新的工作负载。

他们在受控环境里对这台问题主机做了几周的压力测试，始终无法重现那个寄存器错误。静默硬件错误往往就是这样：不可预测、不稳定、在主动寻找时往往躲起来。但一旦把这台机器下线，栈指针偏移的崩溃就彻底消失了。这是强有力的间接证据，说明那台机器的 CPU 在某些运算上，就是会偶发性地产生错误的结果，没有任何报错，没有任何保护机制能检测到这一点。这就是所谓的静默硬件错误。

这是一个很重要的教训。大家通常把硬件当成一个完全可信的基础假设，bug 默认都是软件的责任。但在大规模的云环境里，物理机数量庞大，总会有一定比例的机器在某个组件上出现静默失效。这不是故障，而是在足够大的机群规模下的统计必然。

工程师们也随即改进了他们的基础设施：在崩溃信号处理函数里加入了更完整的寄存器状态记录，这样下次遇到类似情况，只需要看日志就能检测到，不需要 core dump。他们还调整了控制平面，让虚拟机尽量复用而不是频繁重建，使得在他们自己的基础设施层面检测有问题的节点变得更容易。

好，硬件问题那批崩溃解决了。现在来看剩下的"返回到空指针"这类崩溃。

把硬件问题的案例剔除之后，工程师们重新审视剩余的 core dump，发现之前有一个结论彻底反了。他们曾经排除了"C++ 异常展开"这个假设，理由是他们认为某些崩溃发生在根本没有用 C++ 异常的代码路径里。但现在他们发现，那些所谓的"反例"，全都来自硬件损坏那批崩溃。

把硬件问题的案例剔除之后，剩下的崩溃，全部都发生在 C++ 异常展开的过程中。

我需要在这里给大家仔细解释一下 C++ 异常展开的工作原理，因为这是理解后续内容的基础。

当 C++ 代码抛出一个异常的时候，运行时需要完成一件复杂的事：找到应该接收这个异常的 catch 块在哪里，确定沿途哪些析构函数或者清理处理器需要运行，然后把控制权转移到正确的位置。这个过程叫做"栈展开"。

关键的一点是：这个展开过程不是由抛出异常的那个函数自己完成的，而是由一套专门的运行时辅助函数来做的。这些辅助函数会遍历当前的调用栈，读取编译器预先生成的关于每个函数的元数据，这些元数据遵循一个叫做 DWARF 的标准格式，动态地寻找匹配的 catch 块或者清理处理器，然后把控制权转移过去。

用一个类比来帮助理解：正常的函数调用和返回，就像顺着楼梯一级一级走，调用是下楼梯，返回是上楼梯，每次只走一级。但异常展开更像是乘电梯：你可能一下子从五楼跳到一楼，跳过中间所有的楼层，而且沿途还得把所有应该关上的门都关上——这些"门"就是析构函数和清理处理器。这个过程从操作上来说，更接近于 longjmp 或者协程切换，而不是普通的函数调用和返回。

完成这个跳跃需要恢复一大堆寄存器：不只是指令指针 rip，还包括保存的通用寄存器、栈帧指针 rbp，以及最关键的，栈指针 rsp。

Rockset 的二进制文件链接了两个都包含 C++ 异常展开实现的库：libgcc 和 GNU libunwind。动态链接器最终选择了 GNU libunwind 的实现。这让工程师们有些意外——他们原本预期 libgcc 的版本会因为符号版本规则而胜出，但检查实际运行的进程后发现，事实恰恰相反。

这时候，工程师们的工作假设发生了根本性的转变。

也许他们看到的根本不是"一个普通函数返回到了空指针"，而是"异常展开在恢复寄存器状态、转移控制权的那一刻，目标指令指针已经被损坏成了空指针"。换句话说，不是栈上的正常返回地址槽里被写入了空指针，而是展开库在存储目标寄存器状态时，数据在某个时刻被破坏了。

这个假设把搜索范围一下子缩小了很多：要么 GNU libunwind 计算出了错误的目标寄存器状态，要么它计算对了，但在应用之前被某些东西覆盖掉了。

工程师们仔细读了 GNU libunwind 的源代码，找到了关键的机制。libunwind 在执行展开时，会在当前栈上合成一个叫做 ucontext t 的数据结构，把异常被捕获后应该恢复到的目标寄存器状态填进这个结构体里，然后把这个结构体的指针传给一个内部的汇编函数，叫做 _Ux86_64_setcontext。

这个汇编函数负责实际执行寄存器状态的恢复。文章里给出了它最后六条汇编指令。让我用语言来描述这个过程：函数先从 ucontext t 里读取各个寄存器的目标值，然后依次恢复。其中有一条至关重要的指令：把 ucontext t 里保存的目标 rsp 值，加载到实际的 rsp 寄存器里，也就是把栈指针更新为展开之后的新栈底。

问题就在这里。

一旦 rsp 被更新，那个存放着目标状态的 ucontext t 结构体，就脱离了"活跃栈"的保护范围了。还记得我们之前说的红区约定吗？内核在投递信号时，会在新的 rsp 以下一百二十八字节以内的范围构建信号帧。超出这个范围的旧内存，内核可以随意使用，没有任何保护。

所以竞态条件就这样出现了。_Ux86_64_setcontext 把 rsp 更新成了目标值，但 ucontext t 里还有几个寄存器的值没来得及读，包括最重要的目标指令指针 rip。如果在这个极短的窗口里，SIGUSR 二信号到来，内核会在新的 rsp 位置上构建信号帧，而这个信号帧占用的内存区域，可能恰好覆盖掉 ucontext t 里存放目标 rip 值的那段内存。然后当 _Ux86_64_setcontext 去读目标 rip 时，它读到的是被信号帧覆盖过的值——而信号帧里那个位置的内容，往往就是零。

控制权被转移到地址零，内核把进程杀掉了。

这就是整个崩溃的完整机制。

还有一个细节解释了为什么在 core dump 里看起来像是"函数 X 的返回地址槽里是空指针"。因为 setcontext 这类函数需要恢复所有寄存器，包括 rdi 这个保存着 ucontext t 指针的寄存器。所以它不能在最后一步仍然用 rdi 去读目标 rip。实际的做法是：先把目标 rip 的值读出来，保存到栈的某个位置，然后恢复包括 rdi 在内的其他寄存器，最后用 retq 指令从栈上读取目标 rip 并跳转过去。这个"被特意写入栈上、等待最后读取的目标地址"，在 core dump 里看起来和普通的返回地址槽非常像，但它实际上是展开器专门合成的目标地址，不是调用者留下的正常返回地址。这就是为什么工程师们之前一直以为是"普通的返回地址被写坏了"，而没有往异常展开的方向想。

这个竞态窗口到底有多窄？

字面意义上，只有一条指令那么宽。信号必须在 rsp 被更新之后，但在下一条读取目标 rip 的指令之前到来。在现代超标量乱序执行的 CPU 上，几条简单指令可以在一个时钟周期内并发执行，所以这个竞态窗口大约只有一百皮秒，也就是十的负十二次方秒量级。一百万亿分之一秒。

工程师们看到这个结论的第一反应，和我估计大多数人一样：这也太窄了，这个概率真的能解释每天十几次的崩溃吗？

于是他们做了费米估算。如果竞态窗口是若干纳秒的量级，而 SIGUSR 二每隔几毫秒的 CPU 时间就会到来，那么每次异常展开触发 setcontext 时，中招的概率大约是几百万到几千万分之一。听起来极低，但问题在于：Rockset 把异常作为内部反压控制的核心机制。当某台机器过载时，系统通过抛出异常来实现流量管控，拒绝接受新的写入。一台处于过载状态的主机，每秒可能抛出相当数量的异常。把这个异常频率和每次命中的概率相乘，算出来的平均故障间隔，大约是每台使用反压机制的主机每隔几个小时崩溃一次。在整个机群的规模下，这完全能够解释每天十几次的崩溃频率。

那么这个 bug 为什么是现在才暴露出来？它已经在 GNU libunwind 里存在了十八年，时间可以追溯到两千零八年左右第一个支持 x86 六十四位 C++ 异常展开的版本，从来没有被人注意到。

文章给出的答案非常清晰：崩溃率大约正比于三个因素的乘积——异常抛出的频率、信号投递的频率、以及信号处理函数使用的栈空间大小。

Rockset 在这三个维度上都处于极端情况。异常抛出率高，因为把异常用作了反压控制的核心机制；信号投递率高，因为 coarse thread cputime clock 那套机制；而在今年早些时候，工程师们在 SIGUSR 二的处理函数里加了一个叫 timer_getoverrun 的系统调用，目的是统计被合并的信号数量，让 CPU 时间的估算更准确。这个改动让信号处理函数在栈上占用了更多空间。

最后这个改动，看起来就是压垮骆驼的最后一根稻草。如果信号处理函数使用的栈空间足够小，即便信号在竞态窗口里到来，信号帧构建时使用的内存范围也可能正好到不了 ucontext t 所在的位置，bug 就不会触发。在加入 timer_getoverrun 调用之前，他们从来没有观察到这类崩溃。加入之后，在低负载下崩溃率还算可以接受，但当某些使用场景开始给反压机制施加高压时，崩溃就变得足够频繁，引起了工程师的注意。

换句话说：GNU libunwind 的这个 bug 一直都在，只不过三个因素的乘积，直到最近才越过了让它变得可观测的阈值。

这也解释了一个之前让工程师困惑的巧合：为什么两类崩溃——硬件 bug 和 libunwind bug——都高度集中在同一个函数 DocumentTree 冒号冒号 updateDocument 里。来自 libunwind 的崩溃高度偏向这个函数，是因为每次触发反压机制抛出异常时，这个函数总是活跃在调用栈上。来自硬件问题的崩溃也集中在这里，是因为出问题的那台物理机的机型专门用于批量数据写入，而批量写入的 CPU 时间大部分都消耗在这个函数上。两个完全无关的原因，恰好都指向了同一个函数，完美地制造了混淆，让工程师们很长时间都认为这是同一个问题。

最终的解决方案分两步走。

第一步，立即缓解：把 GNU libunwind 替换成 libgcc 提供的展开器实现。这个替换本身就是一个对大规模多核环境有价值的改进，因为 libgcc 的实现做了很多锁竞争方面的优化工作，在大型虚拟机上扩展性更好。

第二步，根治：工程师们向 GNU libunwind 的上游提交了一个独立可重现的复现器和一个修复补丁，同时也验证了其他展开器实现——包括 libgcc 和 LLVM 的 libunwind——没有类似的问题。这个十八年的 bug，终于得到了一个正式的修复，所有使用 GNU libunwind 的 C++ 程序都会从中受益。

好，现在我们来聊聊这个故事对你的实际工作意味着什么。不管你是做后端服务、平台工程、还是任何需要在生产环境里稳定运行的系统，这篇文章里有几个思路是非常值得带走的。

第一个，也是文章最想强调的核心：在深入挖掘单个案例之前，先把精力放在建立高质量的全量数据集上。这听起来像废话，但在实际的压力下，大家往往会本能地跳进最直观的那个案例，开始深挖。这种冲动是人之常情，但它会把你困在一个被污染的信息框架里。Rockset 工程师花了很长时间才意识到他们在混合两个完全不同的 bug。一旦他们停下来，投时间构建覆盖全量 core dump 的自动化分析管线，问题的结构立刻变得清晰了。

第二个，把流行病学视角作为你调试工具箱里的标配。每次面对一个说不通的 bug，都要先停下来问自己：这个症状背后，会不会其实是两个甚至更多个不同的问题在叠加？能不能按时间、区域、硬件类型、软件版本、配置参数对案例做分层，看看是否存在不同的子群体，各自有不同的规律？

第三个，不要把硬件当成一个永远可信的基础假设。在大规模云环境里，物理机数量庞大，统计上一定会有一定比例的机器出现静默硬件错误。CPU 的计算结果可以是错的，内存可以出现位翻转，这些失效通常没有任何明显的报警。实用的应对方法是：加强崩溃时的寄存器状态记录，让硬件错误更容易从日志里被识别；提高虚拟机复用率，减少频繁重建带来的坏节点检测盲区；在团队的 runbook 里明确写入"静默硬件错误"这个排查方向，不要等遇到了才想起来。

第四个，如果你的系统以非常规的方式使用信号，你需要理解你的 C++ 异常展开库是谁提供的，以及它在高信号率下是否经过充分测试。GNU libunwind 这个 bug 的竞态窗口只有一条指令那么宽，对于大多数系统来说，信号频率低到根本不可能触发它。但一旦你把信号频率提高——比如像 Rockset 这样为了 CPU 时间统计而每隔几毫秒就发一个信号——再叠加上高频率的异常，风险就会线性放大。了解自己的系统在哪些维度上是极端的，是预防这类问题的第一步。

第五个，用自动化放大你的分析能力。工程师们用 ChatGPT 写脚本，把分析任务并行跑在所有历史 core dump 上——这不是什么精密的技术，但它把手工抽样分析变成了全量分析，把整个调查从在迷雾中乱撞变成了有依据地寻找规律。这种思路——快速构建自动化工具来放大分析的覆盖范围——是非常值得培养的工程习惯。

最后来做个总结。

这篇文章记录了 OpenAI 如何追踪和修复 Rockset 服务里两类神秘崩溃的完整故事。一是单台物理主机出现的静默 CPU 硬件错误，导致寄存器状态偶发性地出现随机损坏。二是 GNU libunwind 库里潜伏了十八年的竞态条件，问题出在异常展开恢复寄存器状态的最后几条汇编指令之间，一个只有一条指令宽、大约一百皮秒长的信号竞争窗口。两者之所以长时间纠缠在一起、难以调查，是因为在没有足够好的数据支撑的情况下，工程师们把两个完全不相关的 bug 混成了一个问题来处理，每个假设都有来自另一个 bug 的反例在干扰推断。

最关键的突破，不是某个精妙的汇编层面的洞察，也不是对 DWARF 展开元数据的深度理解，而是一个方法论层面的转变：从医生模式切换到流行病学家模式，先建立高质量的全量数据集，让数据自己揭示问题的结构。修复数据，往往比修复推理更有效。
