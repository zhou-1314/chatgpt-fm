今天要和大家聊的是一篇来自 OpenAI 工程博客的文章，英文标题是 "Improving support with every interaction at OpenAI"，我把它翻译成"让每一次交互都改进支持系统——OpenAI 的工程实践"。这篇文章发表于二零二五年九月二十九日。

在开始之前，我要先给大家一个时效性的提示。从发表到今天，这篇文章已经过去了将近十二个月。在 AI 这个领域，一年是一个相当长的跨度，很多具体的工具和 API 都在不断更新迭代。但在提示时效性的同时，我也想先说清楚为什么今天仍然值得认真读这篇文章。

二零二五年下半年，是 AI agent 技术从实验室概念走向大规模商用落地的一个关键节点。OpenAI 在那段时间相继推出了 Agents SDK 和 Realtime API 等工具，各大公司都在摸索怎么用多 agent 系统来改造传统的客服和运营流程，整个行业处于一种"大家都知道方向，但都还不确定怎么做"的状态。这篇文章，就是 OpenAI 在那个节点上，第一次系统地公开分享他们内部是怎么把自己的工具用于自身支持系统的。它记录的不是假设，不是路线图，而是已经在生产环境里稳定运行的真实系统。放在今天来看，文章里描述的这套 eval 驱动的持续改进模型，已经成了行业里越来越多人认可的方向，但能看到第一批实践者当时的设计思路和决策过程，仍然很有参考价值。

那这篇文章值得花二十五分钟认真听的原因是什么？因为它不是在讲"我们用了 AI 就变快了"这种笼统的话。它在回答一个更难的问题：当你的用户数量是数亿级别，每年的支持请求是数百万条，还在以翻倍的速度增长，你应该怎么从系统设计、组织架构、人员角色这三个维度同时重构一套支持体系，让它不只能应对今天的规模，还能在处理问题的过程中持续变得更好。这个问题的答案，对任何做产品的工程师、对任何在推进客服或运营智能化的团队，都有直接的参考价值。

我们先来搭一下背景。OpenAI 服务的用户规模是数以亿计，每年处理的支持请求是数百万条，而且这个数字每年都在翻倍级增长。你可能会想，大公司有大量客服不就行了吗？但文章里指出了一个很有意思的组合：很多大公司面对的是规模挑战，少数公司面对的是超高速增长挑战，而几乎没有公司同时面对这两者，还一边在构建着那个可能从根本上改变这道题答案的技术本身。这个独特的处境，既给了 OpenAI 强烈的压力去重新思考支持模式，也给了他们得天独厚的工具去把想法实现出来。

传统的支持模式是什么样的？就是队列、工单、吞吐量。用户提交一个问题，打开一个 ticket，排队，有人处理，关单。衡量指标是平均响应时间、工单关闭率、用户满意度评分。这套模式在稳定增长的业务里工作得还不错，但它有一个根本性的缺陷：它是被动的、线性的、不会学习的。一个支持代表今天处理了一个复杂的退款纠纷，这个经验留在他脑子里，不会自动变成下一个代表可以使用的知识，也不会变成产品改进的信号。在规模不大、增长不快的情况下，这种知识损耗是可以接受的；但当规模扩大到数亿用户，这种损耗就会累积成一个真实的系统性风险。

OpenAI 的 Ops 团队的愿景，是把支持从一个"处理事务的队列"，重新想象成一个"持续学习、持续进化的 AI 操作模型"。这两个定位之间的差距，就像让员工背标准话术和让员工真正理解业务并能独立判断之间的差距——执行层面可能看起来差不多，但系统能力的上限完全不同。

文章把这套系统的核心架构归纳成三个模块，英文分别叫做 Surfaces、Knowledge、Evals and classifiers，我把它们翻译成表面层、知识库、评估与分类器。我们一个一个来看。

第一个是表面层。这指的是支持系统被交互到的地方，包括聊天窗口、邮件、电话，但越来越多地还包括直接嵌入产品内部的帮助功能。这个概念看起来直白，背后有一个重要的设计哲学：用同一套底层能力来驱动所有不同的交互渠道。不管用户是通过聊天找你、发邮件找你、打电话找你，还是在产品界面里触发了一个内嵌的帮助提示，背后调用的知识库是同一个，质量评估标准是同一套，模型的调用逻辑也是统一的。这样做有什么好处？当你在某个渠道上优化了某类问题的处理方式，这个优化会自动惠及所有渠道，不需要重复做三遍工。对于一个需要同时维护多个交互渠道的团队来说，这是一个非常实质性的效率红利，而且随着渠道越来越多，这个红利只会越来越大。

第二个模块是知识库。但这里说的知识库，不是那种写一次就放在那儿再也没人更新的静态文档。文章特别强调这是"活的、持续改进的"知识，来源是真实的对话、政策文件，以及各种上下文信息。你可以把它想象成一个有版本控制的、会持续生长的维基百科。每次一个真实的对话产生了一个新的洞察，这个洞察就有机会被整合进知识库，影响未来所有类似问题的处理方式。一个企业客户的对话里发现的规律，可以变成开发者常见问题的更新；一个反复出现的用户投诉，可以成为产品设计改进的输入。这个从对话到知识、再到更好的对话的循环，是整套系统能够自我进化的关键基础。

这里还有一个非常关键的设计：知识库不是由工程师或者产品经理单独来维护的，支持代表在日常工作中就在直接向知识库贡献内容。这一点非常重要，因为支持代表是距离用户最近的人，他们最先看到新出现的问题类型，最先感知到哪些答案已经过时了，哪些场景还没有被文档覆盖到。让他们成为知识库的直接贡献者，而不是把信息通过漫长的沟通链传递给某个中心化的知识管理团队，是让知识库保持新鲜和准确的核心机制。

第三个模块是评估器和分类器，英文叫做 Evals and classifiers。这可以说是整套架构里技术含量最高、也最容易被低估的部分。

Evals 要解决的核心问题是：你怎么定义"一个好的支持回答"？这个定义不能只停留在模糊的感觉上，它必须被量化，必须能被程序自动检测，否则你没有办法在大规模的生产环境里持续地测量和改进质量。文章里说，evals 不只是在检测系统有没有解决问题，还在检测回答是不是礼貌的、是不是清晰的、是不是前后一致的。这几个维度加在一起，才是"好的支持回答"的完整定义。而且这些 evals 不是写完之后就存着备查的，它们在生产环境里持续运行，不断对模型的实际行为进行评分和反馈。这相当于给整个系统装了一套在线的、实时的质量监控流水线，而不是只在上线前做一次测试就完事儿。

分类器的作用是什么呢？我来举一个具体的例子帮你理解。当一个新的问题类型开始出现，比如用户开始大量询问某个最近上线的新功能怎么用，支持代表发现了这个趋势之后，可以提议甚至亲手创建一个新的分类器，来自动识别并且路由这类问题。这个过程不需要等工程师排期，代表自己就能做到。在以前的模式里，你发现一个新的问题类型，要写需求文档、提交给产品经理、进入排期、等工程师实现、测试、上线，整个周期可能要两个月。在这个新模式里，代表几天内就能完成。这是一个非常实质性的赋权，它大大缩短了系统适应新情况的响应时间，相当于把一个以月为单位的反馈周期压缩到了以天为单位。

这三个模块最重要的地方，不是它们各自单独的功能，而是它们之间形成的循环。文章用了"loop"这个词，这个反馈循环是整个架构的灵魂所在。

我来用一个大家熟悉的工程类比帮你理解它。在软件开发里，我们有 CI/CD 流水线：代码提交之后，自动测试跑起来，测试通过才能部署，部署之后有监控，发现问题就回到代码修改。这个流水线让每一次代码变更都有快速的反馈，让整个系统在迭代中越来越稳定。OpenAI 这套支持系统做的，是把这个理念搬到了支持和知识管理领域：一次用户对话发生，模型给出回答，evals 对这次回答进行评估，不够好的地方被标记和分析，知识库或者模型行为得到更新，下一次类似的对话表现更好。这个循环跑得越快，覆盖的场景越全，整个系统进化的速度就越快。

文章里说，一个从企业对话里发现的模式，可以影响开发者的常见问题；一个为某个特定案例写的 eval，可以让成千上万个类似案例的处理质量同时提升。这背后的逻辑是：支持系统不只是在解决眼前这个用户的问题，它积累的每一个数据点，都在为整个系统的下一次迭代提供原材料。从这个角度看，每一次对话不只是成本，它也是投资。而这两件事同时发生，系统就有了复利增长的条件。

你可能会问：听起来很美，但要让这个循环真的跑起来，最难的地方在哪里？我个人认为，最难的地方不是技术，而是激励机制的设计。你怎么让支持代表愿意主动去标记一个应该成为测试用例的对话？怎么让他们觉得贡献知识库是自己工作的一部分，而不是额外的负担？这个问题文章后面在讲组织变革的时候有回答，我们一会儿展开。

现在我们来看技术实现层面。文章说，这套系统之所以能建成，很大程度上是因为 OpenAI 直接用了自己的技术栈，文章列出了四个关键组件。

第一个是 Agents SDK。这是专门用来构建多 agent 系统的开发工具包，它给的核心能力是步骤级别的追踪和可观测性，而且这个功能是默认开启的，不需要额外配置。什么意思呢？当一个 AI agent 在处理一个用户问题的时候，SDK 会自动记录每一个步骤：调用了哪个工具、工具返回了什么、模型做了什么判断、最终输出了什么。这让工程师可以在系统出问题的时候重放整个运行过程，定位到具体是哪一步出了问题。这个能力在调试复杂的多 agent 系统时极其宝贵。如果你没有步骤级别的追踪，当系统给出了一个错误的回答，你很可能根本不知道该从哪里开始查，只能靠猜测，这在生产环境里是非常危险的状态。可观测性不是可选的锦上添花，它是让系统能够被改进的前提条件。

第二个是 Responses API，它被用来驱动语气、正确性、政策合规性这些维度的分类器。这个 API 允许你把模型的输出结构化成你想要的格式，这对于构建自动化的评估流程非常有用。你可以让模型不只给出一个回答，还同时输出一个结构化的评估结果，比如这次回答在礼貌性、准确性、政策合规性各个维度上分别的情况，然后这个评估结果可以直接进入 evals 流水线，驱动下一轮的改进。

第三个是 Realtime API，它让语音电话支持成为可能。实时语音支持的技术难度比文字支持要高得多，需要做语音识别、实时推理、语音合成，而且整个链路的延迟要控制在非常严格的范围内，稍微一卡顿，对话的体感就会急速下降，用户体验会比完全没有语音支持还要差。Realtime API 把这些复杂的底层技术都封装好了，让上层的应用开发者可以专注于业务逻辑，而不是底层的技术细节。

第四个是 Evals 仪表板，它让质量随时间的变化变得可见。这个工具的意义，不只是看某一个时间点的质量状态，而是让你能看到趋势：上周部署的一个模型更新，是让整体质量提升了还是下降了？某一个渠道的表现和其他渠道相比怎么样？哪类问题的处理质量最不稳定？这种时序的可视化，是驱动持续改进文化不可缺少的工具，因为没有人会花力气去改进他们看不见的东西。

文章里说，因为这些基础组件都是现成的，他们可以把更多精力放在真正重要的事情上：定义什么是好的、测量它、改进它，而不是把时间花在把不同系统拼接在一起这件事上。这是一个很有价值的设计启示：当你在选技术栈的时候，一个原生支持可观测性和 evals 的平台，可以帮你省下大量的基础设施搭建时间，让你能更快地聚焦在业务本身。

文章还描述了这套系统是怎么一步一步演进的，这个演进路径本身也很有参考价值。他们最开始从一个简单的问答系统起步，用户问、AI 答，能解决一批常见问题。这个阶段系统比较简单：问题进来，检索知识库，生成回答，回答出去，一条线走完。这个阶段的价值在于验证了基本方向，积累了第一批 evals 和真实的对话数据。

随着 Agents SDK 的引入，他们开始扩展到动态行动，也就是那些不只是回答问题、而是需要真正执行某个操作的场景，比如处理退款、查询发票、查找事故工单。这个扩展说明了一个重要的架构选择：从一开始就把"理解和回答"和"执行操作"作为两种不同的能力来设计，用 agent 的方式来组织这些能力，这样当模型能力提升了，或者有新的工具可以用了，你可以直接在现有架构上叠加新能力，而不需要从头重写系统。

文章提到，随着模型的上下文窗口越来越大、Deep Research 功能越来越强，他们可以立刻把这些进步应用到系统里，这是"建在正确的平台基础上"的复利：平台每进步一次，你的系统自动受益，不需要额外的迁移成本。

现在到了我认为整篇文章里最有洞见、也最容易被技术导向的读者跳过的部分：组织变革。支持代表的角色正在从"问题处理员"转变成"系统建设者"，这不是一个小的调整，而是对整个角色定位的根本性重构。

以前，支持代表的工作是处理工单、回答问题、关闭 ticket，绩效指标是每天处理多少条、用户满意度评分多少。这是一个高度事务性的角色，执行的是预先定义好的流程，对系统本身几乎没有影响力。

在新模式下，支持代表被期待做的事情要多得多。他们要标记那些应该成为测试用例的对话——某次对话的处理方式特别好，或者特别差，都值得成为 evals 的一部分。当他们发现新的问题模式出现时，要能提议甚至亲自创建新的分类器。他们还可以快速原型化一些轻量的自动化流程，来填补日常工作里发现的流程漏洞，而且文章说这些事几天之内就能做到，不需要等工程师排期。

文章里有一句话道出了这种转变的核心，翻译过来大概是："支持 agent 不只是在回复工单，他们在影响我们的知识库和政策，他们有一个我们没有的、最接近用户第一线的耳朵。"这里的 agent 是一个精妙的双关，既指支持代表，也指 AI agent，因为在这个新模式下，人和 AI 在做类似的事情：处理问题，同时向系统反馈，共同驱动系统的进化。

这种转变之所以能发生，有几个关键的前提条件。第一是工具层面的赋权，Agents SDK 和 Evals 仪表板这些工具要足够易用，支持代表在没有深厚工程背景的情况下也能上手。第二是文化层面的认可，代表贡献的每一个 eval、发现的每一个问题模式，要被记录、被看见、被纳入绩效，而不是被视为理所当然的无偿劳动。第三是培训模式的变革，以前的培训主要讲政策和标准话术，现在要包括怎么评估对话质量、怎么识别系统性的漏洞、怎么有效地把改进建议反馈回去。这三个条件缺一不可，少了任何一个，这套模式都很难真正运转起来。

领导层在招人的时候也开始寻找一种新型人才：一个能把一线用户同理心和系统设计直觉结合起来的人，既有支持工作的经验和对用户痛点的敏感度，又有优化系统的好奇心和工程思维。文章的原话是"我们开始看到深度专业技能和深度工程技能的联姻，这就是未来部门运作的方式。"这是一个很大胆的预判，说的是未来的工作单元不再是纯粹的业务部门或者纯粹的技术部门，而是两种能力深度融合的混合单元，每个人都既有业务场景的直觉，又有工程思维来优化系统。

在很多公司里，支持团队和产品工程团队是两条完全平行的线，互不打扰。文章描述的模式，相当于要在这两条线之间建一座桥，而且这座桥不是靠少数几个接口人来维护的，而是靠整个支持团队的每一个成员来承载的。这需要从招人、培训、绩效考核到日常工作流程进行全面的重新设计，是一个真正的组织工程问题，不比技术架构问题简单。

好，理解了 OpenAI 的这套模式，我们来想想它对我们自己的工作有哪些具体的启发。

如果你在一家做产品的公司，想要推进客服或者运营的 AI 智能化，这套架构给了我们几个值得认真考虑的设计原则。

第一个原则：把 eval 驱动的质量文化建立在规模扩张之前。很多团队在构建 AI 支持系统的时候，第一个问题是"我们什么时候能上线"，但更重要的问题是"我们怎么知道系统是不是真的在变好"。如果你没有办法量化质量，你就没有办法系统性地改进质量。有一个非常现实的问题：你越晚建立质量评估体系，积累的技术债越多，往后修正的成本就越高，因为你的系统已经在一个模糊的方向上运行了很长时间，沉淀了很多基于错误假设的内容。所以在做系统设计的时候，把 evals 的设计和数据采集机制放在比模型选型、比界面设计更优先的位置。这是整套架构给我们最重要的一课。

第二个原则：把知识库当成需要持续维护的核心工程资产。很多公司的帮助文档，是某个产品经理入职第一周写的，之后就再也没人碰过。这样的知识库训练出来的 AI，就是一个能更快地给出过时答案的系统，结果可能比没有 AI 还要糟糕，因为用户会以为 AI 给的答案是权威的。真正有价值的知识库，需要有一个机制来识别哪些内容已经过时、哪些新出现的问题还没有被覆盖、哪些答案在真实对话里的命中率最高、哪些答案经常被用户追问说明没有真正解决问题。这个机制没有办法靠人工手动来完成，只能靠系统来驱动。

第三个原则：尽可能用同一套底层逻辑覆盖所有交互渠道。如果你的聊天机器人、邮件自动回复、知识库搜索背后用的是三套各自独立的系统，每次你想做一个改进，就要在三个地方同时做，这是一个很大的维护负担，而且很容易出现三个渠道给出相互矛盾的答案的情况，这对用户信任的损害比没有 AI 还要大。在做架构设计的时候，把核心的知识检索逻辑、回答生成逻辑、质量评估逻辑抽象成独立的服务，让不同的渠道都调用同一套服务，改一次，处处受益。

第四个原则：给一线人员真正的赋权，而不只是给他们一套工具。这里有一个非常常见的错误：你给了支持团队一个 evals 仪表板，但没有给他们任何激励机制来使用它；你期待他们标记有价值的对话，但没有把这个纳入绩效考核；你希望他们发现系统漏洞，但发现了也没有快速的通道把改进建议真正落地。工具只是前提，文化和激励机制才是真正能让这套模式运转起来的东西。如果你的支持代表觉得"标记一个问题对话只是在给自己找麻烦"，那这套模式就是死的。

第五个原则：从可验证的小用例开始，建立可以扩展的架构基础。文章里的演进路径是很好的参考：先从简单的问答开始，把 evals 循环跑通，再扩展到动态行动，再扩展到跨渠道部署。这个顺序是有道理的，每一步都在前一步的基础上叠加，而不是一开始就想做最复杂的场景。很多团队犯的错误是上来就想做最难的用例，结果系统没有可观测性，出了问题不知道从哪里查，整个项目陷入泥潭。先小后大，先简单后复杂，先把质量循环跑起来再追求规模，这是这套架构在方法论层面最重要的指引之一。

我还想特别提几个在实践中比较容易踩的坑。

第一个坑：用 AI 来回答所有问题，而不是知道什么时候不该回答。文章里引用了一个工程师的话，他说"我们知道模型什么时候不该回答"，这是一个被严重低估的能力。一个能可靠地说"这个问题超出我的能力范围，让人工来处理"的系统，比一个总是给出答案但有时会给错的系统，在实际生产中要安全得多，对用户信任的损害也小得多。在设计 evals 的时候，一定要把"正确拒绝"这个维度包含进去，而不只是测试回答的质量。很多团队只测"能不能答对"，不测"该不该答"，这是一个很大的盲区。

第二个坑：把 AI 支持系统当成替代人工的工具，而不是增强人工的工具。文章里非常清楚地说，这套系统的成功依赖于人和 AI 的深度协作。支持代表是系统学习的重要来源，是知识库的贡献者，是 evals 的审核者，是模式识别的前线。如果你的目标是用 AI 系统来最大化减少支持团队的人数，你会错过这套模式里最有价值的部分，也会失去系统持续进化最重要的燃料。把人当成 AI 系统的协作伙伴，而不是被替代的对象，这是这套模式能走通的核心前提。

第三个坑：把可观测性当成事后补的东西，而不是一开始就设计进去的基础设施。文章里特别提到 Agents SDK 的步骤级追踪是默认开启的，这个"默认开启"非常重要。如果在构建系统的时候，可观测性是你在出了问题之后才想到要加的东西，你会付出比预期高得多的代价，因为补可观测性往往意味着要对系统架构做比较大的改动。而且更糟糕的是，在没有可观测性的情况下运行的那段时间里，你积累的所有问题都是不可追溯的，白白浪费了宝贵的学习机会。

好，我们来做一个收尾。

今天这篇文章给我们呈现的，不只是一套技术架构，更是一种关于"AI 如何让整个组织持续进化"的思维模型。表面层统一渠道，知识库持续进化，evals 量化质量，三者形成反馈循环，让每一次交互都成为下一次改进的原材料。同时，组织里的每一个人，无论是工程师还是支持代表，都是这个系统的建设者，而不只是使用者。文章最后说，支持应该停止成为一个你去到的地方，而变成一个被编织进每一个产品表面的动作。用户不再"提交工单"，他们只是在需要的地方得到了他们需要的东西。这是一个很美的愿景，也是一个正在发生的方向。

我个人认为，这篇文章里最深刻的洞见，不是具体的技术选型，而是那个关于"组织和 AI 应该一起学习"的核心主张。在很多公司里，AI 系统和人的工作是两条平行线，AI 处理 AI 的，人处理人的。而 OpenAI 描述的这套模式，是把两条线编织在一起，让 AI 的每一次输出都有人来审核和反馈，让人的每一次洞察都能变成 AI 改进的训练信号。这种双向的、持续的协作模式，或许才是 AI 在实际工作场景里真正发挥价值的正确姿势。
