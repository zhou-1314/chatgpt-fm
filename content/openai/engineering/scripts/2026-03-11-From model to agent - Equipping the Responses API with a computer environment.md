欢迎收听 ChatGPT FM，我是你们的主播。今天这期节目，我们来聊一篇 OpenAI 官方工程博客上的文章，英文标题是 From model to agent: Equipping the Responses API with a computer environment，我把它翻译成中文大概是这个意思：从模型到智能体，为响应 API 装备计算机执行环境。这篇文章发表于二〇二六年三月十一日，由 OpenAI 三位工程师联合撰写，分别是 Bo Xu、Danny Zhang 和 Rohit Arunachalam。

今天是二〇二六年九月九日，距这篇文章发表差不多整整六个月了。在 AI 这个领域，六个月是一段不短的时间，期间发生了多少"改变行业格局"的事情，相信每个听众都感受很深。但是，我之所以今天专门来聊这篇文章，是因为它讲的不是某个模型的跑分，也不是某个功能的发布公告，而是在讲工程架构，讲 agent，也就是智能体，到底怎么落地，讲 OpenAI 是如何系统性地思考"让模型真正干活"这件事的。这类内容的时效性比产品发布消息要长得多。架构思路和设计决策背后的逻辑，通常能参考好几年。而且，理解 OpenAI 在今年三月份是怎么想这个问题的，也有助于我们弄清楚接下来这半年里他们在产品方向上做出的很多选择。好，我们正式开始。

文章的核心主题，是行业里一个大家都在谈的转变：从"用模型"到"用智能体"，从 model 到 agent。这个区别到底是什么，我来打个比方。

假设你有一位朋友，精通编程、数据分析、写作，几乎什么都懂。现在有两种合作方式。第一种，你把他关在一个空房间里，什么工具都没有，你通过对讲机告诉他你的问题，他再通过对讲机告诉你答案。他能给你很好的建议，告诉你代码应该怎么写、分析该怎么做，但他做不到真正执行任何事情。第二种，你给他一台电脑、一个数据库、网络访问权限、一个文件系统，让他直接坐下来干活，你只给他一份任务说明，等他完成后给你结果。

这两种合作方式的能力差距，不是百分之二十、百分之五十，而是一个量级的跨越。这就是 model 和 agent 的根本区别。现在大多数开发者调用 AI 接口，即便是最强的那些模型，本质上还是在第一种模式下工作，模型只是在"告诉你怎么做"。而 agent 系统的目标，是让模型真正进入第二种模式，自己执行任务，自己获取结果，自己把事情从头做到尾。

文章的三位作者说，当你真正去构建一个 agent 系统时，会遇到几个非常实际的工程难题。第一，中间文件放哪里？一个复杂任务可能要生成很多中间产物，这些东西需要一个地方存放，不能只存在内存里。第二，大数据怎么处理？你不可能把一张有十万行的电子表格完整地塞进 prompt，token 成本会高得离谱，而且模型在海量信息里找有用内容的效率也很差。第三，网络访问怎么控制？agent 需要调用外部 API，但你又不想给它无限制的互联网权限，安全边界怎么划定？第四，任务超时和错误重试怎么处理？一个任务可能要跑好几分钟，中途出错了怎么办？难道每个开发者都要自己搭一套任务调度和容错系统？

每一个问题单独拿出来都不小。OpenAI 的解题思路是，与其让开发者各自造轮子，不如在 Responses API 这一层直接把这套基础设施做好，让开发者只需要专注于业务逻辑。他们给出的方案，是五个组件的组合，我们一个一个来讲。

先说第一个，也是最基础的：shell tool，命令行工具。

要理解 shell tool，你得先理解语言模型使用工具的本质机制。在训练阶段，OpenAI 给模型看了大量的示例，告诉它各种工具是怎么使用的，调用之后会产生什么效果，应该在什么情况下使用哪个工具。通过这些训练，模型学会了在合适的时机生成结构化的"工具调用请求"。这里有一个关键点需要特别强调：模型本身不能执行任何东西。它能做的，是生成一段结构化的文本，说"我要执行这个命令"，然后交给平台来真正跑。模型是在"提议"动作，而不是"执行"动作。这个区分乍一听好像是废话，但在理解整个系统架构的时候，这个区分非常关键，因为整个 agent 执行循环的设计逻辑，都建立在这个基础上。

Shell tool 让模型可以通过命令行来和计算机交互。Shell，也就是命令行，是 Linux 或者 Mac 终端里那个你输入命令的界面。grep 用来搜索文本，curl 用来发 HTTP 请求，awk 用来处理文本格式，这些经典的 Unix 工具，shell tool 全都支持，开箱即用。

文章里特别把 shell tool 和此前的 code interpreter，代码解释器，做了对比。代码解释器只能跑 Python 代码。而 shell tool 能做的事情宽泛得多：你可以用它编译运行 Go 程序、Java 程序，启动一个 Node.js 服务器，安装软件包，修改系统配置，发送网络请求，解析二进制文件。凡是在命令行下能干的事，原则上都可以通过 shell tool 来做。

这个灵活性的意义非常大。举个你在工作里可能真实遇到的例子：公司有一套核心数据处理管道是用 Java 写的，每次出了问题都要人工跑一堆命令来排查日志、对比输出、定位问题。如果 agent 只能跑 Python，它就很难直接介入这套 Java 工作流，你可能要花大量时间写 Python 包装器去调用 Java 代码，而且这个包装器本身就是一个维护负担。有了 shell tool，agent 可以直接编译 Java 程序、运行它、检查输出日志、对比预期结果、定位出错的行，和人类工程师手动操作没有本质区别。这让 agent 真正能嵌入到你已有的、非 Python 的工程体系里。

当然，shell tool 只是 agent 的"手"，它还需要一个"协调者"来把整个流程跑起来。这就是 Responses API 扮演的角色。

Responses API，响应 API，是开发者与 OpenAI 模型交互的主要接口。加入了 shell tool 支持之后，这个 API 的工作方式变成了一个持续的执行循环：模型提议动作，API 执行动作，把结果喂回给模型，模型再决定下一步，如此反复，直到任务完成。

文章里详细描述了这个循环的机制。当 Responses API 收到一个 prompt 的时候，它先把模型上下文组装好，包括用户的 prompt、之前的对话状态，以及工具的使用说明。这里有一个重要的前提条件：要使用 shell tool，模型必须是在训练时针对 shell 命令做过专门训练的版本，文章里提到是 GPT 五点二 及更新的版本才具备这个能力。模型拿到上下文之后，如果判断需要执行命令，就会生成一个或多个 shell 命令，返回给 Responses API。API 把这些命令转发给容器运行时，也就是真正执行代码的隔离环境，拿到输出之后，再实时地把输出喂进下一轮的模型请求里。整个过程保持流式连接，模型可以看到命令的实时输出，决定是要等更多结果，还是继续发下一条命令，或者直接给出最终答案。这个循环持续到模型认为任务完成，停止生成新命令为止。

文章里还提到了两个在工程上非常实用的细节。第一个是并行执行：模型一次可以在一个响应里提议多个 shell 命令，Responses API 可以用多个独立的容器会话同时执行这些命令，把多路输出整合成结构化结果再返回给模型。这好比你把一个大任务拆成几个子任务，派几个助手同时去做，而不是让他们排队等。比如 agent 可以同时搜索几个不同的日志文件、拉取几个不同来源的数据，大幅节省总时间。

第二个细节是输出上限控制：当 agent 处理大型文件或者跑一个输出量很大的命令时，原始输出可能有几百万行。把全部输出都塞进上下文，代价是灾难性的，而且大量无关信息会干扰模型的判断。所以，模型可以为每个命令指定一个字符上限，Responses API 会强制执行这个上限，保留输出的开头和结尾，把被省略的中间部分用一个特殊标记注明。文章里给出的例子是一个一千字符的截断，格式大概是：开头的文本……省略了一千个字符……结尾的文本。这样模型能知道输出的大致轮廓和关键信息，而不会被海量原始日志淹没。并行执行加上有界输出，让这个 agent 循环既快又高效。

下面讲我个人认为文章里技术含量最高、同时也是最有意思的部分：上下文压缩，context compaction。

上下文窗口，context window，是语言模型一次能处理的全部信息量。一个 agent 跑复杂的长任务，可能要经历几十步甚至上百步操作，每一步的工具调用、执行结果、模型推理，都会不断追加到上下文里。文章里有一段描述很形象：想象 agent 调用一个技能，拿到响应，再追加工具调用和推理摘要，就这样不停叠加，有限的上下文窗口很快就会被填满。一旦填满，后续的请求就会失败，整个任务就会中断。

传统的处理方式是开发者自己设计一套"摘要系统"，定期把历史对话压缩成一段摘要，然后带着摘要继续跑下去。这个方案逻辑上可行，但工程上很繁琐，而且摘要的质量很难保证。如果摘要遗漏了某个关键细节，比如任务的某个重要约束，或者某个中间结果，agent 可能会悄悄走弯路，甚至重复做已经做过的事情，而你可能完全察觉不到。

OpenAI 的解法是把这个能力直接内置到最新的模型训练和 API 层。他们训练最新的模型去分析之前的对话状态，生成一个"压缩表示"，这是一种加密的、在 token 消耗上非常高效的格式，把任务的关键状态提炼保存下来。压缩完成后，新的上下文窗口由这个压缩项加上之前窗口里价值最高的那些片段共同构成。这样，整个工作流就能跨越上下文窗口边界，继续流畅运行，不会因为"记忆满了"而断掉。

这个系统有两种使用方式。一种是服务端自动压缩，开发者设置一个触发阈值，比如上下文使用量达到某个比例时自动压缩，之后 API 自己处理，完全不需要写额外的客户端代码。文章里还提到一个细节：服务端压缩允许上下文在触发阈值附近有一点弹性空间，让临近上限的请求能先被处理再压缩，而不是直接被拒绝，这在实际使用中能避免很多边界情况下的意外失败。另一种方式是调用独立的压缩接口，由开发者手动触发，适合需要更精细控制的场景。

文章里还讲了一个让我印象非常深刻的故事，讲的是 Codex，OpenAI 内部用于辅助编程的 agent 系统，是如何参与开发这个压缩功能的。他们让 Codex 来帮助开发这套压缩系统。Codex 在使用过程中遇到了压缩错误，团队就再启动另一个 Codex 实例来排查这个问题。结果，Codex 一边在自己的日常编程任务中用着这个压缩功能，一边帮助完善它，最终 Codex 本身也成了这套压缩系统最早的、也是最直接的受益者之一。文章里有一句话让我很有感触：大多数工具只要求用户学会如何使用它，但 Codex 是和我们一起成长的。我个人认为这段描述有一定的文学渲染成分，但它背后的逻辑是真实的：当工具足够智能，你可以让它参与自身的迭代，这种内部的自我改进飞轮一旦运转起来，速度是很难从外部追上的。

好，现在来讲第四个组件：容器上下文，或者说 agent 的"工作空间"。这个工作空间有三个层次，分别对应三类不同的资源。

第一层是文件系统。你可以把文件上传到这个隔离的容器里，agent 可以读写这些文件，也可以生成新的输出文件。文章里反复强调了一个重要原则：不要把大量输入数据直接塞进 prompt。这是一个非常常见的反模式，一种你应该主动避免的做法。你有一份两百页的技术文档，想让 agent 回答几个问题，最直觉的做法是把整份文档的文字全部粘进 prompt 里。但这样有两个问题：一是贵，token 都是钱；二是效果不好，模型要在两百页内容里定位关键信息，效率很低，而且信息量太大容易"顾此失彼"，反而漏掉重点。

更好的做法是：把文档上传到容器文件系统，给模型一个目录清单，让它用 shell 命令自己决定打开哪些文件、读取哪些段落。这类似于你雇了一个员工，给他一个档案室的钥匙，告诉他文件在哪几个柜子里，让他自己去找，效率远比你把所有文件的复印件一页一页堆到他桌上要高。模型和人类一样，面对有组织的信息比面对无序的信息堆砌工作得更好。

第二层是数据库。文章建议，对于结构化数据，开发者应该优先使用 SQLite 这样的轻量级数据库来存储，而不是把整张表格的内容塞进 prompt。SQLite 是一种轻量级的关系型数据库，可以直接嵌入到应用里，不需要部署独立的数据库服务器，非常适合 agent 工作流这类场景。

文章给了一个很直观的例子：如果你让 agent 回答"这个季度哪些产品的销售额在下滑"，agent 可以直接向数据库发一条 SQL 查询，只提取相关的行和字段，而不是把整张有几万行的电子表格全部加载进来。这样不仅更快、成本更低，而且对于数据量更大的场景也能自然扩展，你的数据集从几万行增长到几百万行，查询模式不需要变。

第三层是网络访问，这是三层里工程复杂度最高的部分。agent 经常需要调用外部 API 来获取实时数据，需要安装运行时依赖包，有时候还需要访问你内部的一些服务。但是，如果给容器完全开放的互联网访问权限，风险非常大：agent 可能会不小心把内部数据或者上下文信息传到外部服务；可能会误触你不该碰的第三方系统；如果 API 密钥被模型接触到，可能发生凭据泄露而你根本不知道。

OpenAI 的解法是在容器和外网之间加入一个叫做旁路出口代理的组件，英文叫 sidecar egress proxy。所有从容器发出的网络请求，都必须经过这个代理层。代理层负责执行白名单策略，只有你事先批准的域名才能被访问，所有出站流量都有日志可查，可以被监控和审计。

更精妙的是凭据的处理方式。文章里描述的机制叫做域名限定的密钥注入，英文叫 domain-scoped secret injection。它的工作原理是这样的：模型和容器里看到的只是一个占位符，比如一个假的 API key；当实际请求从代理层发出的时候，代理才把真实密钥填入请求头，而且只针对你已经预先批准的特定目标域名。这样，真实密钥永远不会出现在模型可以"看到"的上下文里，密钥泄露的风险从根源上就被大大降低了。即便模型被某种方式诱导去"读出"自己看到的密钥，它看到的也只是一个无意义的占位符。这个设计，我个人认为是这篇文章里安全工程做得最细腻的地方之一。

好，现在来说最后一个组件：agent skills，智能体技能包。

先想象一个场景：你的团队每周都要从某个内部系统拉财务数据，做一些格式转换，生成一份标准化的管理报告。如果用普通 agent 来自动化这件事，每次运行 agent 都得从头重新规划工作流：先调哪个接口，响应格式是什么，哪些字段需要转换，报告的模板是什么，输出文件叫什么名字。每次都在重新发明轮子。不仅浪费时间和 token，结果也很难保持一致，每次可能稍微有些差异，需要额外的人工检查。

Skill，技能包，解决的就是这个问题。一个 skill 本质上是一个文件夹，里面最核心的是一个叫做 SKILL.md 的文件，这个文件里包含技能的元数据，比如名称和描述，以及具体的执行说明，包括步骤、参数、注意事项、预期输出格式。除了这个说明文件，skill 文件夹里还可以包含配套资源，比如 API 规范文档、示例脚本、UI 模板，甚至是测试用的数据样本。你把这个文件夹上传到 OpenAI 平台，平台以版本化的方式存储它，之后可以通过 skill ID 来调用。

调用 skill 的流程是确定性的，文章给出了精确的三个步骤：第一步，获取 skill 的元数据，包括名称和描述；第二步，获取完整的 skill 包，把它复制到容器里并解压；第三步，把 skill 的元数据和容器路径更新到模型的上下文里。之后，模型就可以用 shell 命令来探索 skill 的说明文档，读取 SKILL.md，按照里面的指示逐步执行脚本。整个过程是可重复的，版本可控的，不同的 agent 实例调用同一个 skill，会得到一致的执行路径。

你可以把 skill 理解为给 agent 的"标准操作手册"，有了手册，agent 不需要每次都自己发明一套方法，直接照着手册做就行。而且，skill 是可以组合的，你可以在平台上维护一整套 skill 库，每个 skill 负责一个特定功能模块，agent 按需调用，像积木一样把不同的技能拼合成复杂的工作流。文章里说，一个 prompt 就可以展开成一个端到端的工作流：发现合适的 skill，获取数据，转换成本地结构化状态，查询需要的部分，生成最终的可交付成果。

好，现在我们把五个组件放在一起，看完整的图景。Responses API 是协调者，负责管理整个执行循环；shell tool 给了 agent 动手操作的能力；托管容器是 agent 的工作空间，提供文件系统、数据库和受控网络三重上下文；skills 提供可复用的工作流模板；context compaction 让 agent 能长时间运行而不会因为"记忆满了"而崩掉。

文章里描述的一个完整的端到端例子是从实时数据生成一张业务报告电子表格。流程大概是：agent 接到任务，发现合适的 skill，读取 skill 说明，用 shell 命令调用外部 API 获取数据，把数据存入容器里的 SQLite 数据库，用 SQL 查询出需要的行，最后生成一个电子表格文件作为最终输出。整个过程，一个 prompt 触发，agent 自己把所有中间步骤都搞定。

好，架构讲完了，我们来聊实践，这些东西对你实际工作到底意味着什么。

如果你现在在做 agent 相关的开发，有几个可以直接参考的做法。

第一，把数据和文件放进容器，不要塞进 prompt。这个原则背后的逻辑是：prompt 的空间和 token 是稀缺资源，应该用来放任务说明和关键约束；大量原始数据应该让 agent 自己按需去取，而不是一股脑儿全倒进去。如果你发现自己正在把几百行的 CSV 或者一大段 JSON 手动粘进系统提示词，这就是一个需要停下来重新考虑架构的信号。

第二，用 SQLite 处理结构化数据，给模型数据的描述，比如表的结构、列名和含义，而不是把完整内容倒进去，让模型自己写 SQL 查询。这种做法在数据量增长的时候扩展性非常好，而且查询效率通常比模型在上下文里自己"扫描"数据要高得多。

第三，认真对待网络访问的安全策略。不要为了省事直接给容器全放开的网络权限。花时间定义一个白名单，只允许 agent 访问它真正需要的域名。密钥管理要按照文章里描述的域名限定注入方式来做，不要把真实的 API key 直接写进系统提示词或者 prompt 里，哪怕你觉得模型不会把它读出来，也要避免这种风险。安全问题往往是在你"觉得不会发生"的时候发生的。

第四，如果你在跑长时间的 agent 任务，一定要启用服务端自动压缩，并设置一个合理的触发阈值。这里有一个值得特别注意的地方：压缩不是无损的，模型在压缩时会做取舍，判断什么是重要信息、什么可以舍弃。所以，那些绝对不能丢失的信息，比如任务的核心约束、用户明确提出的要求、某个关键的中间判断，最好在每次 prompt 里明确重申，或者单独存为文件让模型每次都读，而不是完全依赖压缩机制来保留。

第五，如果你有重复性的工作流，考虑把它封装成 skill。任何一个你发现 agent 在多次任务中都要重新规划的流程，都是封装成 skill 的好候选。把执行说明写进 SKILL.md，把 API 规范、示例数据、脚本一起打包，通过 skill ID 来调用，这样可以大幅提高结果的一致性，也方便团队共享和版本管理。

从更宏观的角度来看，这篇文章描述的，是一次从"生成式 AI"到"执行式 AI"的基础设施升级。以前，你调用 API，模型给你文字；现在，你给 agent 一个任务，它给你一个结果文件、一个已经跑完的数据处理流程、一份生成好的报告。这个转变对软件工程师意味着：AI 不再只是你的写作辅助或代码补全工具，它开始成为你的执行单元，能够真正完成端到端的任务，而不只是提建议。

我个人认为，skills 这个概念如果生态真的发展起来，是非常值得期待的事情。如果形成了类似开源包仓库的 skill 生态，你可以在平台上找到各种领域的标准化 skill，比如"财务报告 skill"、"代码审查 skill"、"数据清洗 skill"，把它们组合成专属于你业务场景的 agent 工作流。这条路走通了，agent 系统的开发门槛会大幅下降，很多中小公司也能快速搭建起自己的自动化业务流程。当然，要走到那一步，还需要解决 skill 的安全审查、质量控制、版本兼容、权限管理等一系列工程问题，路还很长。但方向是清晰的，而且这种方向感是这篇文章最有价值的东西之一。

最后做一个总结。这篇文章用五个组件描述了一套完整的 agent 执行架构：shell tool 给了模型动手的能力，托管容器提供了文件、数据库和受控网络三重工作上下文，context compaction 解决了长任务的记忆管理难题，agent skills 实现了工作流的可复用封装，Responses API 把这一切串联成一个流畅的执行循环。

我个人对这篇文章最大的感触是：OpenAI 终于开始在工程层面认真回答"怎么让模型真正干活"这个问题了，而不只是发布一个更强的模型让开发者自己去摸索。基础设施越完善，能用 agent 解决的实际业务问题就越多。理解这套架构，对于今天任何在做 agent 开发的工程师和产品人来说，都是值得投入时间的事情。
