在进入正题之前，我要先做一个时效性说明。今天是二〇二六年九月九日，距这篇文章发表已经将近八个月。在 AI 领域，八个月不是一段短时间，模型换代了，工具接口也更新了好几轮。所以听这期节目的时候，需要把它当成一份工程经验记录来参考，而不是当作最新的产品公告。

先帮你定位一下这篇文章发表时的时代背景。二〇二六年一月，是 GPT 五系列刚刚确立主流地位的阶段。OpenAI 在那个时期刚完成从 GPT 四到 GPT 五体系的代际过渡，旗舰模型的推理能力有了质的飞跃。与此同时，AI agent，也就是能够自主规划和执行多步骤任务的 AI 系统，开始从实验室环境走向企业内部的真实工作流。各家公司都面临同一个问题：怎么把大模型的能力真正落地到日常业务流程里，而不只是停留在演示层面？

OpenAI 这篇文章，是他们作为一家公司，把自己的 AI 工具用在自己内部数据分析工作上的工程实践总结，也就是业界常说的"吃自己的狗粮"。他们用来构建这个 agent 的工具——包括 Codex、GPT 五点二、Evals API 和 Embeddings API——同时也是他们向外部开发者开放的产品。所以这篇文章既是一份内部经验分享，也是一份真实的产品能力验证报告。

好，进入正题，我们从问题本身说起。

想象一下，你是 OpenAI 的一名产品经理。你的管理层在周一的会议上问了一个问题：上周发布的某个功能，到底有没有带来真实的用户活跃度增长？直觉上这是一个简单的数据问题，但实际操作起来往往相当繁琐。你需要先找到存放用户行为数据的表，但数据仓库里可能有几十张名字相似的表，你不确定该用哪一张。你联系了数据团队，但他们今天排期满了，明天才能帮你看。等到明天，拿到了 SQL，跑出来一个数字，但你不确定这个数字是不是对的，因为你不知道这张表有没有包含所有平台的用户，还是只包含了某一类用户。你又去确认，又等了半天。从提出问题到得到可靠答案，几天就这么过去了。

OpenAI 的数据平台面临的就是这个问题的极端放大版本。他们有超过三千五百名内部用户，覆盖工程、产品和研究等多个部门，存储了超过六百拍字节的数据，分布在七万多个数据集里。六百拍字节是什么概念？一拍字节等于一百万太字节，六百拍字节大约相当于六亿G的数据量。七万个数据集，意味着就算你知道自己大概需要什么类型的数据，光是在这七万张表里找到合适的那张，本身就是一件非常耗时的事情。

文章里引用了一个内部员工的原话，我来翻译一下大意：我们有大量看起来非常相似的表，我花了很多时间想弄清楚它们之间到底有什么不一样。有的表包含了未登录用户的数据，有的不包含。有些字段名字有重叠，但含义又不完全相同，真的很难搞清楚该用哪个。

这就是核心痛点。两张表从结构上看可能几乎一样，但一张包含了所有访问流量，另一张只包含了登录用户的行为记录。如果你不知道这个区别，用错了表，分析出来的用户数可能差了两三倍，而你完全毫不知情。而且即便选对了表，写出正确的 SQL 也并不简单：多对多的关联关系写错了会造成数据行数膨胀，过滤条件的逻辑位置写错了会导致数值偏差，空值没有妥善处理会悄悄影响聚合计算的结果。这些错误的共同特点是，查询能正常执行，结果的格式看起来完全正常，但数值是错的，往往很难察觉。

正是在这个背景下，OpenAI 内部决定自研一个 AI 数据 agent，让工程、产品、财务、市场等所有部门的员工，都能用自然语言提问，在几分钟内得到可靠的数据答案，而不需要具备 SQL 技能或者等待数据团队的排期。

这个 agent 是一个纯内部工具，专门为 OpenAI 的数据环境、权限体系和工作流程定制，不对外开放。它由 GPT 五点二 驱动，也就是文章发表时 OpenAI 的旗舰模型。它被集成到员工日常使用的各类工具里：Slack 机器人、Web 界面、集成开发环境、Codex 命令行工具，以及 OpenAI 内部的 ChatGPT 应用。通过 MCP，也就是模型上下文协议，这些入口都能调用同一个 agent 的完整能力，员工不需要切换到专门的系统，在他们已经在用的工具里直接提问就行。

接下来是这篇文章的核心内容，也是今天我们最主要的话题：这个 agent 是如何获取准确上下文、从而给出可靠答案的。

要让 agent 回答关于数据的问题，光靠语言模型本身的能力是远远不够的。如果模型不了解你公司里每张表是做什么用的、有哪些特殊限制、各指标的口径定义是什么，它就可能给出听起来合理但实际完全错误的答案。OpenAI 为这个 agent 设计了一套七层上下文体系。我来一层一层拆解，用一个贯穿始终的比喻来帮你理解：把数据仓库里的每一张表想象成图书馆里的一本书，agent 的任务是找到正确的书，然后真正读懂它。

第一层叫做元数据基础。这是最基本的信息层，就像书的封面和目录：表名、列名、数据类型，以及表与表之间的上下游依赖关系，也就是哪张表是由哪些数据加工而来的，又被哪些下游表所依赖。这些信息帮助 agent 了解数据仓库的整体骨架。但就像只看目录没法让你真正理解一本书的内容一样，元数据只是最基础的起点，远远不够。

第二层叫做历史查询推断。通过分析数据仓库里积累的历史 SQL 查询记录，agent 可以学到很多隐性知识：哪些表经常被联合查询，某张表通常会附带什么样的过滤条件，某个字段在实际使用中通常代表什么业务含义。这就像翻看图书馆的借阅记录和读者留下的批注，从有经验的读者身上学到那些没有在正文里明确写出来的理解。

第三层叫做领域专家策划的描述。这是由了解业务的人工专家为关键表和字段撰写的说明，捕捉那些从数据结构本身根本无法推断出来的东西：这张表的设计意图是什么，某两个看起来相似的字段在语义上有什么本质区别，使用这张表时需要注意哪些陷阱，哪些场景下不适合用它。这一层的信息质量最高，但也是最难规模化维护的——随着业务快速变化，人工文档几乎永远在追赶现实，而不是描述现实。

第四层，也是我在整篇文章里认为最值得重点说的设计：代码级别的上下文，用 Codex 去爬取和分析生产每一张数据表的数据管道代码。

你可能会问，为什么要读代码？让我解释一下这背后的逻辑。一张数据表里的数据，它的真正含义通常不在列名里，也不在表名里，它藏在生产这张表的代码逻辑里。生成数据的代码里有过滤条件：哪类用户在入库之前就被排除掉了，哪个时间范围的数据才被纳入计算；有聚合逻辑：这个数值字段是原始事件的计数，还是经过去重之后的独立用户数，还是加权处理之后的结果；有更新机制：这张表是实时写入的，还是每天凌晨跑一次批处理，昨天的数据什么时候才能准确；有数据范围：这张表只覆盖了某些产品线，还是涵盖了全部业务流量。

这些信息，对于编写了这段代码的数据工程师来说不是秘密。但对于产品经理、市场分析师、财务同学这类非技术用户来说，这些代码是完全不可见的黑盒，而他们恰恰是最需要数据来支持决策的人。

OpenAI 的做法是让 Codex 爬取并分析生产每一张数据表的管道代码，把代码里隐含的业务逻辑、约束条件和数据范围转化成对这张表的结构化理解。文章里给了一个很具体的例子：两张 schema 结构几乎相同的表，一张只包含 ChatGPT 的第一方流量，另一张包含了所有来源的流量，包括通过合作伙伴渠道产生的访问。如果你要分析 ChatGPT 产品本身的用户表现，用后者来计算用户数，结论就会被大幅高估。通过读取生产这两张表的代码，agent 能够明确识别并说明这个关键区别，让用户在提问阶段就能选对数据源，而不是等结果出来之后才发现用错了表。

更重要的是，这一层上下文是自动刷新的。代码更新了，下一次离线处理完成后，agent 对这张表的理解就自动同步了，完全不需要人工干预。这从根本上解决了数据文档永远滞后于实际情况这个几乎所有公司都头疼的长期问题：让代码本身作为最权威、最及时的文档。

第五层是文档上下文。agent 可以接入公司内部的 Slack 消息、Google 文档和 Notion 笔记，从中获取数据仓库本身不包含的机构知识。比如某次产品功能上线的具体时间节点和背景、某个内部 A/B 实验的代号和实验设计、某个关键业务指标的官方口径定义是如何确定的。这些信息散落在各个协作工具里，是公司在日常运营中自然积累起来的集体记忆。如果没有系统化接入这些来源，agent 就永远无法把数据上的波动和具体的业务事件对应起来，也无法理解公司内部特有的术语和代号。

这些文档在接入时经过两个处理步骤：用 OpenAI 的 Embeddings API 把内容转化成向量嵌入存储起来，方便快速语义检索；同时配合权限控制，确保 agent 只能帮用户获取用户本人有权限访问的文档内容，不会因为引入 AI 层而产生信息越权的问题。

第六层是记忆系统。这是 agent 能够持续进化的关键机制。当用户指出 agent 的某个错误，或者 agent 在对话中发现了某个不显而易见的数据处理规则，这个知识会被保存为一条持久的记忆，下次遇到类似问题时直接调用，不再从零开始摸索。

文章里举了一个非常具体的例子来说明记忆层的价值。有一次，agent 需要过滤某个特定 A/B 实验组的数据，但它不知道这个实验在数据库里是通过一个特定的字符串标识符来标记的，而不是通过实验名称本身。agent 只会模糊地尝试字符串匹配，结果总是出错，要么什么都匹配不到，要么把不相关的数据也拉进来。当用户明确告知了正确的过滤方式并保存为记忆之后，之后每次遇到这类过滤需求，agent 就能准确处理了，不再重蹈覆辙。

记忆层专门针对的是这类知识：非显而易见的过滤条件和业务约束，它们既不能从 schema 里推断出来，在人工文档里也通常没有记录，但一旦处理错误就会造成严重的分析偏差。记忆分为全局层级和个人层级两种，全局记忆对所有用户生效，用于记录对整个组织都适用的数据规则；个人记忆只对特定用户生效，用于记录某人特有的分析习惯或业务场景约定。用户可以手动创建和编辑记忆，agent 自己在发现新知识时也会主动提示用户是否要保存。

第七层是实时数据探查能力。当某张表完全没有现成的上下文信息，或者现有信息已经严重过时，agent 不会直接放弃，而是可以向数据仓库发出实时查询，现场探索表的结构、字段分布和数据样本，从而动态推断这张表的含义和适用场景。它还可以与数据平台里的其他系统对话，比如 Airflow 任务调度系统、Spark 计算框架，获取那些数据仓库本身无法告诉你的上下游处理信息，比如某个数据管道最近一次成功运行是什么时候，某张表的数据延迟通常是多少小时。

这七层上下文是怎么在实际运行中高效组合的？文章描述了一个离线加实时的双轨架构。每天运行一个后台数据处理管道，把表的使用记录、人工注解和 Codex 提取的代码理解整合成一份统一规范的表描述，然后用 Embeddings API 把这些描述转化为向量嵌入并存储起来。当用户真正提问的时候，agent 不会去扫描全部七万张表的原始信息，那样太慢了，延迟会高得完全无法使用。而是通过 RAG，也就是检索增强生成这个技术，只拉取与当前问题最相关的那几张表的上下文信息，再把这些上下文连同用户的问题一起交给 GPT 五点二 来推理。这套设计让上下文的深度和响应速度得以同时保证，即便面对七万张表的规模，运行延迟依然控制在可接受的范围内。

说完上下文体系，我们来聊聊这个 agent 的推理机制和自我纠错能力。

大多数数据问题不是一问一答就能解决的。用户往往需要先问一个大问题，看了初步结果之后再追问、调整方向、聚焦到某个细分维度。这个 agent 被设计成一个能够全程陪你探索的对话式分析伙伴，而不是一个只接受单次查询的工具。它保留跨多轮对话的完整上下文，你问完第一个问题之后，可以直接跟上"按地区拆分看看"或者"聚焦在最近三十天"，不需要每次都重新解释背景。如果 agent 理解错了你的意图，你可以在它生成中间结果的时候随时打断，重新给出方向，它会立刻调整，不会把跑偏的路径执行到底。

更重要的是，agent 会主动评估自己的中间结果。比如执行了一条 SQL 之后，返回的结果集是零行。agent 不会直接把这个空结果交给用户，而是先判断：这个零行是合理的吗？还是说 join 条件写错了，或者过滤范围设得太严，把所有数据都过滤掉了？如果判断是后者，agent 会回头审查自己的推理逻辑，调整方案，重新尝试。这个闭环的自我纠错过程，把原本需要用户手动来回迭代的检查工作内化到了 agent 内部，用户看到的是一个经过多轮自我审视之后的最终结果，而不是一堆需要自己判断的中间状态。

对于那些定期重复的分析任务，比如每周的业务健康报告、某类数据表的例行质量检验，agent 还支持把这些重复分析的步骤和最佳实践打包成可复用的工作流，只需要设置一次，之后每次执行都能保证方法一致、结果可比，不会因为不同人手工操作而产生口径不统一的问题。

接下来说质量保证，这部分对我们自己做 AI 应用很有参考价值。

OpenAI 使用了自家的 Evals API 来持续评估这个 agent 的回答质量。具体做法是构建一套精心设计的测试集，里面每个条目都是一个真实的数据分析问题，配套一条由人工编写并确认正确的标准 SQL 查询，也就是所谓的黄金 SQL。评估时，把自然语言问题发给 agent，让它生成 SQL，执行这条 SQL，然后把执行结果与黄金 SQL 的结果做比较。

这里有一个关键细节值得强调：评估不是在做字符串匹配，不是判断两条 SQL 是不是写得一模一样。因为同样的查询目的可以有很多种不同的写法，语法不同但结果等价的答案应该被判定为正确。他们的做法是把生成的 SQL 和实际的查询结果这两个信号，一起送给 Evals API 的评分器，用模型来判断两个结果集是否等价，并给出评分和解释。这样既能识别语法不同但语义相同的正确答案，也能捕捉那些 SQL 看起来差不多但结果集有细微偏差的隐性错误。

这套评估系统承担了两个角色。在开发阶段，它就像单元测试，每次修改 agent 的能力或者系统提示，都跑一遍评估，确保没有引入新的回归问题。在生产阶段，它就像预警系统，帮团队在问题还没扩大之前第一时间发现质量下滑的苗头，而不是让用户来帮你发现 bug。

文章最后总结的几条实践教训，我认为是整篇文章含金量第二高的内容，仅次于多层上下文体系的设计思路，对我们自己做 agent 开发非常有参考意义。

第一条：给 agent 的工具集要精简，不能有太多功能重叠。他们最初把完整的工具集都暴露给 agent，结果发现当多个工具功能有重叠时，agent 不知道在什么情况下该用哪个，在工具选择上浪费推理资源，还容易选错。最后他们限制并合并了部分工具。这背后有一个值得记住的原则：对人类来说，多几个功能相近的工具没什么问题，我们有足够的背景知识来判断应用场景；但对 agent 来说，工具之间的语义模糊会直接降低决策质量，让 agent 把推理资源花在本不该花的地方。

第二条：高层级的指引优于详细的步骤规定。他们发现，如果系统提示写得非常细，规定了 agent 应该按什么顺序做什么，反而会适得其反。用户的问题是千变万化的，你提前预设的正确路径无法覆盖所有情况，有时候这些过于具体的指令会把 agent 强行推向一条错误的轨道，让它明知结果不对还得照着走。他们最终改为给出高层级的目标和原则，把具体的执行策略交给 GPT 五点二 的推理能力来自主决定，结果反而更健壮、更准确。这背后有一个更深层的启示：当模型的推理能力足够强的时候，你要做的不是替它规划每一步，而是清楚地告诉它你要什么，然后信任它的判断。

第三条：读代码胜过读文档。这是我认为整篇文章最值得反复咀嚼的一句话，我再强调一遍：理解一个数据集最可靠的方式，不是看 schema，不是看列名，甚至不是看历史查询记录，而是读生产它的管道代码。代码里有那些永远不会出现在文档里的假设、约束和业务意图，它是数据集最真实、最及时的说明书。OpenAI 通过让 Codex 读懂数据管道代码，让 agent 真正理解了数据，而不只是记住了字段名。

在安全性方面，这个 agent 采用了权限透传的设计。它本身不持有任何额外的数据权限，用户通过 agent 能查到什么，完全取决于用户本人已有的权限。如果某张表用户没有权限访问，agent 会明确告知，并尝试推荐用户有权访问的替代数据集。这个设计的意义在于：引入 AI 层不带来新的权限绕过风险，数据安全边界和没有 agent 之前完全一致。同时，agent 在给出每个答案时会展示自己的推理过程、所做的假设和执行的步骤，用户可以追溯到原始数据和查询，保证全链路的可审计性。

好，说完原文内容，我来聊聊这些东西对你的实际工作意味着什么。

如果你在公司里负责数据平台建设、AI 工具开发，或者日常从事数据分析工作，这里有几个可以直接借鉴的方向。

首先，在构建企业内部的数据问答系统时，不要只依赖表的 schema 和人工文档，要把生产数据的管道代码也纳入上下文。代码是最权威也最及时的描述，它不会因为时间推移而过时——代码更新之后，上下文自动刷新了。如果你所在的团队还没有成体系的数据管道代码库，把代码仓库整理好其实是为未来的 AI 工具建设打的基础，这个投入是值得的。

其次，设计一个记忆层来积累踩坑知识。你的数据仓库里一定有一些非显而易见的过滤规则、历史遗留的字段约定、特殊的数据范围限制，这类知识不在文档里，没有人系统地整理过，但处理错了就会造成严重的分析偏差。专门设计一个机制来收集和复用这类知识，是提升 agent 可靠性最高性价比的投入，而且实现门槛并不高。

第三，建立黄金测试集，持续跑评估。收集十到二十个你最关心的核心分析问题，为每个问题确认一个正确答案，把这套测试集作为回归测试持续运行，用模型来判断结果等价性，而不是做字符串匹配。这个方法的成本不高，但能帮你在 agent 行为出现回归时第一时间发现，把问题消灭在扩散之前。

第四，控制工具集规模，抵制"给 agent 更多能力总是更好"的直觉。工具集要精简，每个工具的职责要清晰，功能重叠的工具要合并或者明确区分使用场景。边界清晰的小工具集，往往比功能丰富但语义模糊的大工具集在实际使用中表现更稳定。

需要特别提醒的是，OpenAI 描述的这套系统是在他们已有的完善数据基础设施上构建的，包括规范的权限体系、相对完整的数据治理流程、成体系的数据管道代码库。如果你所在的公司数据基础设施还处于建设初期，不要试图一次性复制全部七层。从最容易落地的几层入手，比如先把 schema 元数据和人工描述做好，再逐步引入历史查询上下文和代码理解，迭代推进。完美是优秀的敌人，先有一个能跑起来的版本，比什么都规划好但迟迟不上线要有价值得多。

最后来做一个总结。

这篇文章的核心价值在于：它告诉我们，要让 AI 真正用好在企业数据场景里，关键不在于模型有多强，而在于你能不能构建一套让模型真正理解你的数据、你的业务、你的机构知识的上下文体系。OpenAI 的答案是七层上下文加上离线批处理配合实时检索的架构，再加上持续运行的评估机制，让 agent 不只是能写 SQL，而是真正读懂了数据背后的业务含义。

我个人认为，这篇文章最值得带走的核心洞察只有一句话：代码是理解数据最可靠的文档。这一点，无论今天还是一年后，都不会过时。
