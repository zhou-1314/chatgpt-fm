## Script

今天要聊的这篇文章，英文标题叫 "An open-source spec for Codex orchestration: Symphony"，我把它翻译成"用于 Codex 编排的开源规范：Symphony"。这篇文章发表于二零二六年四月二十七日，作者是 OpenAI 的三位工程师，Alex Kotliarskyi、Victor Zhu 和 Zach Brock。

距今大概四个半月。四个月在 AI 领域，是好几轮工具迭代的周期，但这篇文章描述的问题和解法，今天看依然非常贴地气，甚至比发布时更加相关——因为那会儿 coding agent 才刚刚从实验性工具变成很多工程团队的日常配置，现在更多人真的在用了，也真的在碰文章里说的那些坑。这篇文章发表的时间节点，大概是在 Codex 大规模进入企业研发工作流的关键时期，coding agent 已经足够可靠，可以独立完成真实的工程任务，但怎么管理多个并发运行的 agent，怎么让它们不互相干扰、高效协作，这个问题还没有公认的答案。Symphony 是 OpenAI 内部对这个问题给出的一个答案。

我觉得这篇文章值得专门出一期，原因有三个。第一，它不是在描述一个抽象的技术方向，而是记录了一个真实团队从踩坑到找到解法的完整过程，里面有具体的决策、具体的失败和具体的数字。第二，最终的解法出人意料地简单：Symphony 的核心就是一个 Markdown 文件，叫 SPEC.md，一份规范文档，不是一套庞大的框架。第三，这篇文章里藏着一个更深层的工程哲学，关于当代码本身的成本趋近于零时，整个软件工程的工作方式会发生什么根本性的变化。好，我们进入正题。

故事要从六个月前说起，也就是大约二零二五年十月前后。这个团队做了一个在当时颇具争议的决定：他们要构建一个完全没有人类手写代码的代码库。这不是说多用 AI 辅助，而是字面意义上的，仓库里的每一行代码都必须由 Codex 生成。为了做到这一点，他们从头重新设计了工程工作流，建设了一个对 agent 友好的代码仓库，在自动化测试和各种安全护栏上投入了大量精力，把 Codex 当成一个正式的团队成员对待。这段经历他们在之前的一篇关于 harness engineering 的文章里有详细记录，如果你感兴趣可以单独去看。

这个实验成功了。但成功之后，他们撞上了下一个瓶颈：上下文切换的代价。

让我来解释一下这是什么感受。想象一下，你现在同时开着五个 Codex 会话，每个会话对应一个不同的任务。第一个会话在重构某个模块，第二个在写单元测试，第三个在修一个 bug，第四个在升级依赖，第五个在写迁移脚本。你需要轮流盯着每一个，及时给出反馈，发现跑偏了要纠正，卡住了要介入。每次从一个会话切换到另一个，你的大脑都要重新加载这个任务的背景信息：这个任务目标是什么，已经做到哪一步了，下一步要做什么，之前遇到什么问题。这个过程消耗的不是你的时间，而是你最宝贵的资源：注意力。

文章里有一个描述非常准确。他们发现，大多数工程师在保持注意力不崩溃的前提下，最多能同时管理三到五个 Codex 会话。超过这个数字，生产效率就开始下滑。工程师会忘记哪个会话在做什么，不停地在终端之间来回切换，去调试那些跑到一半卡住的长任务。Agent 本身执行得很快，但人成了整个系统里的瓶颈。

他们用了一个比喻，我觉得说得非常精准：我们实际上建了一支由极其能干的初级工程师组成的团队，然后安排我们的人类工程师去全职微管理他们。初级工程师执行力强，但需要指导，这没问题。真正的问题是，如果每个初级工程师都需要一个高级工程师盯着，那扩大团队规模反而会让高级工程师的工作量成倍增加，整个组织的效率天花板就被"管理带宽"死死锁住了。

怎么解决这个问题？他们做了一个思维方式上的转变，我认为这是这篇文章里最值得停下来好好想的地方。他们意识到，自己一直在优化错误的对象。团队的关注点放在 coding session 和 merged PR 上，但这两个东西只是手段，不是目的。软件工程真正的工作单元是什么？是 issue、task、ticket、milestone，是任务本身，而不是实现任务的那个会话。

换句话说，他们问了自己一个问题：如果我们不再直接管理 agent，而是让 agent 自己去任务看板上领任务，会发生什么？

这个问题的答案就是 Symphony。

Symphony 的核心设计思路极其简洁。他们把 Linear——也就是他们用的项目管理工具——变成了整个编码工作的控制平面，你可以理解为调度中心。具体逻辑是这样的：Linear 上每一个处于开放状态的 issue，都对应一个正在运行的 agent 工作空间。Symphony 持续监视这个任务看板，确保每一个活跃任务都有一个 agent 在跑，直到完成。如果某个 agent 崩溃了或者卡住了，Symphony 会重启它。如果有新任务出现，Symphony 会捡起来，开始安排执行。

他们把 Linear 的 issue 状态设计成一个状态机。"待办"状态意味着还没有 agent 分配；"进行中"意味着 agent 正在工作；"审核中"意味着 agent 已完成，等待人工 review；"合并中"意味着 PR 正在走 CI 流程；"已完成"意味着工作落地了。每个状态之间的转换由 Symphony 驱动，agent 来执行，人只在关键节点介入审查。这就把原来那个"工程师盯着会话"的模式，彻底翻转成了"人盯着结果、系统盯着过程"的模式。

这个设计带来了一个非常重要的副作用：工作从会话里解耦出来了，也从单个 PR 里解耦出来了。原来你对着一个 Codex 会话工作，会话和任务是绑定的，会话崩了任务就中断了，而且每个任务只能对应一个 PR。现在不一样了，任务是独立存在的实体，哪个 agent 来执行是可以替换的，而且一个 issue 可以产生多个 PR，分布在不同的仓库；也可以根本不产生任何代码，就是一个纯粹的调研分析任务。

这个解耦之后，ticket 能代表更大颗粒度的工作单元。文章里举了一个很好的例子：他们会提交一个任务，让 agent 先去分析整个代码库、分析 Slack 里的讨论、分析 Notion 文档，然后产出一份实施方案。人类 review 这份方案之后，agent 再根据这份方案生成一棵任务树，把大工作拆解成多个阶段，并定义阶段之间的依赖关系。

这里就涉及到了一个特别精妙的设计：DAG 执行。DAG 是 Directed Acyclic Graph 的缩写，中文叫有向无环图，是计算机科学里描述有依赖关系的执行顺序的经典模型。在 Symphony 的语境里，它意味着 agent 只会开始执行那些"前置任务已完成"的任务，执行顺序自然涌现出来，而且能够自动并行。文章里给了一个具体的例子：他们在做 React 升级，但 React 升级依赖于先迁移到 Vite，因为 React 新版本和旧的构建工具有兼容问题。他们把"React 升级"这个 issue 标记为"阻塞于 Vite 迁移"。结果正如预期，agent 们是在 Vite 迁移完成之后才自动开始动 React 升级的，整个过程没有任何人为干预，顺序自动正确。

想象一下如果是人工管理这件事，你需要记住这个依赖关系，每天早上来了先看看 Vite 那边搞好了没有，再决定 React 那边要不要开工，还要跑去通知相关的工程师。现在你根本不用操这个心，系统自己知道。

更有趣的是，agent 自己也可以创造新任务。在实施过程中或者 review 阶段，agent 经常会注意到超出当前任务范围的改进机会——一个性能问题、一个重构机会、一个更好的架构方向。在老的工作方式下，agent 要么跑偏去搞这些不相关的东西，要么完全忽略掉它。现在的做法是：agent 直接在 Linear 里提一个新的 issue，人类来评估这个 issue 值不值得做、什么时候做，然后由后续的 agent 来执行。agent 保持专注在自己当前的任务上，但也不会让潜在的改进机会在空气里消散。

Symphony 特别适合大型 monorepo。文章里提到 OpenAI 内部有一个很大的 monorepo，在这类仓库里，让一个 PR 最终落地是一件慢而脆弱的事情——CI 可能需要跑几十分钟，主分支可能在你合并之前又有人提交了，产生了冲突，某些 flaky test 随机失败，需要重试。这些繁琐的最后一公里工作，以前都需要工程师手动处理。Symphony 会全程监视 CI 状态，在需要的时候自动 rebase，自动解决冲突，自动重试那些随机失败的检查。等一个 ticket 到达"合并中"这个状态，他们对这个改动能顺利进主分支的信心已经非常高了，不需要人在旁边守着。

作者们对工作模式变化的描述特别值得记住：探索的经济学改变了。原来你要做一个实验性的探索，你需要自己亲自去驾驶 Codex 会话，这有时间成本和注意力成本，每一次探索都是你个人注意力的投入。现在你只需要在 Linear 上开一张 ticket，描述你想探索的方向，agent 去跑，你来看结果，不喜欢就扔掉。失败也是有价值的信息，而成本几乎为零。

这个逻辑甚至改变了谁可以发起工作。文章里说，他们的产品经理和设计师现在也可以直接往 Symphony 里提 feature request 了。他们不需要知道怎么 checkout 代码仓库，不需要懂 Codex 怎么操作，只需要描述他们想要的功能。然后他们会收到一个 review 包，包里有一段视频，演示这个功能在真实产品里跑起来的样子。这对一个工程组织来说是相当深刻的变化。原来产品决策和工程实施之间有一个翻译成本，PM 需要给工程师讲需求，工程师需要理解 PM 的意图，然后才能开始做。现在这个翻译成本大幅降低了，PM 描述想要什么，agent 直接给出一个可以看的结果。

来说说 500% 这个数字背后的含义。某些团队在引入 Symphony 的头三周里，合并的 PR 数量增长了五倍。你可能会以为这是因为每个 PR 写得更快了，但实际上更重要的原因是：发起工作的认知成本下降了，大量原来因为"感觉不值得专门开一个会话来做"而被搁置的小任务和改进，现在都可以轻松地提成 ticket 让 agent 去搞。过去那种"这个改动有价值但不值得我花半天时间"的任务，现在的成本是一两分钟在 Linear 上写一条 issue。这种边际成本的下降，直接解锁了大量原本被搁置的价值。

好，现在来说说 Symphony 是怎么被建出来的，这里有一个迷人的自指逻辑。

第一个版本的 Symphony 非常简陋：就是一个 Codex 会话跑在 tmux 里，轮询 Linear，看到新任务就派一个子 agent 去处理。管用，但不稳定。第二个版本集成进了他们主项目仓库，利用了已有的 agent harness 基础设施。等基本功能有了，他们就用 Symphony 来继续开发 Symphony 本身。这个自举的过程很迷人——系统到了一定成熟度之后，开始给自己派任务、给自己写代码、给自己修 bug。

在 OpenAI 内部演示时，大家看到 Symphony 自己在管理任务、自动附上 proof-of-work 视频，反应非常正面。各个团队有机地自发采用了这个系统，没有人强推。文章里提到 OpenAI 内部的一个原则：内部的产品市场契合度是对外发布的前提。正是这个有机的内部增长，让他们决定把 Symphony 开源出来。

开源之前，他们做了一件事：把系统里所有对内部基础设施的依赖剥离掉，把核心思路提炼成一个独立的 SPEC.md 文件，然后让 Codex 来实现它。参考实现用的是 Elixir。Elixir 是一个相对小众的语言，基于 Erlang 虚拟机，以并发处理和高容错性著称。在通常情况下，一个团队不会轻易选择小众语言，因为招聘、维护、社区支持都会成为问题。但文章里有一句话说得很直白：当代码本身实际上是免费的，你终于可以根据语言的真实优势来选语言了。Elixir 天生就是为大量并发进程的管理和监督而设计的，有进程崩溃了能自动重启，高可用性是它的核心特性。这正好是 Symphony 需要做的事情——管理一堆并发运行的 agent 进程，有 agent 挂了要重启，要保证系统全天候稳定运行。用 Elixir 来做这件事，比用 JavaScript 或者 Python 自然得多。

他们还做了一件很有意思的事情来打磨 SPEC.md：让 Codex 分别用 TypeScript、Go、Rust、Java、Python 实现了一遍 Symphony。目的不是验证实现质量，而是用多种实现来检验规范本身的严密性。当某个细节在五种语言里有四种实现方式不同时，说明规范在这里有歧义，需要澄清。每种语言都实现成功了，这个过程帮助他们移除了大量的含糊表述，让规范更加精确。

还有一个技术细节值得专门讲一下：Codex App Server 模式。传统上用 Codex，要么通过网页界面，要么通过命令行，这两种方式都是为人类交互设计的，不适合程序化调用。Codex App Server 是一个无界面的运行模式，提供了一套有文档的 JSON-RPC 接口——JSON-RPC 是一种轻量级的远程调用协议，让程序之间可以互相发消息、调用功能——可以用来程序化地开启会话、发消息、响应 agent 的输出。Symphony 就是通过这个接口来和 Codex 通信的，而不是模拟键盘输入或者解析终端输出，后者那种方式极其脆弱，稍微有一点界面变化就会崩。这让整个系统的稳定性和可扩展性有了质的提升。

文章里还提到了一个安全设计：动态工具调用。为了避免把 Linear 的访问凭证暴露给子 agent，他们通过动态工具调用的方式，暴露了一个执行 Linear 查询的函数接口，但真正的凭证由 Symphony 的主进程持有，子 agent 拿到的只是调用这个接口的能力，拿不到凭证本身。这是最小权限原则的一个具体应用，在多 agent 系统里非常重要，一旦某个子 agent 被注入了恶意指令，它能造成的破坏范围是受限的。

好，现在来聊聊实践层面的内容。如果你今天就想把这套思路用起来，需要关注哪些事情？

第一，最低成本的入口是直接去看 Symphony 的开源仓库，核心就是那个 SPEC.md 文件。OpenAI 明确表示，他们不打算把 Symphony 维护成一个独立产品，提供的是参考实现。但这不意味着你无法上手，恰恰相反，你完全可以把 SPEC.md 发给你自己用的 coding agent，让它根据这个规范实现一个适配你自己工作流的版本。文章里说，他们希望大家这么做，就像之前很多开发者把 harness engineering 的博客发给 agent 让它帮忙搭建 agent 友好型仓库一样。spec 在，实现不重要。

第二，在引入这类 agent 编排系统之前，你的基础设施必须先达到一定成熟度。你需要有完善的自动化测试，覆盖率要高，agent 能通过跑测试来验证自己的修改是不是对的。你需要有 end-to-end 测试，可以驱动浏览器或者 app，验证 UI 行为是否符合预期。你需要有清晰的文档，特别是描述开发工作流的文档——文章里他们叫 WORKFLOW.md——告诉 agent 从拿到 issue 到提 PR 到处理 review 意见，标准流程是什么。这个东西的关键不在于内容多复杂，而在于它要存在。文章里特别指出，这个工作流原来是每个工程师都默默知道的隐性规则，没有人写下来过。Symphony 迫使他们把这些隐性规则显式化，这本身就是一件很有价值的事情。而且，如果你之后想在工作流里加一个新步骤，比如让 agent 在完成工作后附上一段自我反思，你只需要更新 WORKFLOW.md，Symphony 自然就会引导 agent 遵循。你还需要有 CI 流水线，而且 CI 日志要对 agent 可读，让 agent 能独立诊断构建失败的原因并自己修复。如果这些基础设施不到位，agent 会经常失败，而且你分不清楚是 agent 的问题还是基础设施的问题。

第三，要想清楚什么任务适合委托给 Symphony，什么不适合。适合的是目标相对明确、可以拆解成独立子任务、可以通过自动化测试验证正确性的工作：常规的功能实现、依赖升级、代码重构、有明确复现步骤的 bug 修复、文档更新、数据库迁移、大规模的代码格式化或者 lint 修复。不适合的是那些高度模糊、需要强判断力的工作：当你需要在两个根本性的架构方向之间做决策，当你在调试一个极其诡异的非确定性 bug，当你需要和外部利益相关方不断沟通来定义需求。文章里也诚实地说了，这类任务往往恰恰是工程师们觉得最有意思、最有挑战性的工作，Symphony 让他们有时间和空间专注在这些地方。

第四，要建立正确的 review 文化。从亲自驾驶 agent 到委托 agent 干活，review 的性质变了。原来 review 的时候，你对每一行代码的来龙去脉了如指掌，因为是你一步步引导 agent 写的。现在你看到的是 agent 独立完成的成果，你看到输出，不知道过程。这要求你更加依赖测试和文档来弥补对过程的缺失。文章里提到 Symphony 会生成 proof-of-work 包，包括视频演示，让 agent 演示它做的东西跑起来的样子。这是一个非常好的实践，大大降低了 review 的认知成本，你看视频就知道功能是不是对的，不需要自己去跑起来验证。

第五，也是最重要的：不要等基础设施完美了再开始。Symphony 的第一个版本就是一个跑在 tmux 里的 Codex 会话，粗糙但有效。他们先把核心循环跑起来，然后根据真实遇到的问题逐步迭代，加稳定性、加功能、加护栏。文章里也提到，他们在 agent 失败时不是手动修补结果，而是回头加护栏和能力，让 agent 下次能自己成功。这是一个很健康的迭代路径：失败是信号，信号指向投资方向。找一个最小化可行的切入点，用起来，然后根据遇到的具体问题来迭代。

好，来收尾了。

这篇文章传递的最核心信息，我认为有三层。第一层是技术层面的：agent 编排不需要复杂的框架，一份写得好的规范文档加上合适的工具，就足够让事情运转起来。Symphony 的核心是 SPEC.md，不是 Elixir 代码。第二层是工程文化层面的：当代码的边际成本趋近于零，软件工程的工作方式会根本性地改变，工程师的价值越来越体现在判断力、探索力和架构设计上，而不是实现本身。第三层是组织层面的：人类工程师最稀缺的资源是注意力，不是时间。好的系统设计应该保护工程师的注意力，让他们专注在真正需要深度思考的地方，而不是被分散在无数个需要随时盯着的会话上。

我个人认为，Symphony 的 SPEC.md 模式是一个非常值得借鉴的设计哲学。不是写代码，是写规范。让 agent 来选择怎么实现。这种思维方式在 AI agent 能力不断提升的背景下，可能会成为越来越多工程工作的核心范式。你今天写一份好的规范文档，明天能力更强的 agent 会给你一个更好的实现。而如果你今天写了一个具体实现，你就被这个实现锁住了，模型进步的红利不会自动落到你头上。从这个角度看，Symphony 不只是一个 agent 编排工具，它是一种新的工程方法论的早期样本。
