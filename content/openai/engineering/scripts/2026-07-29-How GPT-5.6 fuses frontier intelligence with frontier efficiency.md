推理栈是什么？简单来说，就是模型训练好之后，怎么把用户的问题接收进来、跑出答案、再返回给用户的这一整套系统。听起来好像就是"把问题传进去跑一遍"，但工程上极其复杂。文章里列了好几个层面的优化，我来逐个拆解。

第一个优化方向是负载均衡，英文叫 load balancing。

你可以把 OpenAI 的推理系统想象成一个超大型的全球外卖调度中心。全球有无数用户同时在发请求，这些请求需要被精确分配到各个数据中心的 GPU 集群去处理。如果调度做得好，每台机器都在满负荷高效运转；如果调度做得差，有些 GPU 忙到过热、有些在闲着发呆，整体效率就会低很多，同样的硬件能服务的用户数量就少了。

OpenAI 的负载均衡分三个层次。第一层是全局路由，根据地理位置、可用容量和 GPU 的类型来决定请求应该发往哪个数据中心。第二层是集群内分配，根据当前负载情况、请求的上下文长度、缓存命中情况来决定把工作派给哪个模型实例。第三层是实例内部，负责把具体的计算工作细分到不同的加速器核心上去。每一层都有调度策略，每一层的调度策略都影响着整体成本和效率。

文章说，他们用 GPT 五点六 Sol 跑在 Codex 这个编程 agent 工具里，来分析真实的生产流量数据，识别出以前被工程师忽视的不均衡来源，测试新的路由策略，并且持续调整这些调度规则。就凭负载均衡这一项优化，就大幅降低了模型的服务成本。文章用了 dramatically 这个词来描述效果。

这里我想停下来强调一件非常重要的事：GPT 五点六 Sol 在这里扮演了一个双重角色——它既是被优化的对象，也是执行优化工作的工具本身。是 Sol 跑在 Codex 里分析流量数据、写路由策略代码、设计实验方案。这个"模型来优化自己运行基础设施"的循环，是整篇文章最让我觉得意味深长的设计。我们在后面几个优化里还会反复看到这个模式。

第二个优化是 kernel 优化，也就是对 GPU 计算核心程序的优化。

我先解释一下什么是 kernel。GPU 在执行神经网络计算的时候，底层运行的是一段段高度特化的小程序，这些程序就叫做 kernel，也可以叫核函数。可以把它们想象成一条工厂流水线上每个工位的详细操作规程：第一个工位负责做矩阵乘法，第二个工位负责计算激活函数，第三个工位负责注意力机制的计算。这些操作规程写得好不好，直接决定了每个工位的效率和产出。如果规程写得冗余，哪怕原材料足够好、机器也足够先进，流水线整体还是跑不快。

文章说，即使单个操作已经很快，多余的内存搬运、线程之间的同步等待、低效的数据排列方式，都会让 GPU 白白空转。GPT 五点六 Sol 的任务，就是找到哪些计算可以预先完成、哪些可以直接跳过、哪些可以并行同时执行，然后重写生产环境里使用的核心 kernel 代码。

更有意思的一层设计是，OpenAI 还专门在训练 GPT 五点六时，让它学会用两种 GPU 编程语言来写 kernel。一种叫 Triton，是 OpenAI 自己维护的开源 GPU 编程语言；另一种叫 Gluon，也是他们开发的类似工具。这两种语言都是为了让编写 GPU 计算程序这件事，比直接用底层的 CUDA 语言更高效、更容易维护。所以这里有一个非常精妙的嵌套关系：他们专门训练 Sol 学会写 GPU 程序，然后让 Sol 去帮他们重写运行 Sol 自身的那些 GPU 程序。本质上，是用一个更聪明的 Sol 在优化让 Sol 运行起来的基础设施。

这些 kernel 优化，加上更广泛的相关改进，把端到端的推理服务成本降低了百分之二十。对于一个在全球规模服务十亿用户的系统来说，百分之二十的成本降低是一个极其可观的数字，换算成真实的硬件费用节省是天文数字级别的。

当然，让模型去改动生产环境里的核心计算代码，正确性和安全性是第一大问题。文章提到，他们为此开发并开源了一个叫 FpSan 的验证工具，全称是 Floating-Point Sanitizer，可以叫做浮点数清理器。浮点数运算非常容易出现精度损失、数值上溢或者下溢之类的问题，如果 kernel 代码里有这类错误，模型的输出就会出现数值异常，轻则给出奇怪的答案，重则直接崩溃。FpSan 的作用就是在 Sol 写出 kernel 代码之后，系统性地验证这些代码在数值计算上的正确性。有了这层自动化验证，他们才敢把模型生成的 kernel 代码部署到真实的生产环境里。

第三个优化是投机解码，英文叫 speculative decoding。

这个技术的原理有点像"猜测加验证"的游戏。我们知道大语言模型生成文本的方式是逐个 token 地生成，每次生成一个 token 都需要完整地跑一遍模型的前向传播，计算量非常大，而且这个过程本质上是串行的，一个接一个，等一个 token 出来了才能开始算下一个。那有没有办法一次主模型的计算产出多个 token，而不是每次只出一个？

投机解码的思路是这样的：在主模型旁边，同时运行一个小得多的草稿模型，也叫做 speculator，让它用非常低的成本快速猜出接下来几个 token 可能是什么；然后把这几个候选 token 打包交给主模型，让主模型在一次前向传播里同时验证这几个猜测是否正确。如果草稿模型猜对了，主模型就直接接受，相当于一次主模型的计算产出了多个 token；如果猜错了，就从第一个错误的位置重新生成。整体来看，因为草稿模型非常轻量、速度极快，而主模型只需要做并行的验证工作而不是每次都顺序生成，整个系统的吞吐量就大幅提升了。

你可以这样来想象：主模型是一位资深编辑，每看一眼稿子都要花很大精力；草稿模型是一位实习生，快速草拟几句话出来；然后编辑快速扫一眼，哪些对就接受，哪些不对就从那里重写。只要实习生的命中率够高，整个工作流的效率就会大幅提升。

文章里说，GPT 五点六 Sol 参与设计并运行了数百个实验，测试草稿模型的大小、结构和各种特性组合，找到最优的配置方案。不仅如此，Sol 还自主启动并监控了草稿模型的整个训练过程，当出现硬件故障或者训练不稳定的情况时，Sol 会自主干预解决，而不是等工程师来处理。最终这些改进让 token 生成效率提升了百分之十五以上。百分之十五意味着什么？用同样的硬件，可以多处理将近六分之一的额外请求，或者等量地降低运行成本。在 OpenAI 这个规模上，这个数字背后是非常真实的资源节省。

第四个优化是 KV 缓存的精细化配置管理。KV 缓存，全称是 key-value cache，键值缓存，是大语言模型推理中最核心的中间产物之一。

当模型处理输入 token 的时候，它会为每一个 token 计算出一对向量，分别叫做 key 和 value，这两个向量在后续生成每一个输出 token 的时候都会被反复读取和参考。如果把这些向量存在缓存里，后续生成就不需要重新计算它们，能大幅减少计算量。你可以把它想象成做研究时的读书笔记：你精读一本书的时候做了详细笔记，之后回答相关问题就不用重新翻书，直接查笔记就行了；如果没有笔记，每次答题前都要重读一遍书，那效率就很低。

但问题来了：KV 缓存的最优配置高度依赖于具体的工作负载特征。输入有多长、输出有多长、同时处理多少条请求、缓存命中率是高是低——这些因素不同，最好的批处理策略、内存分片方式、缓存管理逻辑都不一样。以前这个配置参数空间太大，工程师只能靠经验估一个大致的通用规则来应付所有场景，做不到针对每种实际工作负载精细调优。

有了 GPT 五点六 Sol 在 Codex 里帮忙之后，他们现在可以系统性地分析真实生产流量的实际特征，自动生成候选配置方案，评估不同配置在真实工作负载下的实际表现，然后针对每一类场景做超精细化的调优。这让从同样硬件里榨出的有效推理产出，达到了以前靠人工调优做不到的水平。

这四个方向综合起来——负载均衡、kernel 优化、投机解码、KV 缓存配置——就是推理层效率提升的全貌。文章里有一句话我非常认同：任何一项单独的改进看起来可能都有限，但这些收益会像复利一样叠加起来。一个百分之二十、一个百分之十五、再叠加负载均衡和缓存配置的优化，累积下来对整体成本和性能是非常显著的影响。

好，推理层讲完了，我们来聊第二个大主题：智能体编排层，也就是 agentic harness。

文章说，这个编排层是用 Rust 这种系统级编程语言写的编排框架，连接着模型、工具，和用户的工作环境。ChatGPT Work 和 Codex 都运行在这个框架之上。

为什么 agent 场景对效率的要求特别高？一个普通的单轮对话，用户发一条消息，模型回一条，就结束了，成本很低。但一个复杂的 agent 任务可能需要几十次模型调用：检查源代码、搜索历史部署记录、读取故障报告、修改文件、跑测试……每一步都是一次独立的请求，每次请求都要经历准备上下文、传输数据、跑推理、调用工具、处理结果这一整套流程。文章举了一个例子：如果一个任务需要三十次模型请求，每次多一秒钟，加起来就是多半分钟；如果每次请求多消耗额外的 token，三十次下来成本就翻倍甚至更多。这个乘数效应，让 agent 场景下的效率优化比普通的单轮对话重要得多。

编排层主要做了两个方向的优化，我分别来讲。

第一个叫做延迟工具发现，英文是 deferred discovery。

随着 agent 被授权访问越来越多的工具、插件、技能和历史对话记录，上下文窗口会很容易急剧膨胀。你想象这样一个场景：如果每次 agent 开始工作，都要把所有可用工具的完整定义全部塞进上下文，哪怕这次任务只用到其中两三个工具，那剩下几十个工具的定义全都是纯粹的浪费。这不只是浪费 token 费用，还会占用模型宝贵的注意力资源，让它面对大量和当前任务完全无关的信息，可能产生不必要的推理分支，甚至干扰它对真正重要的信息的判断。

延迟发现的思路是：工具不需要一开始就全部亮出来，只有当编排层或者模型自身判断某个工具在当前任务阶段可能被需要时，才把那个工具的定义加入上下文。自定义的 MCP 工具、各种插件、技能模块，默认都是按需出现的，而不是默认全部加载进来。同时，单个工具的输出也要受到约束。文章说，工具的输出默认被限制在一万个 token 以内，除非模型明确请求更高的上限。这防止了某一个数据密集型工具一次性返回大量内容把整个上下文窗口直接撑爆的情况。

第二个优化是关于 prompt 缓存命中率的精细设计，这里有几个非常巧妙的工程细节。

在一个 agent 任务的执行循环里，同样的系统指令、同一段对话历史、同一批工具定义，可能在单次任务的多轮模型调用里被反复发送给 GPU 处理。处理这些重复内容既浪费算力，也增加直接的 token 费用。Prompt 缓存的原理是：如果当前请求的前缀部分和之前已经处理过的某个请求的前缀完全相同，就可以直接复用之前的计算结果，完全不需要重新跑一遍，大幅节省成本。

但要实现高命中率，必须保证请求的前缀真的是一模一样的。哪怕只有一个 token 的差异，缓存就会失效，之前的计算就白费了。所以编排层在设计上做了几件精心安排的事情。

第一，所有模型能看到的历史记录，都以只追加的方式来处理。新消息、工具调用结果、环境状态更新，全部添加到上下文的末尾，绝对不会插入到之前内容的中间。这样前缀部分永远保持固定，不会因为任何插入操作导致缓存失效。

第二，工具的呈现顺序是确定性的。每次发给模型的请求里，工具定义的排列顺序不会随机变化，而是始终按照固定的、可预期的顺序出现。这样工具定义这一块的 token 序列在多次请求之间是稳定的，缓存命中率自然更高。

第三，运行时的一些配置，比如各种审批策略，是在执行阶段动态应用的，而不是直接硬编码进工具定义里。这样工具定义本身保持稳定一致，不会因为不同运行时配置的差异而导致每次请求都出现一个略微不同的 prompt 前缀。

这三个设计放在一起，形成了一套让 prompt 缓存命中率最大化的完整工程方案，最终让 Codex 和 ChatGPT Work 的整体缓存命中率维持在很高的水平，从而在不降低输出质量的前提下，大幅降低了 agent 场景下的单次任务成本。

好，技术部分讲完了，我们来聊聊这对实际工作的具体启示。

如果你是一个在用 OpenAI API 做应用开发的工程师，GPT 五点六给了你三个清晰的选择档位，正确的策略是针对不同任务类型分别评估这三个模型的效果和成本。Sol 适合那些需要最强推理能力、对输出精度要求极高的任务，比如复杂代码重构、深度研究分析报告、需要多轮逻辑推演才能解决的架构设计问题；Terra 适合绝大多数日常工作流场景，比如文档撰写、代码审查、内容生成，是性价比最优的起点；Luna 适合高吞吐、对延迟敏感、任务相对明确的批量处理场景，比如批量文本分类、快速摘要生成、简单问答系统。

一律用最贵的 Sol 会让你的 API 账单快速爬升，一律用最便宜的 Luna 可能在需要推理的任务上质量明显不达标，两种极端都会造成浪费。最好的做法是用较小的任务样本在三个模型上都跑一遍，对比质量和成本，再做决策。

如果你在构建自己的 agent 系统，不管是基于 OpenAI 的还是其他任何平台的，prompt 缓存命中率是一个值得认真对待的工程目标。文章里描述的几个设计原则——历史只追加不插入、工具定义顺序固定、运行时配置不写死在 prompt 里——这些是通用的 agent 架构最佳实践，不是 OpenAI 专有的，你完全可以把这些原则带回到自己的系统里去。

举一个具体的例子。如果你在做一个客服 agent，每次对话开始时你可能会往系统 prompt 里放用户的账户信息、当前活动详情、最近的订单记录。如果这些内容每次对话都不一样，前缀就永远无法命中缓存。一个更好的做法是：把固定不变的指令部分放在前缀最开头，把随用户变化的动态内容放在后面的用户消息里。固定部分可以享受缓存复用，只有动态部分需要每次重新计算，整体成本就能下降很多。

工具数量的管控也是一个容易忽视的点。很多开发者在做 agent 的时候，喜欢把所有可能用到的工具全部注册进来，觉得工具越多 agent 就越强大。但这篇文章告诉我们，工具太多会膨胀上下文、分散模型注意力、干扰它的判断。更好的做法是按照使用场景把工具分组管理，在不同的任务阶段动态加载对应的工具集，而不是把所有工具都在每次请求里一股脑全放进去。这个思路和 OpenAI 的 deferred discovery 设计是完全一致的。

文章结尾有一句话说得很克制，但含义很深：他们对 Sol 在优化中扮演的角色感到乐观，因为这会加速优化本身的节奏。背后的逻辑是：每一代更强的模型，都会更有效地帮助优化下一代的基础设施；而下一代更强的模型，又会进一步加速优化的速度。这是一个自我加速的飞轮，一旦真正转起来，它的加速度只会越来越高。
