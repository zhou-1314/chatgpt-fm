文章来自 OpenAI 研究团队，英文标题是 Separating signal from noise in coding evaluations，我把它翻译成"在代码评测中分离信号与噪声"，发表于二〇二六年七月八日。距今大概两个月，不算久远，但这篇文章讨论的问题会在相当长的时间内影响整个 AI 行业的走向。

文章的核心结论只有一句话：AI 编程能力领域最主流的基准测试之一，SWE-Bench Pro，经过 OpenAI 的严格审查，大约三成任务是有根本性缺陷的。

你可能会想，一个基准测试有点缺陷，这有什么大不了的？但当你想清楚这意味着什么，就会明白这件事的严重性。模型在 SWE-Bench Pro 上的通过率，是判断它代码能力强弱的重要依据，这些数字会影响研究方向的选择、产品选型的决策，甚至 OpenAI 内部的安全部署判断。如果评测本身就是扭曲的，那所有基于这些数字做出的判断，就建立在一个有问题的地基上。这不是学术问题，这是会影响真实决策的基础设施层面的问题。

我们先来聊聊背景，理解为什么这个问题会发生，又有多大。

在 AI 领域，评估模型能力靠的是基准测试，英文叫 benchmark，你可以把它想象成一套标准化考试卷。就像高考可以相对客观地评价一个学生的语文数学水平，基准测试可以相对客观地告诉我们某个 AI 模型在某类任务上表现如何。代码能力尤其适合这种标准化评测，因为代码结果相对客观——要么测试通过，要么不通过，没有太多主观解释的空间。

SWE-Bench 这个系列评测正是基于这个思路。SWE 是 Software Engineering 的缩写，也就是软件工程。SWE-Bench 的核心思路是从真实开源代码仓库的历史记录里，取出一些 GitHub 的 issue——也就是代码问题报告——和对应的 pull request——也就是解决这些问题的代码提交——然后让 AI 来解决这些真实存在过的 bug 或功能需求，用仓库里原有的单元测试来判断模型的解法是否正确。

这个思路从设计上来说非常合理，数据来自真实世界，不是人为凑出来的题目，理论上应该能很好地反映真实的工程能力。但问题就出在这个"真实世界"本身。

在此之前，OpenAI 曾经发现 SWE-Bench Verified——也就是 SWE-Bench 的一个经过人工筛选的版本——已经出现了严重的设计缺陷和数据污染问题，基本上不能再提供有意义的评测信号了。他们当时建议大家转向 SWE-Bench Pro。

SWE-Bench Pro 是专门为了解决前一个版本的问题而设计的新版本。它的任务更长、更复杂，更接近真实软件工程师日常工作的场景，目的是更好地追踪 AI 智能体——也就是 agent——在编程方面的能力上限。具体来说，在七百三十一个公开任务上，前沿模型的通过率在八个月内从百分之二十三点三飙升到了百分之八十点三。这个进步速度非常惊人，让很多人相信 AI 的代码能力真的在以几乎垂直的曲线提升。

然后，OpenAI 对这个新版本做了类似的深度审查。结果发现：大约三成任务存在根本缺陷。而且他们同时撤回了此前推荐使用 SWE-Bench Pro 的建议。

这就引出了今天的核心：他们是怎么发现这件事的，问题具体出在哪里，又意味着什么。

我们先来看审查方法。OpenAI 建立了一个三层质量保证流程，越深入越精细。

第一层是自动化过滤。他们用程序化的方式，对每一个任务的所有相关信息进行扫描：模型收到的任务指令是什么、模型尝试解决任务时产生的代码是什么、用来给模型打分的测试用例是什么，还有模型失败时的报错追踪记录。通过这些信息，程序自动标记出那些看起来可能有问题的任务。结果是，七百三十一个任务里，有二百八十六个被标记为可能有问题，比例将近四成。这说明问题不是零星偶发的，而是相当普遍的。

第二层是 AI 调查员智能体的深度审查。对于第一层筛出来的可疑任务，他们用基于 Codex 的调查员智能体来做更深入的分析。Codex 是 OpenAI 专门针对代码任务优化的 AI 系统。这些智能体被赋予了真实的工作权限：可以访问对应的代码仓库，可以运行测试，可以读取文件，可以分析模型的失败案例，看失败是偶发的还是系统性的。

这些智能体要做的核心判断是区分两种情况。第一种是合理的模糊性，也就是说题目描述虽然不够精确，但如果仔细研究代码仓库的上下文和惯例，是可以推断出正确解法的，这种情况下题目本身没有根本问题。第二种是真正的缺陷，也就是题目本身存在根本性问题，不管模型多努力，也无法给出一个同时满足题目描述和测试要求的解法。

每个被审查的任务，会经过多次独立的智能体分析，最后由人类研究员汇总判断，给出最终标签。

第三层是人工标注活动。与此同时，他们专门组织了一批有丰富经验的软件工程师，对被标记的任务做人工审查。每个任务由五名工程师独立评审。在正式审查之前，这些工程师接受了专门培训，了解这个基准测试的设计目标、问题的分类体系和各种边界情况。

评审流程有个重要细节：评审员必须先根据题目描述、测试用例和参考答案，自己独立形成判断，然后才去看 AI 智能体的分析报告作为辅助参考。这样设计是为了防止人类被 AI 的结论带偏，保证人工审查的独立性。他们要给任务打上问题类别标签和严重程度评级，如果五个人意见分歧很大，或者有人信心不足，就会升级到进一步审查。

这套流程结合了规模和深度：自动化过滤处理全部七百多个任务，AI 智能体审查处理近三百个可疑任务，人工标注则对这些可疑任务做最终裁定。这种分层方式既保证了覆盖率，又保证了关键判断的准确性。

好，我们来看他们发现的四类核心问题。我会用类比来解释每一类，方便你在通勤路上建立直觉。

第一类：测试标准过严。

你可以想象这样的场景。你参加一个编程面试，题目要求是实现一个函数，对一个列表进行排序并去重。你写了一个完全正确的解法，逻辑无懈可击，功能完全实现。但面试官给你判了不及格，原因是你的输出顺序和他们预设的参考答案不完全一样——他们期待的是一种特定的保序去重算法，而你用了集合去重然后排序。你的结果在功能上是对的，但在实现细节上和他们的答案不一样，所以失败了。

这就是测试过严的问题。原始 GitHub pull request 里的测试，是为了验证那个特定的代码提交而写的，它检查的是具体的实现细节，而不是功能本身的正确性。但当这个测试被拿来评测 AI 时，只要模型的解法和原始实现的细节不完全一致，就会判定失败，哪怕模型的解法在功能上完全正确，甚至更简洁更优雅。

这个问题在从真实代码库提取数据的基准测试里非常普遍。根本原因在于，当年写这些测试时，目的是"验证这次具体的代码提交"，而不是"定义一个与实现无关的功能正确标准"。两者之间存在本质差异，但在 SWE-Bench 的流程里，这个差异没有被处理干净。

第二类：描述不充分。

这类问题是说题目给的信息不够，模型不知道应该做什么，或者只能根据猜测来确定方向。

类比一下，想象你接到一个需求，产品文档上只写了"优化用户登录体验"，没有说具体是哪个登录入口、优化什么方面、什么是"好"的标准、有什么约束条件。你可能会做出一个你认为合理的改动，但这个改动和评分标准对不上号。

SWE-Bench 系列的数据来自 GitHub 上的 issue 和 pull request 讨论。很多关键信息是在维护者和贡献者来回讨论中逐渐明确的，这些讨论可能跨越了十几条甚至几十条评论。当这个讨论链被压缩成一个孤立的任务描述时，那些在对话中确立的隐含约束和具体期望就丢失了。模型没有参与那段人类之间的来回讨论，当然不知道最终决定了哪些没有写进正式题目的要求。

你可以想象这样的情形：可能在第七条评论里，维护者说了一句"我们要确保这个改动不影响 Windows 路径的处理逻辑"，这个约束从来没有进入正式的任务描述，但测试里有对应的检查。模型按照题目说的做，通不过那个检查，但这不是模型能力不足，而是题目本身没有把完整信息传达出来。

第三类：测试覆盖率不足。

这类问题是说测试只检查了功能需求的一小部分，导致不完整甚至有缺陷的解法也能通过测试，被判定为成功。

想象你写了一段排序代码，它对于正整数数组能正确运行，但对于包含负数或者重复元素的情况会给出错误结果。如果测试用例里只有正整数数组，你的代码会拿到满分，尽管它对于其他输入是错的。

在 AI 评测的语境里，这意味着模型提交了一个半吊子解法，只要碰巧满足了那几个不完整的测试，就会被评定为成功解决了任务。这会让模型的能力被高估，因为很多看起来的"通过"其实是利用了测试的漏洞，而不是模型真正理解并完整解决了问题。

在这个类别上，人工审查员和 AI 智能体之间的差距最大。人工审查员认为有百分之九点四的任务存在覆盖率不足的问题，而 AI 智能体只识别出了百分之四点一。这将近一倍的差距很说明问题。判断测试覆盖率是否充分，需要对功能需求有深入的理解，需要有能力主动想到"这个功能还有哪些情况应该被测试到"，这种工程直觉目前仍然是人类更擅长的领域。

第四类：误导性提示。

这是最让人抓狂的一类问题。题目描述明确指引模型去做一件事，但测试用例检查的是另一件事，两者之间存在矛盾。模型如果认真按照题目描述做，必然失败；但如果忽视题目描述而去猜测测试的真实意图，在逻辑上也是一件很奇怪的事情。

这类问题出现的典型情形是这样的：GitHub issue 里的原始描述提出了某个改动方向，但在 pull request 的多轮讨论过程中需求发生了变化，最终合并的代码和测试反映的是修改后的需求，而任务描述仍然保留了原始 issue 的表述。于是模型拿到的题目是前后矛盾的，按照描述做不对，按照测试的隐含要求做又需要忽视描述，陷入两难。这对模型来说极不公平，它的失败不是能力问题，而是信息本身就是错的。

这四类问题，都指向同一个根源：数据是从人类协作过程中程序化提取的，而人类协作天然充满了上下文依赖、隐含约定和动态变化，这些特质很难被干净地打包成孤立的评测任务。

我们来看人工审查和 AI 审查之间的系统性差异，这部分也很有意思。

总体来看，两者在问题类别判断上的重叠率是百分之七十四，也就是大约四分之三的情况判断一致，这个一致性算不错。还有一个关键数据：在第一层自动化过滤标记出来的所有可疑任务里，没有任何一个任务，是"没有问题"被人工审查员判定为最常见结论的。也就是说，凡是自动化过滤认为有问题的任务，人工审查也都确认至少存在某种问题，误报率很低。

差异主要体现在两个方面。第一，人工审查员更倾向于给同一个任务打多个标签，也就是同时识别出多个维度上的问题，而 AI 智能体倾向于选出最突出的一个类别。这说明人工审查捕捉到了更细腻的问题叠加情况，而 AI 智能体的标记方式更为保守，不会过度判定。第二就是覆盖率不足那个类别的差距，人工识别出百分之九点四，智能体只发现了百分之四点一。

这个对比揭示了一个很有价值的工程结论：AI 智能体作为规模化初筛工具效果不错，找出真实存在问题的任务准确率高；但它可能低估问题的复杂性和严重程度，对于需要深度工程直觉的判断类型，人类仍然有显著优势。三层结合的方式，是两者之间很好的平衡点。

现在我们来想一个更深层的问题：为什么这些问题会系统性地出现在从真实代码库提取的数据里？

GitHub 上的代码协作是一个充满人类语言模糊性和上下文依赖的过程。一个 issue 的描述可能非常粗糙，因为提问的人假设维护者有足够多的背景知识。一个 pull request 的讨论可能来回修改了七八次，最终合并的版本和最初的设想大相径庭。测试用例是在具体讨论中一边调整需求一边写的，它记录的是"这次我们决定这样处理"，而不是"这类问题的通用正确解法"。

这一切对于人类之间的协作来说完全自然，没有任何问题，人类在参与协作的过程中会自然积累上下文，理解那些没有明说的约定。但当我们把这些原始材料剪切出来、打包成孤立的评测任务时，那些依赖于上下文的隐含信息就丢失了。评测任务假设一个孤立的 AI 可以单独解决这道题，但这道题本身从来不是为了孤立解决而设计的。这就像把一段法庭庭审记录改编成一道中学阅读理解题，然后抱怨学生回答得不准确——问题可能不在学生，而在于原始材料本来就不适合这种用法。

文章里还提到了一个我认为非常值得关注的发现：随着模型能力的提升，现在可以用更强的模型来帮助审计评测数据本身了。

这是一种非常有趣的递归关系。以前，评测数据的质量审计只能靠人工，成本很高，速度很慢，覆盖率很低。七百多个任务如果全部靠人工仔细检查，是非常耗时耗力的。但现在，OpenAI 用 Codex 智能体当调查员，让它们访问代码仓库、运行测试、分析失败案例，实现了大规模的自动化审计，然后再把有疑问的部分交给人工做最终裁定。

你可以把这想象成：以前质量审查只能靠少数资深工程师一条一条地看，效率极低，覆盖率也有限；现在可以先让一批能干的 AI 助手把所有情况快速过一遍，标记出可疑的，再让资深工程师集中精力处理那些真正有疑问的案例。这不仅更快，而且因为 AI 的覆盖率很高，真正有问题但被漏掉的任务也少了很多。

这个能力是随着模型变强才成为可能的。两年前的模型没有办法像现在这样准确地分析代码、运行测试、理解报错信息、区分"合理模糊"和"真正缺陷"。这意味着，未来每一代更强的模型，都会让我们有能力更精确地审视这一代模型的评测数据质量。这是一种正向循环，但也需要我们有意识地把这个能力用到评测质量保障上，而不是只盯着模型本身的性能数字。

好，我们来说说这对你实际工作的意义，这是今天我最想让你带走的部分。

第一，对引用 SWE-Bench Pro 数字要更谨慎。OpenAI 已经撤回了推荐使用这个基准测试的建议。如果你在报告、方案或者技术文章里引用某个模型在 SWE-Bench Pro 上的通过率数字，需要加上一个重要注脚：这个数字的可信度现在有相当大的折扣，因为三成题目存在缺陷。一个模型得了百分之七十五，不代表它真的能正确解决百分之七十五的软件工程任务。它的真实能力可能更高，因为有些失败是因为题目本身有问题；但也可能被高估，因为有些通过是因为测试覆盖率不足而蒙混过关的。两个方向都有可能，这就是数字失真的本质——你没办法只靠这一个数字判断方向。

第二，任何评测数字都不等于真实能力，但这一点在 AI 快速迭代的今天尤其值得强调。当你在公司内部讨论要不要引入某个代码 AI 工具的时候，最可靠的判断来自在你自己的真实代码库上实际跑一跑，而不是看它在某个排行榜上的分数。不同公司的代码库有不同的特点，不同团队的工程规范不同，一个在公共基准测试上表现出色的模型，不一定适合你的具体场景，反之亦然。基准测试是一个参考维度，不是最终裁判。

第三，这套三层质量审查流程本身，是一个非常值得借鉴的工程模式。如果你负责数据质量、测试用例质量、或者内部评测体系的设计，可以考虑类似的分层策略：第一层用自动化工具做大规模粗筛，快速找出可疑案例；第二层用 AI 智能体做更深入的专项分析，区分不同类型的问题；第三层用领域专家做最终的人工裁定，保证关键判断的准确性。这种方式在效率和准确性之间取得了很好的平衡，而且随着 AI 工具本身变强，中间那一层的效果会越来越好，整体成本也会越来越低。

第四，文章里总结的四类评测缺陷，不只是 SWE-Bench Pro 的问题，也是你在设计任何评测体系或者测试套件时需要对照检查的清单。你的测试标准是否过于绑定了特定的实现方式而非功能本身？你的需求描述是否足够完整，还是隐含了太多的上下文假设，需要读者自己脑补？你的测试用例覆盖率是否真正测到了功能的各个边界情况，还是只测了最顺畅的主路径？你的任务描述和评分标准之间有没有矛盾或者误导？这四个问题，放到内部评测、集成测试，甚至日常代码审查的 checklist 里，都是有价值的检查项，不只是在做 AI 评测的时候才有用。

第五，如果你的团队在用 AI 工具自动生成测试用例，要特别注意检查这些测试有没有覆盖到边界情况。AI 生成的测试有时候会有类似的偏差——它会优先测试它认为"正常"的情况，而忽略那些奇怪的边界输入。这和 SWE-Bench 里低覆盖率测试的问题是同一类的。机器生成的测试需要人工的审查和补充，不能完全依赖。

第六，从更宏观的角度看，OpenAI 在文章里明确提到，这些评测结果会影响他们基于 Preparedness Framework——风险准备框架——做出的安全部署决策。这个框架决定了哪些模型可以被部署在哪些场景下，决定了某个模型的能力是否达到了需要特别谨慎对待的安全门槛。如果评测数据是扭曲的，安全评估就可能偏离现实，部署决策就可能基于错误的能力认知。这不只是一个技术问题，它触及到我们整个社会对 AI 系统安全性的判断基础。对于我们这些 AI 工具的使用者来说，这也是一个提醒：不要把所有信任都押在一套可能有缺陷的评测体系上，要建立对 AI 能力更立体、更来自实际使用经验的认识。

还有一点值得特别提一下。文章结尾，OpenAI 表达了一个明确的期望：希望评测社区开发新的基准测试，由有经验的软件工程师专门为测试模型能力而设计，而不是从现有的代码协作记录中程序化提取。这个方向意味着，未来更可靠的评测数据，可能需要从一开始就按照"这道题是给 AI 做的"这个目标来设计，而不是把人类协作的副产品重新包装一下。这是一个更高的成本和更高的门槛，但如果结果的可信度能因此显著提升，这个投入是值得的。

好，我们来做个收尾。

这篇文章的核心信息是：SWE-Bench Pro，当前 AI 代码能力评测领域最主流的基准测试之一，经过 OpenAI 严格的三层审查流程，被发现大约三成任务存在根本性缺陷。缺陷来自四个方向：过严的测试标准、不够清晰的任务描述、测试覆盖率不足，以及误导性的题目表述。OpenAI 已经撤回了推荐使用它的建议，并呼吁行业开发专门为测试模型能力而设计的新基准测试。

我个人认为，这篇文章最深刻的价值不只是揭露了一个具体的问题，而是揭示了一个系统性的困境：从人类协作过程中提取数据来评测 AI，本质上就存在错配的风险。真正可靠的评测，需要从一开始就为 AI 评测这个目的而设计，而不是把人类协作的副产品重新包装一下。这是一个需要整个行业共同面对的问题，不是单独一个数据集的问题。

同时，这篇文章也给了我一个令人振奋的信号：更强的模型不只是被评测的对象，也正在成为帮助我们更好地评测的工具。这种递归的自我校准能力，可能是未来 AI 评测体系迈向更可靠方向的重要路径。我们用更好的模型来审视模型的评测，这个循环如果能持续运转，整个行业对 AI 能力的判断就会越来越准确。
