今天我们来聊一篇来自 OpenAI 工程博客的技术文章，标题是英文的，叫做 Unlocking the Codex harness: how we built the App Server，翻译成中文就是"解锁 Codex 执行框架：我们如何构建 App Server"。这篇文章发表于二〇二六年二月四日，作者是 OpenAI 的技术人员 Celia Chen。

有一个时间背景需要跟你说一下。今天是二〇二六年九月，距离这篇文章发表已经过去了大约七个月。七个月在 AI 领域不算短，但也不算长。这篇文章描述的技术不是遥远的实验室研究，而是已经在生产环境跑着的实际工程。Codex CLI 的源码是开源的，App Server 协议今天就能用。所以即使文章发表于年初，它对你现在的工作仍然有很强的参考价值。

讲一下发表时的背景。二〇二六年年初，AI 编程工具正处于从"酷炫演示"走向"日常生产工具"的关键节点。OpenAI 在二〇二五年推出了 Codex 这个专门面向软件开发的 AI 智能体，不同于早期只能补全代码的工具，Codex 能够独立完成跑测试、修 bug、做代码审查这样的完整任务。到二〇二六年初，Codex 已经有了好几个不同的产品入口——有网页版、命令行工具也就是 CLI、VS Code 插件、JetBrains 插件，以及刚推出不久的 macOS 桌面应用。这篇文章就是在这个背景下出现的，它解决的是一个非常具体但极其重要的工程问题：当你有了一个强大的 AI 智能体内核，怎么让它能被这么多不同技术栈的客户端，安全、稳定、高效地共享使用？

为什么值得专门花时间听这期？我觉得有两个原因。第一，这是一篇工程实践文章，不讲模型能力，专门讲智能体的产品化架构，这类内容在业界还比较少见。第二，如果你在考虑把 AI 智能体能力嵌入你自己的产品，这篇文章的架构模式和踩过的坑，能帮你少走很多弯路。

好，我们先从背景故事讲起。

Codex 背后真正干活的是一套叫做 Codex harness 的东西。harness 这个词直译是"驾驭工具"或者"系统框架"，在这里可以理解为 Codex 的执行引擎，是整个产品的大脑。这套框架包含了 Codex 的核心智能体循环，也就是 agent loop，这个循环负责协调用户、大语言模型和各种工具之间的交互。用户说"帮我跑一下所有测试然后给我总结失败原因"，agent loop 就会把这个任务一步步拆解，决定先调用哪个工具，拿到结果之后把结果交给模型推理，模型再决定下一步做什么，循环往复，最终给用户一个完整的答案。

问题在于，Codex 产品的界面太多了，而且每个界面的技术栈都不一样。命令行工具是用 Rust 写的终端界面，VS Code 插件是 TypeScript，macOS 桌面应用是 Swift，JetBrains 的插件是 Kotlin。这些是完全不同的语言和运行时环境。

如果每个产品都自己实现一遍智能体的核心逻辑，那就是在重复造轮子。更大的问题是，一旦核心逻辑有更新，你要同步修改好几套代码，维护成本极高。而且不同实现很容易出现行为不一致——同样一个任务，网页版和 VS Code 插件给出的结果可能不一样，这会让用户非常困惑。

所以，需要一个统一的中间层，让所有客户端都能调用同一套核心逻辑。这就是 App Server 的存在意义。

但是这个 App Server 不是从一开始就规划好的，它是从实际需求里慢慢长出来的。这个演化故事非常值得听。

最开始，Codex 命令行工具就是一个 TUI，也就是 terminal user interface，终端用户界面。用户直接在终端里和 Codex 对话，智能体的核心逻辑和界面渲染逻辑是混在一起的，跑在同一个进程里。这种方式开发迭代很快，但也留下了后患。

后来，团队要做 VS Code 插件。IDE 里的交互方式和纯文字终端完全不同。你需要在编辑器里显示代码差异对比，也就是 diff，需要实时流式展示智能体的推理进度，需要弹出权限确认对话框，需要把工具调用的结果嵌入到编辑器的视觉结构里。这些都比纯文字终端复杂得多。

团队不想给 VS Code 单独再写一套智能体逻辑，所以需要找一个方式，让 VS Code 插件能通过某种接口驱动同一套 agent loop。

他们首先想到的是 MCP，也就是 Model Context Protocol，模型上下文协议。这是 Anthropic 提出的一个开放协议，让 AI 模型能够通过标准接口调用外部工具。但问题是 MCP 的语义和他们的需求对不上。MCP 更适合描述"工具调用"，是一个比较简单的请求响应模型，而 Codex 需要的是一个更复杂的双向会话流：服务器要能主动向客户端推消息，要能在执行操作前暂停等用户确认，要能流式传输逐步生成的内容。把这些复杂语义套进 MCP 框架里，会非常别扭。

于是他们自己设计了一个基于 JSON-RPC 的协议，镜像了 TUI 的交互循环，这就成了 App Server 的第一个非正式版本。当时团队没预期这个协议会被其他人依赖，所以设计得比较随意，不是一个稳定的 API。

随着 Codex 的用户量增长，越来越多的内部团队和外部合作伙伴也想把 Codex 嵌入他们自己的产品。JetBrains 想做 IntelliJ 级别的智能体体验，Xcode 想集成，Codex 的桌面应用需要同时协调很多个 Codex 智能体并行工作。这些需求让团队意识到，必须把这个临时协议升级成一个真正的、稳定的、向后兼容的平台级接口。这就是现在 Codex App Server 的样子。

好，背景讲完了，我们进入架构。先说 Codex core，这是整个系统的核心。

文章把 Codex core 定义为两件事：首先是一个库，所有的智能体代码都住在这里；其次是一个运行时，可以被启动来跑 agent loop，并且管理一个 Codex 对话线程的持久化状态。

Codex core 包含三大块功能。

第一块是线程生命周期管理和持久化。这里的线程是 Codex 里"一次会话"的意思，不要和操作系统里的线程混淆。Codex 可以创建新会话、恢复之前中断的会话、基于一个已有会话创建分支，以及归档旧会话。所有的事件历史都会被持久化存储，这样客户端断线重连之后还能看到一致的会话时间线。

第二块是配置和认证。Codex 负责加载配置文件、管理默认值，以及运行认证流程，包括"使用 ChatGPT 账号登录"这类操作，以及管理登录凭据的状态。

第三块是工具执行和扩展。Codex 在沙箱环境里执行 shell 命令和文件操作，同时还接入了 MCP 服务器和 skills 技能这样的扩展机制，让这些外部能力能在统一的安全策略模型下参与智能体循环。

这些就是 Codex 的大脑。App Server 则是大脑和外部世界之间的接口层。

App Server 是一个长期运行的进程，同时也是定义了客户端和服务器之间通信方式的 JSON-RPC 协议。它内部有四个主要组件。

第一个是标准输入输出读取器，负责从标准输入读取客户端发来的 JSON-RPC 消息，以及把要发给客户端的消息写到标准输出。

第二个是 Codex 消息处理器，它是客户端和 Codex core 之间的翻译层。它把客户端发来的 JSON-RPC 请求翻译成 Codex core 能理解的内部操作，同时监听 Codex core 内部产生的事件流，把底层的细粒度事件转化成一组稳定的、适合 UI 展示的 JSON-RPC 通知，发回给客户端。

第三个是线程管理器，负责为每一个正在进行的会话线程启动一个独立的 core session。

第四个就是这些 core thread 实例，也就是实际运行着 agent loop 的 Codex core 进程。

客户端和 App Server 之间的通信方式是 JSON-RPC over stdio，格式是 JSONL，也就是每行一个 JSON 对象。你可能会问，为什么不用 HTTP？HTTP 对于本地进程间通信来说有些重，有额外的连接开销。而 stdio 是最简单、最普遍的跨进程通信方式，几乎所有编程语言都原生支持，不需要依赖任何额外的网络框架。JSON-RPC 协议本身也极其简单，只需要解析 JSON 就能实现客户端，用 Go、Python、TypeScript、Swift、Kotlin 任何一种语言都能写出来。

这个 JSON-RPC 接口被设计为向后兼容的，意思是老版本的客户端可以安全地和新版本的服务器通信，不会因为服务器升级了就报错。这一点对于那些不能频繁发版的合作伙伴非常重要，后面讲 Xcode 的例子时还会具体说到。

接下来讲这篇文章最有技术含量的部分，也是我觉得设计最精彩的地方：协议的三个核心原语。

设计一个智能体交互的 API 比设计普通的请求响应 API 要难得多。普通 API 你发一个请求，我给一个响应，一来一回就完事了。但智能体的交互不是这样的。用户说一句话，智能体可能要先思考，然后调用一个工具，拿到结果之后再思考，再调用另一个工具，期间还可能需要问用户要授权，最终才给出答案。整个过程是一个展开的、有结构的序列，可能涉及很多中间步骤和中间产物。

客户端需要能忠实地表达这个序列：用户输入是什么，智能体每一步的进度如何，中间产生了什么东西，比如代码差异，也就是 diff。如果你的 UI 要做得好，不能等智能体全部跑完才一股脑展示结果，你需要像 ChatGPT 那样实时流式展示，每产生一点就展示一点。

为了让这个交互流既容易集成又对不同 UI 都有适应性，团队设计了三个核心原语，每个都有清晰的边界和生命周期。

第一个原语叫做 item，也就是条目，是 Codex 里输入输出的最小单位。每个 item 都有类型，类型可以是用户消息、智能体消息、工具调用、权限确认请求、代码差异，等等。每个 item 都有一个明确的生命周期。首先服务器会发出一个 item/started 事件，告诉客户端这个条目开始了。然后对于内容需要流式传输的条目，比如智能体的回复在逐字生成，服务器会不断发出 delta 事件，每来一片新内容就发一个。最后，当这个条目完成时，服务器发出 item/completed 事件，带上最终的完整内容。

这个设计让客户端可以立刻开始渲染。你不用等到整个智能体消息全部生成完才显示给用户，而是可以一边生成一边显示，就像你在 ChatGPT 里看到的那种逐字出现的效果。对于代码 diff 这种条目，客户端也可以在文件开始生成的时候就展示出来，而不用等全部文件都改完。

第二个原语叫做 turn，也就是回合，是一个由用户输入触发的智能体工作单元。它开始于客户端提交一个输入，比如"跑一下测试然后给我总结失败原因"，结束于智能体把这个输入对应的所有输出都产生完了。一个 turn 里面包含了一个有序的 item 序列，代表了智能体在处理这个输入过程中经历的中间步骤和产出。

你可以用写文章来做个类比。item 就是一个个句子，turn 就是围绕一个主题的一整个段落，是对一个问题完整展开的表达。

第三个原语叫做 thread，也就是会话线程，注意这里的线程是"对话会话"的意思，跟操作系统里的线程是不同概念。thread 是一个 Codex 用户和智能体之间正在进行的会话的持久容器，一个 thread 里面包含了多个 turn。thread 可以被创建、恢复、分叉和归档。会话历史会被持久化，这样客户端断线重连之后可以拿到完整的时间线，不会丢失之前的上下文。

用写作做比喻的话，thread 是整本书，turn 是每一章，item 是章节里的段落。

这三个原语设计有一个很重要的底层思想：明确的边界和生命周期。每个原语什么时候开始、中间会发生什么、什么时候结束，都是精确定义的。这对于构建可靠的 UI 非常关键，因为 UI 需要知道在每个状态节点该展示什么、该更新什么、该结束什么动画。

我想多说一下 approval，也就是权限确认这个机制，因为它体现了 App Server 协议的一个重要特性：双向性。

通常我们说的 API 是单向的：客户端发请求，服务器给响应。但在 Codex 的场景里，智能体在执行某些敏感操作之前，比如删除文件、运行一个可能有破坏性的脚本，需要先问用户确不确定。这就需要服务器主动向客户端发一个请求，而不是等客户端来问。

这就是 JSON-RPC 双向通信的体现。服务器发出一个 approval 请求，同时暂停当前 turn 的执行，等待客户端回复。客户端收到这个请求之后，会弹出一个确认对话框给用户，类似于"Codex 想要执行某个命令，允许吗"。用户选择允许或者拒绝，客户端把结果发回给服务器，服务器才继续或者取消当前 turn。

这个机制解决了 AI 智能体里一个很现实的安全问题：你肯定不希望一个 AI 工具在没有你明确授权的情况下做一些不可逆的操作。而且因为这是协议层面的设计，每种客户端都必须实现这个确认流程，不会因为某个客户端实现偷懒省掉了就导致安全漏洞。

除了 approval 之外，文章还介绍了会话开始时的握手，也就是 initialize 请求。在双方正式开始工作之前，客户端必须先发一个 initialize 请求，服务器回一个响应，双方在这一步确认协议版本、特性开关、默认配置。这就像两个人第一次见面要先自我介绍，让双方都知道对方能做什么、用什么方式沟通，然后再开始干正事。

好，协议设计讲完了，现在来看不同客户端是怎么接入 App Server 的。文章介绍了三种接入模式。

第一种是本地应用和 IDE，包括 VS Code 插件、JetBrains 插件、Xcode、macOS 桌面应用这些。

这些客户端的做法是：在发布的应用包里打包进去一个平台特定的 App Server 二进制文件，在运行时把这个二进制 launch 成一个子进程，然后通过 stdin 和 stdout 保持一个双向的 JSON-RPC 通信通道。对于 VS Code 插件和桌面应用来说，发布包里就包含了对应平台的 Codex 二进制，而且版本是固定的，确保客户端运行的永远是经过测试的那个版本。

Xcode 的做法稍微不同，很有意思。Xcode 把客户端发版周期和 App Server 发版周期解耦了。Xcode 的客户端代码保持稳定，但可以在需要的时候指向一个更新版本的 App Server 二进制。这样 Xcode 就可以在不发布自己的客户端更新的情况下，享受服务端的改进——比如更好的自动压缩功能，或者新支持的配置选项，或者 bug 修复——而不需要等 Xcode 自己发版。

这个设计能行得通，正是因为 App Server 的 JSON-RPC 接口是向后兼容的。老版本的客户端可以安全地和新版本的服务器通信，协议升级了不会把老客户端搞崩。

我觉得这个设计可以类比成餐厅的运作方式：菜单是客户端，后厨是服务器。菜单可以很久不变，但后厨的做法和食材可以在顾客不知情的情况下悄悄升级，只要端出来的菜还是菜单上的那些菜，顾客就没有影响。

第二种模式是 Codex 网页版，这里的情况稍微复杂一些，因为浏览器不能直接 launch 一个子进程。

所以这里加了一层 worker：服务端有一个 worker 进程，它在一个容器里启动 App Server 二进制，通过 stdio 和 App Server 通信，然后把 App Server 产生的事件流转成 HTTP 加 SSE，也就是 Server-Sent Events，推送给浏览器。浏览器端的页面通过 HTTP 和 SSE 接收这些事件，渲染 UI。

这种架构的好处是浏览器端可以非常轻量，不需要自己维护智能体的状态。同时，因为 Codex 实际的计算发生在服务端容器里，即使你的浏览器标签页关掉了、网络断了，任务还是会在服务端继续跑。等你下次重新打开，新的会话可以重新连上来，从中断的地方继续接着看，不会丢失进度。

文章里专门提到了这样一个道理：Web 会话天然是不可靠的，标签页随时可能关掉，网络随时可能断。所以不能让浏览器端作为长期任务的状态来源。把状态和进度放在服务端，才能保证工作的连续性。智能体能做的任务越长、越复杂，这个原则就越重要。

第三种模式是 TUI，也就是原来的命令行终端界面。这里有一个有意思的历史问题。

因为 TUI 是 Codex 最早的形态，它是直接在同一个进程里和 Codex core 交互的，直接调用 Rust 的内部类型，根本没走 App Server 协议。这让早期开发迭代很快，但也让 TUI 成了整个系统里的一个特殊案例：它的行为和其他客户端不一致，而且因为绕过了 App Server 层，有些功能很难在 TUI 里支持。

现在 App Server 已经成熟，团队计划把 TUI 也重构成用 App Server 的方式，让它像其他客户端一样：launch 一个 App Server 子进程，通过 JSON-RPC over stdio 通信，接收同样的流式事件和 approval 请求。

这个重构解锁了一个我觉得非常有前瞻性的使用场景——TUI 可以连接到运行在远程机器上的 Codex 服务器。你在本地用终端操作，但 Codex 的智能体实际跑在一台算力更强的云端机器上，靠近代码库和计算资源。就算你的笔记本进入睡眠或者断网了，服务端的任务还是继续跑，等你重新连上去就能看到最新的状态和进度。

这相当于把 Codex 从"本地工具"升级成了"远程计算能力"，本地只是一个控制面板和显示界面。我个人认为这是这篇文章里最有战略意义的一个点，它代表了 AI 智能体从单机工具走向分布式基础设施的演化方向。

好，客户端接入方式讲完了。文章还有一个很实用的部分，对不同集成方式做了横向比较，给那些想接入 Codex 的团队做参考。

文章列出了五种驱动 Codex 的方式。

第一种是 MCP 服务器模式。直接运行 codex mcp-server 命令，然后任何支持 stdio MCP 客户端的工具都可以连上来调用 Codex，包括 OpenAI 的 Agents SDK。如果你已经有了基于 MCP 的工作流，这是最快速的接入方式。但代价是你只能用到 MCP 暴露出来的那些能力，Codex 特有的交互——比如实时 diff 更新、复杂的会话语义——在 MCP 框架里不容易表达。

第二种是通用智能体协议。有些框架提供了一个可以适配多个模型提供商的通用抽象层，如果你想用一个统一接口协调多个不同来源的智能体，这类框架有用武之地。但代价是通用协议会找各家都支持的最小公分母，一旦你需要 Codex 特有的工具和会话语义，这些能力就很难在通用层里表达。文章也说了，这个领域还在快速演化，更成熟的标准还在形成中。

第三种就是 App Server，也是文章主推的方式。用 App Server，你能拿到 Codex 完整的 harness 能力，包括完整的智能体循环、用 ChatGPT 账号登录、模型发现、配置管理这些功能。代价是你需要自己构建客户端的 JSON-RPC 绑定代码，需要一定的集成工作量。

但文章里有一个非常实用的提示——你可以把 App Server 的 JSON Schema 文档喂给 Codex 本身，让 Codex 来帮你生成这个绑定代码。文章提到，很多合作伙伴团队就是这样做的，都能很快做出一个能跑起来的集成。而且对于 TypeScript，可以直接从 Rust 协议定义自动生成类型定义，对于其他语言，可以生成 JSON Schema 然后用对应语言的代码生成工具来处理。

第四种是 CLI 自动化模式。如果你只需要在 CI 流水线或者脚本里跑一次性的任务，直接用 Codex CLI 的非交互模式就好了。你传一个任务进去，它跑完了，输出结构化结果，退出，有明确的成功或失败退出码。这是最轻量的接入方式，对于自动化脚本和持续集成场景非常合适。

第五种是 TypeScript SDK。这是一个 TypeScript 库，让你在 Node.js 应用里以库调用的方式控制本地的 Codex 智能体，不需要自己搭 JSON-RPC 客户端。因为这个 SDK 比 App Server 发布得早，所以目前支持的语言少、覆盖的功能面也小。文章说，如果开发者有兴趣，他们可能会增加更多语言的 SDK 来封装 App Server 协议，这样更多团队就能用上完整的 harness 能力，而不用从零写 JSON-RPC 客户端。

好，说完了文章的主要内容，我们来聊聊对你实际工作的意义。

如果你是一个正在构建 AI 产品或者内部工具的工程师，Codex App Server 代表了一类重要的架构模式，值得认真琢磨。

最直接的应用场景：如果你想在自己的产品里嵌入一个 AI 编程助手能力，不需要从头训练模型，直接接 Codex App Server 就能拿到一个经过生产验证的 AI 编程智能体。你的主要工作是在你的语言里实现客户端的 JSON-RPC 绑定，然后设计如何在你的产品 UI 里展示 item、turn 和 thread 这三个概念对应的内容。

对于大多数团队，我建议的起步路径是这样的：先去 Codex CLI 的开源仓库看文档和 JSON Schema 定义，然后用你的主力语言实现一个简单的最小可用客户端——能发 initialize 请求、能接收通知、能处理 approval 确认。文章建议把 JSON Schema 喂给 Codex 让它帮你生成这个客户端，我觉得这是个很实在的建议，值得一试。

有几个坑我想专门提醒一下。

第一个坑是不要低估 approval 流程的复杂性。很多人做集成的时候会忽略这个。Codex 在执行某些操作之前会暂停，等待用户确认，服务器这时候会主动向客户端发一个请求。你的客户端必须能正确处理这种服务器主动发来的请求，否则 turn 会卡在那里永远完不成。文章的示例代码里有 approval 流程的完整展示，仔细看。

第二个坑是对于 Web 场景，一定要把状态维护在服务器端。如果你把对话状态存在浏览器里，用户一关标签页就全丢了。Codex App Server 的 thread 持久化机制是为服务端状态设计的，要充分利用它。

第三个坑是工具沙箱的权限配置。Codex 里所有的 shell 命令和文件操作都是在沙箱里执行的，如果你要集成 MCP 扩展或者自定义 skills，需要理解 Codex 的安全策略模型，提前配置好沙箱的权限边界，不然工具调用会因为权限不够而失败。

从更宏观的角度来看，这篇文章揭示了 AI 智能体产品化的一个核心模式：把智能体逻辑层和 UI 展示层彻底分离，用一个标准化的、双向的、流式的协议来连接它们。

这个模式解决了 AI 产品开发里一个经典困境：核心模型和智能体逻辑在快速迭代，但你的 UI 层和客户端集成不可能跟着每次改动都重写。有了这种稳定的中间层协议，服务端可以快速迭代，客户端只需要对协议的稳定接口负责，只要接口兼容，服务端怎么变都不影响客户端。

我个人认为，这种"智能体即服务，通过稳定协议暴露能力"的模式，会成为未来 AI 基础设施建设的一个标准方向。这跟当年 LSP，也就是语言服务器协议，把代码编辑器和语言分析工具解耦的逻辑非常类似。LSP 出现之前，每个编辑器都要单独适配每种编程语言；LSP 出现之后，一种语言只需要实现一次 LSP 服务器，所有支持 LSP 的编辑器都能自动获得支持。Codex App Server 正在做类似的事情：一套智能体核心，通过一个稳定协议，支持所有不同的客户端界面。随着越来越多的 AI 智能体产品走向成熟，类似的分层和协议标准化会越来越普遍。

最后我们来收尾。

这篇文章的核心主题是"如何把一个 AI 智能体产品化"。它解决的问题非常具体：当你有了一个强大的智能体内核，怎么让它被不同语言、不同平台、不同发版节奏的客户端安全稳定地共享使用。

Codex App Server 的答案是：设计清晰的分层架构，把智能体核心和客户端用向后兼容的双向流式协议连接起来；用 item、turn、thread 三个原语准确表达智能体交互的结构；把状态和计算放在服务端，让客户端保持轻量；通过 approval 机制在协议层面保证用户对智能体行为的控制权。

我个人觉得这篇文章最值得学习的不是某个具体的技术决策，而是那种从实际需求出发、逐步演化出稳定标准的工程思路。App Server 不是从一开始就规划好的，它是从做 VS Code 插件的实际需求里长出来的，经历了从临时方案到稳定平台的演化。这种由真实场景驱动、逐步抽象、最终形成标准接口的做法，是在快速迭代环境里处理不确定性的务实方法，也是很多成功基础设施项目的共同路径。
