## Script

今天要聊的这篇文章，英文原标题是 Building a safe, effective sandbox to enable Codex on Windows，中文翻译过来是"在 Windows 上构建一个安全有效的沙盒，让 Codex 得以运行"。文章发表于二〇二六年五月十三日，作者是 OpenAI Codex 工程团队的技术人员 David Wiesen。

先说一下为什么值得听这期。Codex 是 OpenAI 推出的编程 agent，这类 AI 编程工具现在已经很普遍了，但你有没有想过，当一个 AI agent 在你的本地电脑上帮你跑命令、改文件的时候，它的权限是怎么管控的？这篇文章回答的就是这个问题——而且是从 Windows 平台这个最难搞的角度来回答的。读完这篇文章，你会对操作系统安全机制有一个很具体的理解，同时也会对 AI agent 的安全设计有新的认识。文章写得很坦诚，不只讲了最终成功的方案，还详细记录了走了哪些弯路、为什么放弃，这种记录方式在技术博客里并不多见。

我们先来搞清楚背景。Codex 是 OpenAI 的编程 agent，agent 这个词可以翻译成"智能代理"，但在这个语境里它的实际含义是：一个可以自主执行任务的 AI 程序，不需要你每一步都手动确认。你跟它说"帮我修这个 bug"或者"帮我给这个函数加单元测试"，它就会自己去读代码、分析问题、修改文件、跑测试，一条龙做下来。你用它是为了不用自己做那些繁琐的操作，这才是使用它的价值所在。

Codex 跑在你本地的电脑上，通过命令行工具、IDE 插件或者桌面客户端来使用。它的架构是这样的：你本地有一个叫做 harness 的程序，你可以把它理解为"指挥官"，负责管理你和云端模型之间的对话，同时把模型的指令翻译成本地命令来执行。模型在云端做推理，本地的 harness 负责执行操作，比如读文件、写文件、跑 Git 命令、跑测试，等等。

现在核心问题来了：Codex 默认情况下是以你这个用户的身份和权限在运行的。你能读的文件它能读，你能写的文件它能写，你能访问的网络它能访问。这种能力很强大，但也潜藏着风险。如果 AI 模型给出了一个错误的指令怎么办？如果有恶意代码混进了你的项目，诱导 Codex 去执行危险操作怎么办？在 AI 能力越来越强的今天，这是实实在在需要考虑的工程问题。

所以 Codex 需要一个沙盒。沙盒这个词英文叫 sandbox，你可以把它想象成小孩玩沙子的沙坑。孩子在沙坑里可以随便折腾，堆城堡、挖沟渠，但沙子不会飞出去弄脏外面的地方。在软件里，沙盒是一个被操作系统层面限制住的执行环境：程序在沙盒里运行，但它能做的事情受到了严格约束。这些约束是由操作系统强制执行的，不是靠程序自觉遵守的软性规则。

Codex 的目标是：沙盒内的代码可以读取几乎任何文件，但只能在你当前工作目录里写文件，并且默认没有网络访问权限。要真正做到"操作系统层面强制执行"，就需要操作系统提供相应的工具。

Mac 上有 Seatbelt，这是苹果专门设计的沙盒工具，灵活而强大，Codex 直接用它来做精细隔离。Linux 上有 seccomp 和 bubblewrap，可以在系统调用层面做过滤，技术上很硬核。但是 Windows 偏偏没有一个开箱即用、适合这种场景的原生沙盒工具。

当 David Wiesen 在二〇二五年九月加入 Codex 工程团队时，面对的现实是：Windows 版 Codex 根本没有沙盒实现。Windows 用户在使用 Codex 时，只有两个糟糕的选择：要么手动批准 agent 想执行的几乎每一条命令，哪怕只是读个文件，这既烦人又失去了用 Codex 的意义；要么开启"完全访问模式"，让 Codex 不受任何限制地执行命令，省了麻烦但完全没有安全保障。两个选项都很糟糕。

在动手自己做之前，团队认真研究了 Windows 已有的几种隔离机制，看看有没有现成的能用。他们调研了三个方向，但每一个都有绕不过去的根本性问题。

第一个是 AppContainer。这是 Windows 内置的沙盒机制，采用"基于能力"的隔离模型。它的设计思路是：一个应用程序在安装时声明它需要访问哪些资源，系统就只给它这些权限，其他全部拒绝。这个机制的好处是隔离边界是真实的、操作系统强制执行的，不是靠程序自觉遵守的软性约束。

但问题在于，AppContainer 是为那种"事先知道自己要访问什么"的应用程序设计的。一个音乐播放器知道它只需要读音乐文件，不需要执行系统命令；一个图片编辑器知道它只要读写图片。这类应用非常适合 AppContainer。但 Codex 完全不是这样的程序。Codex 要驱动各种开发者工作流：Shell 脚本、Git 命令、Python 脚本、包管理器、各种构建工具，还有 agent 在执行过程中临时决定需要调用的任意二进制程序。你根本没法事先枚举它需要访问什么。AppContainer 的隔离边界是真实的，但它的设计形状跟"让一个 agent 像真正的开发者那样工作"完全对不上，强行适配的代价是无法承受的兼容性问题。

第二个是 Windows Sandbox。这是微软提供的一种一次性轻量级虚拟机。你在里面跑什么都行，关掉之后所有内容全部消失，隔离性极强，安全边界非常硬。而且它对任意软件的兼容性比 AppContainer 好得多，因为里面就是一个完整的 Windows 环境。

但核心问题是：Codex 需要直接操作用户本地真实的代码仓库、真实的开发工具、真实的环境配置。你不可能把用户的整个开发环境搬进一个一次性虚拟机，这涉及大量主机与虚拟机之间的数据同步和桥接工作，复杂且引入延迟。还有一个更实际的产品问题：Windows Sandbox 这个功能在 Windows Home 版本上根本就不可用。很多开发者用的恰恰是 Home 版，一个对相当大比例用户不可用的功能，不是有效的解决方案。

第三个是 MIC，全称 Mandatory Integrity Control，强制完整性控制。Windows 给每个进程和对象都有一个"完整性级别"，分低、中、高等，决定系统对它们的信任程度。基本规则是：一个低完整性进程不能往更高完整性的对象写数据，即便普通访问控制允许这个写操作也不行。

这个机制乍一看很适合：让 Codex 以低完整性运行，把允许它写的工作目录标记为低完整性，这样它就只能写那些目录，其他地方写不了。而且是操作系统原生支持的，不是软性约束。

但仔细一想，问题很严重。你把工作目录标记为低完整性，这个改变不只对 Codex 有效，而是对机器上所有低完整性进程都有效。浏览器沙盒里跑的进程通常是低完整性的；如果你不小心访问了一个恶意网页，里面的代码拿到了低完整性执行权限，它就可以往你的代码仓库里写东西了。你的整个项目的信任模型被破坏了，而且这种破坏很难控制、也很难向用户解释清楚。

三条路都走不通，团队决定自己动手实现。

第一版原型的目标是：不要求管理员权限。在 Windows 上，很多系统操作需要"提权"，也就是弹出那个熟悉的 UAC 对话框，让用户点"是"才能继续。对于一个开发工具来说，如果每次启动都需要用户确认提权，体验会非常差。所以团队希望沙盒的正常运行不需要管理员权限。

为了在这个约束下控制文件写入，团队用了两个 Windows 核心概念：SID 和写受限令牌。

SID 的全称是 Security Identifier，安全标识符。这是 Windows 用来标记身份的基本单位。你这个用户有一个 SID，管理员组有一个 SID，你的这次登录会话也有一个专属 SID。当一个进程想访问某个文件或目录时，Windows 会检查这个进程的 SID 是不是在那个文件或目录的访问控制列表（ACL）里，以及它有什么样的权限。

关键是，Windows 还允许你创建"合成 SID"——这种 SID 不对应任何真实用户，纯粹是个标记，但它可以出现在 ACL 里，用来控制访问权限。这给了团队一个精巧的操作空间：创建一个只属于 Codex 沙盒专用的合成 SID，比如叫做 sandbox-write，然后用这个 SID 来精确控制哪些目录可以被沙盒写入，完全不影响系统上其他任何进程或用户。

另一个关键概念是写受限令牌，英文叫 write-restricted token。在 Windows 里，进程令牌是一个安全对象，定义了一个进程的身份和权限。写受限令牌是一种特殊令牌，它要求所有写操作必须同时通过两道独立的访问检查才能成功。第一道是正常的权限检查：令牌的主体身份有没有权限写这个位置？第二道是额外检查：令牌的受限 SID 列表里，至少要有一个 SID 也被授权了这个写操作。两道都通过，写才成功；任何一道失败，写就被拒绝。

你可以把这个理解成一把需要两把钥匙才能打开的锁——银行金库里常用的那种双人授权设计。只有你的个人钥匙（用户权限）是不够的，还需要那把专属的沙盒钥匙（受限 SID）也被授权了目标位置，才能写入。

把这两个工具结合起来，第一版沙盒的工作流程是这样的：

安装阶段，创建一个叫做 sandbox-write 的合成 SID，把这个 SID 的写、执行、删除权限授予到当前工作目录，以及用户在配置文件里额外指定的可写目录。同时对一些敏感的子目录——比如 Git 目录、Codex 的配置目录——显式拒绝这个 SID 的写权限，这样 agent 就改不了 Git 历史或者 Codex 自身的配置了。

运行阶段，Codex 的每一条命令都在一个写受限令牌下启动。这个令牌的受限 SID 列表包含三个成员：Everyone（所有人组的 SID），当前登录会话的 SID，以及合成的 sandbox-write SID。命令进程就在这个令牌下运行，所有写操作都要经过双重检查。因为 sandbox-write 这个 SID 只被授权了特定的几个目录，沙盒里运行的进程就只能往那些目录写文件，其他任何地方都会被拒绝。而且这个限制会传递给所有子进程，所以 Codex 启动的 Git、Python、Shell 脚本，以及这些程序再启动的任何子进程，全都在同样的写访问约束下运行。

对于网络访问，因为不想要求管理员权限，团队没法直接用 Windows 防火墙——配置防火墙规则需要管理员权限。所以他们采取了"堵住明显逃跑路线"的策略：把子进程环境里的各种代理变量设置到一个死端点。比如把 HTTPS 代理、ALL 代理、Git 的 HTTPS 代理全都指向本地的九号端口——端口九在 TCP 协议里是"丢弃"端口，发过去的包会被直接丢弃，连接会立即失败。对于 Git 的 SSH 传输，把 GIT_SSH_COMMAND 环境变量设置成直接退出并返回错误。还在 PATH 最前面插入了一个拒绝目录，里面放了假的 SSH 和 SCP 脚本，这样常见的网络工具会优先触发这些假脚本然后失败。

这套方案能拦住大多数常见开发工具的网络请求，因为大多数工具都遵守代理环境变量。但这本质上是"劝阻性"的，不是强制性的。如果一个进程不理会环境变量，直接自己建立 socket 连接，那它完全可以绕过这些限制。这是第一版原型最严重的缺陷。

总结一下第一版的优缺点。优点很明显：不需要管理员权限，对用户透明，文件写入控制非常精细，可以精确到目录级别。缺点有四个：第一，对工作目录应用 ACL 可能很耗时，尤其是大型项目；第二，往用户真实文件系统写入了 ACL 条目，有系统足迹；第三，如果想调整沙盒的访问策略，需要重新跑一遍 ACL 操作，成本很高，而 Mac 上的 Seatbelt 改一行配置文件就行；第四，最关键的，网络保护是假的，任何自己实现网络栈的程序都能绕过去。最后这点让团队决定继续改进。

于是进入第二版：需要提权的高级沙盒。

为了做到真正的网络隔离，团队决定使用 Windows 防火墙。防火墙可以在操作系统层面强制阻断对外网络连接，是真正意义上的硬性隔离。但要使用防火墙规则，有两个关键难题。

第一，防火墙规则需要管理员权限来创建。团队的新策略是：把提权操作集中在安装阶段，安装时以管理员权限完成所有设置，之后日常运行不再需要提权。

第二，Windows 防火墙规则必须绑定到某个具体的 Windows 用户身份。你不能说"对受限令牌有效"——Windows 防火墙根本不认识受限令牌这个概念，它只认用户身份。而且你也不能把规则绑定到真实的 Windows 用户，因为那会把所有以这个用户身份运行的程序的网络都断掉，包括 Codex 本身和用户的所有其他程序。

解决方案是：在本地创建两个专用的 Windows 用户账户。一个叫 CodexSandboxOffline，防火墙会对这个账户完全阻断对外网络访问；另一个叫 CodexSandboxOnline，没有防火墙限制，用于需要访问网络的操作。沙盒内运行的所有命令，都以这两个账户之一的身份来运行，不再以真实用户的身份运行。

这个改变看似只是换了个账户，但背后涉及大量额外的工程工作。

首先是安装阶段大幅扩展。需要：创建合成 SID；创建两个沙盒用户账户；用 Windows 的 DPAPI，也就是数据保护 API，把这两个账户的凭据加密存储到一个沙盒用户自身读不到的位置，保证沙盒用户没法拿着自己的凭据去做其他事情；创建防火墙规则，封锁 CodexSandboxOffline 的全部对外网络连接，并验证规则的正确性。

其次是读取权限问题。第一版原型里，沙盒进程以真实 Windows 用户的受限令牌运行，所以用户能读的文件它也能读。但现在沙盒进程是以 CodexSandbox 用户的身份运行的，这个用户是新创建的，系统里根本没有给它设置任何权限。Windows 默认不允许一个用户读取另一个用户的 profile 目录。这意味着很多 Codex 需要读取的文件，比如用户 home 目录下的各种配置文件，对 CodexSandbox 用户来说是读不到的。

为了解决这个问题，安装阶段还需要给这两个沙盒用户显式授予读权限，覆盖一批常用目录：用户的 profile 目录，Windows 系统目录，Program Files 目录，Program Files x86 目录，ProgramData 目录。这个授权操作本身也是通过 ACL 实现的，涉及的目录通常很大，ACL 操作很耗时。团队把这部分操作放在后台异步执行，不阻塞主安装流程。

再者是进程创建的权限壁垒，这是整个设计里最技术性的一个挑战。

团队想要的流程是：Codex 主程序调用 Windows API 用 CodexSandbox 用户身份登录，拿到令牌，在上面创建写受限令牌，最后用这个受限令牌来启动子进程。听起来很直接，但在实践中走不通。

问题出在一个叫 CreateProcessAsUserW 的系统调用上。这个调用允许以特定令牌的身份创建进程，但它需要调用方进程拥有特殊的系统级权限，通常只有高权限的系统服务才有。Codex 主程序作为普通用户程序，没有这些权限。也就是说，Codex 主程序可以拿到 CodexSandbox 用户的令牌，可以在上面创建受限令牌，但就是没法用这个令牌来启动新进程。这是一道权限壁垒。

解决这道壁垒的方法，是引入一个中间人进程，叫 codex-command-runner.exe。这个程序的唯一职责是：以 CodexSandbox 用户身份运行，接受来自 Codex 主程序的命令请求，然后在自己的进程上下文里完成受限令牌的创建和子进程的启动。

整个流程分两部分。第一部分：Codex 主程序调用 CreateProcessWithLogonW——注意这个 API 和 CreateProcessAsUserW 不同，它允许普通用户程序以另一个用户的凭据来创建进程——以 CodexSandbox 用户的凭据来启动 codex-command-runner.exe，这一步还没有受限令牌。第二部分：在 codex-command-runner.exe 内部，它打开自己的进程令牌，这个令牌已经属于 CodexSandbox 用户了，然后提取登录会话 SID，调用 CreateRestrictedToken 创建受限令牌，最后调用 CreateProcessAsUserW 以这个受限令牌启动真正的子进程。因为 codex-command-runner.exe 已经是 CodexSandbox 用户的进程，它有权限对自己的令牌做这些操作，也有权限用 CreateProcessAsUserW 来创建子进程。

这样绕了一圈，但每一步都落在正确的权限边界内，Windows 安全机制全程没有被绕过，每一个 API 调用都是合法的。

最终的架构有四个层次。第一层是 codex.exe，Codex 主程序，始终以普通用户权限运行，负责管理对话和决策。第二层是 codex-windows-sandbox-setup.exe，沙盒安装程序，在安装阶段以管理员权限运行，负责所有需要提权的设置工作：创建用户、配置 ACL、设置防火墙规则。第三层是 codex-command-runner.exe，命令运行器，以 CodexSandbox 用户身份运行，负责在正确的权限边界内创建受限令牌和启动子进程。第四层是实际执行任务的子进程，在受限令牌和防火墙规则的双重约束下运行。

四层结构，每一层职责清晰，互不越界。作者在文章里引用了爱因斯坦的话："一切事情应该尽可能简单，但不能更简单。"这句话很好地概括了这个设计的哲学——复杂是必要的代价，不是为了炫技，每一层的存在都有它要解决的具体问题。

另一个值得注意的架构决策是：把需要提权的操作专门封装到一个独立的安装程序里，而不是让主程序 codex.exe 偶尔提权。这样 codex.exe 在日常运行中始终是普通用户进程，Windows 专属的安装逻辑也不会让 codex.exe 在其他平台上变得臃肿，安装程序的生命周期也独立于主程序的生命周期。这是最小权限原则在工程实现上的一个好例子。

好，技术细节讲完了。我们来聊聊这篇文章对实际工程工作有什么意义。

第一个启示：平台差异比你想象的要深。我们通常觉得，一个功能在 Mac 和 Linux 上跑通了，移植到 Windows 不过是改改路径分隔符的事。但这篇文章告诉你，在操作系统安全边界这个层面，三个平台的底层哲学是完全不同的。Mac 的 Seatbelt 给你一套声明式策略语言，写几行规则就能定义精细的访问策略，灵活而强大。Linux 的 seccomp 让你在系统调用层面做过滤，是非常底层的能力。Windows 的安全模型围绕 ACL、SID、令牌、完整性级别、防火墙规则这套体系构建，跟前两者的思路完全不同。如果你在做跨平台的系统级工具，早点投入时间理解这些差异，会省去后期大量的技术债。

第二个启示：agent 的安全需求和传统应用安全非常不同。传统应用你事先知道程序要做什么，可以给一个固定的权限集合。但 agent 是开放式的，它随时可能决定要调用一个新工具、运行一段临时脚本、安装一个包、读一个意料之外的文件。这要求你的沙盒既要足够灵活，能容纳各种开发工作流，又要足够严格，能防止真正危险的操作。灵活性和严格性之间的张力，是做 AI agent 基础设施时最核心的工程挑战。作者明确说，他们花了大量精力在"与 agentic 工作流的兼容性"和"真实的权限执行"之间找平衡，这个思路值得所有做 AI agent 产品的工程师认真思考。

第三个启示：网络隔离必须做到操作系统层面。用环境变量来阻止网络访问是靠不住的。Codex 的第一版就犯了这个错：用代理变量劝阻网络请求，看起来能用，但本质上可以被绕过。任何自己实现了网络栈的程序，或者任何不遵守代理变量的工具，都能绕过。最终还是要靠防火墙规则，绑定到具体的系统用户身份，才是真正的隔离。这个原则不只适用于 Windows，在任何平台上，如果你用应用层的方式来模拟操作系统层的隔离，都是在走钢丝。

第四个启示，也是我个人最欣赏的一点：这个项目展示了一种务实的工程进化路径。团队没有一开始就设计出完美的方案，而是从一个能解决主要问题但有缺陷的原型开始，识别出最不可接受的缺陷，然后有针对性地改进，每次只引入解决当前最大问题所必要的复杂度。第一版解决了文件写入控制；第二版在此基础上解决了网络隔离；每次改进都有明确的工程理由。这种迭代方式，在实际工程实践中比"先把所有问题想清楚再动手"要可靠得多，因为很多问题只有真正动手才会暴露出来。

如果你现在正在开发 AI coding agent 相关的工具，或者你的团队在考虑给内部的 AI agent 加上安全沙盒，我建议重点关注两件事：一是尽早调研你目标平台上操作系统级别的隔离原语，不要假设它们跟你熟悉的其他平台一样；二是把文件系统隔离和网络隔离当成两个需要独立设计的子问题，它们背后依赖的机制可能完全不同，需要分开考虑，分开测试。

好，今天这期我们完整地过了一遍 OpenAI 工程师 David Wiesen 在 Windows 上为 Codex 构建沙盒的过程：从调研三个现有 Windows 隔离方案都发现不适合，到实现一个基于合成 SID 和写受限令牌的第一版无需提权沙盒，再到认清网络保护太弱，升级到创建专属 Windows 用户、配置防火墙规则、引入 codex-command-runner.exe 的高级沙盒，最终形成四层架构。
