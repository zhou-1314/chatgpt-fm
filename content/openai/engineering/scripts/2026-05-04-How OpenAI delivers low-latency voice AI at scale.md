今天我要给大家介绍的这篇文章，英文标题是"How OpenAI Delivers Low-Latency Voice AI at Scale"，我把它翻译成中文是"OpenAI 如何在超大规模场景下实现低延迟语音人工智能"。这篇文章由 OpenAI 技术团队的两位成员 Yi Zhang 和 William McDonald 联合撰写，发表于二零二六年五月四日，发布在 OpenAI 官方网站的工程博客栏目。

距今大约四个月，这篇文章处于语音 AI 技术高速演进的一个关键节点上。彼时 ChatGPT 的语音模式已经被数亿用户广泛使用，OpenAI 同时向开发者提供 Realtime API，让外部团队也能在自己的产品里接入实时语音能力。这篇文章的背景，就是在如此庞大的规模下，OpenAI 工程团队如何解决实时语音系统的基础架构问题。这不是一篇讲"未来会有什么"的展望文章，而是一篇讲"现在的系统是怎么运转的"的工程实践文章，技术细节扎实，架构思路清晰，非常值得深读。

我们先从一个非常基础但至关重要的问题讲起：为什么语音 AI 对延迟如此敏感？

你可以想象两种完全不同的对话体验。第一种是对讲机模式，英文叫 push-to-talk，就是那种按着按钮说话、松手之后才能听到对方回复的模式。你说一句，对方处理完，回复你一句。在这种模式里，哪怕有一两秒的停顿，用户也能接受，因为整个交互本来就被设计成"你说我听、我说你听"的严格轮流模式，停顿是这个交互模式的一部分，是预期中的行为。

第二种是真正的自然对话，就是面对面聊天或者打电话的那种体验。在这种模式里，双方可以随时打断对方，可以在对方还没说完的时候就开始"嗯""对对对"地实时回应，语气词和确认信号几乎是同步发生的。这种对话对延迟极其敏感，因为人类的大脑在漫长的进化过程中，已经深度适应了几乎零延迟的面对面交流模式。研究表明，超过两三百毫秒的延迟，人就会开始感受到对话的不自然。超过五百毫秒，就会明显觉得卡顿，对话的流畅感完全被破坏。

ChatGPT 的语音模式，以及 OpenAI 提供给开发者的 Realtime API，追求的是第二种体验，真正的自然对话，而不是 push-to-talk。这意味着系统必须能够在用户还在说话的时候，就同步开始做语音转录、做推理、调用工具、生成语音回复。这种并行处理的模式，英文叫 streaming，流式处理，它是实现自然对话感的底层技术前提。文章里有一句话说得很生动：这就是一个让人感觉是在对话，而不是在轮流按发言键的系统，和一个 push-to-talk 系统之间的根本区别。

而要实现流式处理，第一步就是要保证音频数据能够以一个连续的、低延迟的流的形式，从用户端实时传送到服务器端，再从服务器端把生成的语音流回给用户。这中间的传输层，选择什么协议、怎么部署，就是这篇文章要讨论的核心工程问题。

OpenAI 选择的传输层是 WebRTC。WebRTC 全称是 Web Real-Time Communication，网页实时通信。很多人一听到 WebRTC 第一反应就是浏览器里的视频通话，Google Meet 的网页版、Zoom 的浏览器端，这些确实都是 WebRTC 的典型应用。但 WebRTC 的内涵远不止于此，它是一套完整的、专门为实时媒体传输设计的协议栈，把实时通信里面最硬核的几个工程难题都标准化了。我来逐一给你解释这几个难题。

第一个是 ICE，全称是 Interactive Connectivity Establishment，交互式连接建立。这个协议解决的问题是：互联网上的两台设备，如果都藏在 NAT，也就是网络地址转换设备后面，怎么找到对方，建立起一条可以通信的通道？你的手机、你家里的电脑，几乎都在路由器的 NAT 后面，你的 IP 对外网来说是路由器的公网 IP，不是你设备真正的局域网 IP。如果服务器想把数据包发给你，就必须先做一系列探测和协商，找到一条路由器愿意放行的路径。ICE 就是负责完成这一系列探测的，它会尝试多种路径和方法，包括通过 STUN 服务器来探测公网地址，以及通过 TURN 服务器来做中转，最终找到一条两端都能通信的路径。这个过程非常复杂，ICE 把它标准化并实现好，让应用层不需要自己去处理这些细节。

第二个是 DTLS 和 SRTP 的组合。DTLS 是 Datagram Transport Layer Security 的缩写，是基于 UDP 的加密握手协议，负责建立一个安全的加密通道。SRTP 是 Secure Real-time Transport Protocol，安全实时传输协议，负责在这个通道上加密传输实际的音视频数据。这两个结合在一起，保证了媒体流从客户端到服务器全程加密，中间人无法窃听或篡改。

第三个是 codec 协商，也就是编解码器协商。发送方需要把原始音频压缩成某种格式才能高效传输，接收方需要按同样的格式解压才能播放。这个压缩解压的算法就叫 codec，双方必须事先协商好用哪种 codec。这个协商过程通过 SDP，也就是 Session Description Protocol，会话描述协议来完成，SDP 是一个描述会话参数的文本格式，双方在建立连接时互相发送 SDP 来告知自己支持哪些 codec、期望用什么参数传输媒体。

第四个是 RTCP，全称 Real-time Transport Control Protocol，实时传输控制协议。它监控传输质量，比如丢包率、延迟、抖动等指标，并根据这些数据反馈来调整发送速率，防止网络拥塞把语音质量搞崩。

第五个是客户端内置的音频处理功能，比如回声消除和抖动缓冲。回声消除防止你说话的声音被麦克风捕捉后形成回声；抖动缓冲平滑网络传输中的时间波动，让播放的音频连续流畅。这两个功能在浏览器和移动平台上，WebRTC 都有经过大量真实场景验证的成熟实现，开发者可以直接享用，不需要自己实现。

文章里有一句话说得很精准：如果没有 WebRTC，每个客户端就需要分别为 NAT 穿透、媒体加密、codec 协商、网络自适应找自己的解决方案，不同平台之间互不兼容，维护成本极高。有了 WebRTC，这些苦活儿都有了标准答案，工程团队可以把精力集中在把实时媒体接到模型推理这个真正创造价值的事情上。

选定了 WebRTC 之后，下一个核心问题是：服务器端应该用什么架构来部署 WebRTC？

文章里对比了两种主流的服务器架构模式：SFU 和 transceiver。

先说 SFU，全称是 Selective Forwarding Unit，选择性转发单元。你可以把 SFU 想象成一个多方通话场景里的"调音台"或者"交换机"。每个参与者都和这台调音台建立一条独立的 WebRTC 连接，调音台负责决定把谁的音视频流转发给谁。在三十人的在线课堂里，每个学生都连到同一个 SFU，SFU 把老师的画面转发给所有学生，把每个学生的音频按需转发。SFU 还适合做录制、策略控制、接入更多参与者等功能的扩展。对于多方场景来说，SFU 是非常标准的选择，很多成熟的开源和商业方案都是基于 SFU 架构的。

但 OpenAI 的使用场景不一样。他们绝大多数的会话都是一对一的，一个用户对一个 AI 模型，或者一个应用对一个实时 agent。在这种一对一的、对延迟极其敏感的场景里，SFU 的那套"调音台"架构就显得多余了，引入了不必要的复杂性和额外的中间层。

OpenAI 选择的是 transceiver 模式，我把它翻译成收发器模式。在这个模式里，有一个 WebRTC 边缘服务负责完整地终止客户端的 WebRTC 连接。这里的"终止"是一个技术词汇，意思是：ICE 握手在这里完成，DTLS 握手在这里完成，SRTP 的加解密在这里做，会话的完整生命周期由这个服务来管理。完成之后，这个收发器服务把媒体数据和事件，转换成更简单的内部协议，传给后面的模型推理服务、语音转录服务、语音生成服务等等。

这个设计最大的好处是：只有 transceiver 这一层需要理解和处理复杂的 WebRTC 协议，后面所有的后端服务都完全不需要知道 WebRTC 是什么，它们只需要处理普通的内部接口，可以像普通的云服务一样方便地水平扩展。系统的复杂性被集中在一个地方，而不是分散给所有后端。

Transceiver 模式确定了之后，问题来了。传统的 WebRTC 服务器，有一个非常普遍的部署方式，叫做 one-port-per-session，也就是一个会话对应一个 UDP 端口。你有多少个并发的语音会话，就需要在服务器上开放多少个 UDP 端口。这在小规模场景里还凑合，但在 OpenAI 这种规模下，这个模式会带来三个严重的问题。

第一是端口数量的问题。大量并发会话意味着需要暴露出去一个非常大的公网 UDP 端口范围，比如从一万到六万，总共五万个端口。云服务商的负载均衡器和 Kubernetes，也就是 K8s 的服务机制，都不是为管理几万个公网 UDP 端口而设计的。端口范围一大，防火墙规则、健康检查配置、滚动发布时的端口管理，复杂度就急剧上升，运维成本极高。

第二是安全问题。暴露几万个公网 UDP 端口，等于把服务的对外攻击面扩大了几万倍，网络安全策略很难精细化，安全审计也非常困难。一旦有端口配置错误或者安全漏洞，影响范围会非常大。

第三是弹性扩容的问题。在 Kubernetes 里，工作负载随时会被扩容、缩容、重新调度到不同的节点上，这是 Kubernetes 的核心设计哲学：工作负载应该是可以自由迁移的。但是 one-port-per-session 要求每个运行实例都稳定保持一批公网 UDP 端口，当实例被调度到新的节点时，这些端口的分配和回收就会变得非常脆弱，端口和实例的绑定关系一乱，正在进行的媒体会话就会中断。

这三个问题叠加在一起，成为了 OpenAI 工程团队必须解决的核心挑战。他们需要找到一种方式，把公网 UDP 的暴露面缩小到极少的固定地址和端口，同时还能正确地把每个用户的数据包路由到负责该会话的那个 transceiver 实例。

他们的解决方案叫做 relay 加 transceiver 的分层架构，这也是这篇文章最核心的工程创新。

核心思路是把两件事拆开来处理：接收公网流量，以及维护 WebRTC 会话状态。

Relay，中继器，是一个极其轻量级的 UDP 转发服务。它对外只暴露非常小的、固定的公网 UDP 地址和端口，所有用户的数据包都打到这里。关键点来了：relay 不做任何 WebRTC 协议的处理。它不解密媒体，不运行 ICE 状态机，不参与 codec 协商，也不知道什么是 DTLS 握手。它就做一件事：看一眼数据包头部里面的几个字节，读出路由信息，然后把这个数据包原封不动地转发给正确的 transceiver 实例。

Transceiver 仍然是完整地拥有整个 WebRTC 会话状态的地方，包括 ICE 连接信息、DTLS 握手状态、SRTP 加解密密钥、会话的生命周期管理。从客户端的视角来看，它面对的是一个完全标准的 WebRTC 端点，感知不到 relay 的存在，整个客户端的代码完全不需要做任何修改。

这个架构最精妙、也是最需要深入理解的地方，是 relay 如何处理第一个数据包的路由问题。

你想一想这个场景：relay 收到用户的第一个 UDP 数据包时，这是一个全新的会话，relay 和任何一个 transceiver 之间还没有建立关于这个用户的任何路由记录。Relay 怎么知道这个包应该转发给哪个 transceiver 实例？

有一种思路是查询外部系统，比如让 relay 去问一个路由注册中心："这个用户的包应该发给谁？"但这样做有个严重的问题：一次外部查询往往需要几十毫秒，这对于实时语音系统来说是完全不可接受的延迟，而且引入了外部依赖，让数据包的热路径变得复杂。

OpenAI 的解决方案非常巧妙，他们利用了 WebRTC 协议里原本就存在的一个字段：ICE ufrag。

ICE ufrag 的全称是 username fragment，用户名片段，这是 ICE 协议在会话建立阶段双方互相交换的一个短字符串标识符。标准的 WebRTC 流程是这样的：双方通过信令交换 SDP，SDP 里包含了每一方的 ICE ufrag。当客户端开始发送 STUN 数据包，也就是 Session Traversal Utilities for NAT 协议的数据包，来做 ICE 连通性检查时，这个数据包里会携带服务器端的 ufrag，用来声明"我是在找这个特定的会话"。这是 ICE 协议的标准行为，所有实现了 WebRTC 的客户端都会这样做。

OpenAI 的做法是：在服务器端生成 ufrag 时，不是随机生成一串字符串，而是在这串字符串里编码进路由元数据，包括目标 transceiver 集群的信息以及目标 transceiver 实例的信息。这串字符串对客户端来说完全透明，客户端不知道里面有路由信息，它只是按 ICE 协议的标准规范把这个 ufrag 带在 STUN 请求里发出去。

Relay 收到这个 STUN 数据包之后，解析包头，读出 ufrag，从中解码出路由元数据，就知道了这个包应该转发给哪个 transceiver 集群的哪个实例，然后直接转发。这一切完全发生在内存里，不需要任何外部查询，速度极快。

完成第一个包的路由之后，relay 会在内存里建立一个映射记录，把客户端的源 IP 加端口，映射到对应 transceiver 的目的 IP 加端口。后续的 DTLS 握手数据包、RTP 音频数据包、RTCP 控制数据包，全部按照这个内存里的映射记录直接转发，不需要再去解析 ufrag，整个转发流程非常轻量。

文章里还介绍了一个细心的容错设计。Relay 被设计成可以随时重启的轻量服务，如果某个 relay 实例重启了，内存里的映射记录就丢失了。这时候怎么办？答案是：下一个 STUN 数据包到来时，relay 可以再次从 ufrag 里解码路由信息，重新建立映射记录，这个过程几乎是瞬间完成的。此外，他们还用了 Redis，一个高性能的内存数据库，来缓存客户端地址到 transceiver 地址的映射关系。这样即使在 relay 重启期间，也能更快地从 Redis 里恢复路由，不需要等下一个 STUN 包到来。这是一个非常典型的"快速自愈"设计思路：接受局部故障的存在，同时确保系统能够快速自动恢复，而不是试图完全避免任何故障。

这个用 ICE ufrag 编码路由元数据的设计，我个人认为是整篇文章里最精彩的一个点。它利用了协议原生就存在的字段，没有修改任何客户端行为，没有增加新的协议扩展，没有引入任何外部查询，却优雅地解决了"第一个数据包如何路由"这个看似棘手的问题。

完成了单站点的 relay 加 transceiver 架构之后，下一步是全球化部署。OpenAI 把这个叫做 Global Relay，全球中继网络。

在理解 Global Relay 之前，有一个重要的网络原理需要先说清楚。当我们讨论语音 AI 的端到端延迟时，这个延迟由几个部分构成：模型推理的时间，这个很难压缩，因为模型本身需要时间思考；还有网络传输的时间，用户的语音从设备传到服务器需要多久，以及服务器生成的语音传回用户设备又需要多久。

网络传输的延迟，在很大程度上取决于用户和服务器之间的物理距离，以及数据包在这段路程上经过的网络路径的质量。如果你在上海，OpenAI 的服务器在美国西海岸，你的数据包就需要跨越整个太平洋。光速在光纤里的传播速度大约是每秒二十万公里，跨太平洋的路程单程就要六七十毫秒，再加上公网路由不是理想状态，实际的往返延迟会更高，而且公网路径上容易有抖动和丢包。

Global Relay 解决的就是这个问题。OpenAI 在全球多个地理位置部署 relay 节点，每个节点的代码完全一样，都是那个轻量的 UDP 转发逻辑。上海的用户，数据包只需要走到亚洲最近的 relay 节点，就进入了 OpenAI 自己管控的骨干网络，剩下的路程都在这个骨干网上走，延迟更低、更稳定、更可预测。

你可以类比快递的物流中心网络。以前从成都寄东西到上海，包裹可能要先飞到北京，再转飞上海，走了很多弯路。现在有了更合理的物流枢纽布局，成都的包裹可以直接走成都到上海的高铁，路程大幅缩短。Global Relay 做的就是类似的事：把"进入 OpenAI 网络"这个动作，从远在美国变成就在附近。

更精妙的是，这套 Global Relay 的路由引导和信令流程是紧密结合的。当用户发起 WebRTC 连接的信令请求时，OpenAI 用 Cloudflare 的地理位置就近引导功能，把这个信令请求路由到离用户最近的 transceiver 集群。Transceiver 集群在生成 SDP 回答时，会把离该用户最近的 Global Relay 节点地址写进去，同时在 ufrag 里编码足够的路由信息，让 Global Relay 知道应该把收到的流量转发给哪个 transceiver 集群。这样，从会话一开始，信令路径和媒体路径就都被锚定在地理上最合适的位置，用户到 OpenAI 网络的第一跳尽可能短，ICE 连通性检查也更快完成，用户等待开始说话的时间就更短。

接下来我们深入看一下 relay 服务的实现细节。这个服务是用 Go 语言写的，OpenAI 使用了 Pion 这个 Go 语言的 WebRTC 库作为基础，文章里特别强调他们有意识地让实现保持简洁，没有引入复杂的底层优化框架。这句话背后有很多工程智慧，我来给你一一展开。

第一个技术细节是 SO_REUSEPORT，这是一个 Linux 内核提供的 socket 选项。在默认情况下，一个 UDP 端口只能被一个进程绑定，所有进来的数据包都由这一个进程的读取循环来处理，这就是一个单点瓶颈。SO_REUSEPORT 允许同一台机器上的多个进程或者线程同时绑定同一个 UDP 端口，内核会负责把进来的数据包均匀分发给这些绑定者。这样，同一台 relay 服务器上可以运行多个并行的工作线程，每个线程独立处理一批数据包，突破了单一读取循环的吞吐量上限。

第二个技术细节是 runtime.LockOSThread。Go 语言的并发基础单元是 goroutine，Go 自己的轻量级协程，运行时调度器会把大量 goroutine 自动调度到少量的操作系统线程上执行。在大多数情况下，这种调度是透明的，程序员不需要关心。但对于处理网络数据包的场景，goroutine 在不同 CPU 核心之间来回迁移会造成 CPU 缓存失效，增加上下文切换的开销。runtime.LockOSThread 把负责读取 UDP 数据包的 goroutine 锁定在一个特定的操作系统线程上，也就是锁定在一个固定的 CPU 核心上。配合 SO_REUSEPORT，来自同一个网络流，也就是同一对源目的 IP 地址加端口的数据包，会稳定地在同一个 CPU 核心上处理，CPU 缓存命中率更高，不必要的上下文切换减少，整体处理效率提升。

第三个技术细节是预分配缓冲区、最小化内存分配。Go 语言有自动垃圾回收机制，简称 GC。GC 对于大多数应用来说是一个非常方便的功能，让开发者不需要手动管理内存。但对于追求极低延迟的网络应用来说，GC 暂停是一个头疼的问题：每次 GC 运行时，应用可能会有短暂的停顿，造成数据包处理延迟出现毛刺，也就是偶尔突然变长的情况。他们的做法是在服务启动时预先分配好足够大的内存缓冲区，在处理每个数据包时尽量复用这些预分配的缓冲区，减少运行时动态分配内存的次数，从而降低触发 GC 的频率，消除延迟毛刺。

第四个值得说的选择是，他们没有使用内核旁路技术，英文叫 kernel bypass。内核旁路是一类专为高性能网络应用设计的技术，代表性的框架包括 DPDK。它允许用户态程序绕过操作系统内核的网络栈，直接轮询网卡的数据队列，从而大幅提升数据包处理的吞吐量，适合电信级的包交换系统等需要极致性能的场景。但内核旁路框架的运维复杂度很高，需要特殊的网卡驱动配置，调试起来也更困难。

OpenAI 发现，通过上面这几个相对简单的优化手段，他们的 Go 实现已经足以支撑全球的实时媒体流量规模，不需要引入内核旁路。这是一个非常清醒务实的工程决策：在满足实际需求的前提下，优先选择实现更简单、运维更方便的方案，把复杂的技术留给真正需要的时候。用他们自己的话说，"先把简单方案的潜力用尽，再考虑复杂方案"，这是一种很值得学习的工程哲学。

关于人才，文章里还透露了一个有意思的信息：Pion 这个 Go 语言 WebRTC 库的创建者和维护者 Sean DuBois，以及 WebRTC 最早的架构师之一 Justin Uberti，这两个人现在都是 OpenAI 的员工。这意味着 OpenAI 在实时媒体基础设施这个方向，是在最顶尖的领域专家指导下，基于最成熟的开源实现来构建系统，而不是从零造轮子。这也说明 OpenAI 对语音和实时交互这个方向的战略投入，远不是简单地调用 API 拼凑，而是在打造自己深度的技术护城河。

好，聊完了技术细节，我们来看看这篇文章对于我们这些正在做 AI 应用的工程师，有哪些实际的参考价值？

第一点，如果你在用 OpenAI 的 Realtime API 构建实时语音应用，理解这套底层架构能帮你更好地排查问题和优化体验。当你的应用出现语音延迟、连接不稳定、偶尔卡顿的问题时，你能快速判断问题出在哪一层：是信令阶段的问题，还是媒体传输路径上的问题？是地理路由不合理，还是本地网络的抖动？有了这套架构知识作为基础，你的排障思路会清晰很多，而不是对着黑盒子猜测。

第二点，这篇文章给出了一个非常清晰的架构设计原则：把复杂性集中在一个薄薄的专用层里，而不是分散给每个后端服务，也不是推给客户端。在 OpenAI 的方案里，relay 层很轻，它只做转发，不需要懂 WebRTC；transceiver 层很专注，它完全拥有 WebRTC 状态；后端推理服务最轻，完全不需要知道 WebRTC 是什么，只需要处理普通内部协议。每一层各司其职，复杂性边界清晰。这种分层设计的思路，在任何需要处理复杂网络协议的系统里都适用，不管你是在做实时视频、游戏同步、金融行情推送，还是其他对延迟敏感的实时系统。

第三点，ICE ufrag 编码路由元数据这个设计，给我们提供了一个非常有价值的思维模式：当你需要在系统里传递元数据时，优先看看已有协议里有没有合适的字段可以复用，利用协议原生的机制往往比发明一个新协议层更优雅，对现有客户端的影响也最小。这个思路可以推广到很多协议设计场景：在 HTTP 请求头里携带分布式追踪的 trace ID，在数据库连接参数里携带路由 hint，在 DNS 响应的 TTL 里编码负载均衡权重，这类"借用协议原生字段"的设计在大型系统里非常常见，而且往往是最优雅的解法。

第四点，如果你的团队正在规划自建一套实时音视频系统，或者正在考虑如何在 Kubernetes 上部署 WebRTC 相关服务，这篇文章踩过的坑你一定要提前消化。One-port-per-session 在 Kubernetes 里的可扩展性陷阱，有状态的 WebRTC 协议在无状态容器调度环境里的困境，这些不是 OpenAI 独有的问题，而是所有在云原生环境里部署 WebRTC 的团队都会遇到的挑战。提前规划好分层架构，把有状态的部分和无状态的部分分清楚，比等到生产环境出问题再来补救，要省力得多，也要安全得多。

第五点，对于做 Go 语言高性能网络服务的工程师来说，文章展示的性能优化组合拳非常实用：SO_REUSEPORT 多工作线程绑定同一端口、LockOSThread 锁定 CPU 核心、预分配缓冲区减少 GC 压力。这三个手法单独来看都不新鲜，在 Go 网络编程的最佳实践里经常能看到，但这篇文章给出了一个真实的大规模生产应用案例，证明这个组合在实际场景里足够有效，让你不需要上升到内核旁路的复杂度就能满足高性能要求。这是一个很有说服力的压测数据。
